# execution_engine

The run engine module of the TxResBench app: one analysis = one persisted run
row holding the analysis config (outcome, decision day, look-ahead,
covariates, N-at-a-time, save-model flag, selected methods / resolved
models) and the input snapshot. The module validates eligibility per method
at run start, prepares each method's contract bundle, drives the environment
download state, executes each method in its own sandboxed stack under the
analysis's lane count, streams per-method state/logs over SSE, keeps failures
with their reasons, normalizes container output into the contract's universal
outputs, and persists everything so a later screen can reopen a run, rerun it
with the same settings and clear it. It is one server module with typed HTTP
surfaces under `/api/txr/*` and an in-process repository seam for the
modules that consume its records.

## Boundaries

- No sandbox machinery: bwrap argv, layer mounting, env fetch/verify/cache are
  the `sandbox` module's (`run_method_in_stack`, PROV-SS-1/3/4; `MethodEnvManager`,
  PROV-SS-4). The engine passes the manifest's refs as data and never spells a
  registry host (INV-5).
- No env-image build/publish: `method-env-images` publishes the committed
  `src-app/server/data/method-env-images.json` this module embeds.
- No catalogue facts / eligibility engine / estimates: `method_catalogue` is
  this module's in-process provider (the `envmanifest::facts_for` seam).
- No CSV/Excel parsing or the canonical bundle model: `file_validator` owns
  them; the engine calls its `validate` + `canonical_bundle` on the in-memory
  parsed tables.
- No model persistence: saving/exporting trained models is the consumer
  module's join against the run record's produced-model rows; the engine
  produces `/model` outputs and records their digests.
- No UI: the screens that render this state are the sibling modules.

## Embedded data — what is generated from what

The engine's runtime reads two committed first-party data files (INV-4: the
app ships its own copy; nothing is read from the benchmark tree at run time).
Both are compiled into the binary and both are boot-validated — a file this
binary cannot interpret is a boot refusal, never a degraded silent state.

| embedded | generated by | consumed via |
|---|---|---|
| `src-app/server/data/method-env-images.json` (schema v1, `layer_schema: 1`) | `scripts/generate-method-env-images.py` (reads the methods repository at build time; one entry per runnable method per published arch, sorted by `(env_id, arch)`, byte-identical for one `source_revision`) | `envmanifest` — `env_for`/`base_for`/`size_bytes` (the host-arch entry: layer oci ref + tag + byte-verify pin + size, and the base pairing anchor) |
| `data/method-catalogue/catalogue.json` (schema v1) | `scripts/method-catalogue/gen_method_catalogue.py` (reads the benchmark tree at build time) | `envmanifest::facts_for` — the `method_catalogue` in-process accessor (group, tasks, draw facts, fitted/saves/frozen facts) |

The manifest's `base_ref` is the pairing-anchor NAME, never a fetch target:
the layer design (§7 of `docs/design/method-env-layer-artifacts.md`) makes
the digest the identity (`com.txr.trimmed-from-digest`), and the app's own
base namespace is the `sandbox` module's. A method whose manifest entry is
missing stays a per-method `cannot_run` + `ENV_UNKNOWN` at run start (the
catalogue set and the published layer set legitimately differ — the layer set
grows as methods are published).

Regeneration (on the publisher's machine; the generator reads the methods
repository at build time only):

```sh
python3 scripts/generate-method-env-images.py --check
python3 scripts/method-catalogue/gen_method_catalogue.py --check
```

Both `--check` runs validate parity against the committed bytes; both write
nothing.

## HTTP surface (`/api/txr/*`, gated by the reused `jobs::use`)

- `POST /txr/runs` (202 `TxrRunSummary`) — create + start a run (400
  `EMPTY_METHODS`/`EMPTY_MODELS`/`INVALID_*`, 404 `METHOD_NOT_FOUND`, 409
  `RUN_ALREADY_ACTIVE`); `GET /txr/runs` (paged) + `GET /txr/runs/{id}`
  (the detail: summary + method rows + produced models + estimate + outcome
  facts; 404 `RUN_NOT_FOUND`).
- `GET /txr/runs/{id}/stream` — the SSE stream (status / method / log /
  progress / prediction frames; replay-on-connect + terminal close).
- `GET /txr/runs/{id}/logs` — paged log lines (`after_seq`, `method_id`,
  `limit` ≤ 2000).
- `POST /txr/runs/{id}/{stop,methods/{method_id}/stop,methods/{method_id}/
  skip,rerun,at-a-time}` + `DELETE /txr/runs/{id}` + `DELETE /txr/runs` —
  the control surface (202/200/204; 400/404/409 per the plan's closed error
  vocabulary).
- `GET/POST /txr/runs/{id}/predictions(.csv)` — the heatmap data + the CSV
  download, served while the run is active (finished methods only; 409
  `PREDICTIONS_UNAVAILABLE` when none).
- `GET/PUT /txr/analysis-config` — the sticky E-screen settings singleton.

The per-method columns the predictions surface serves are the ENGINE'S
recorded artifact `output/<method_id>/chance.csv`
(`patient_id,probability,note` — 6-decimal probability, empty when abstained,
the per-patient note escaped): the container's raw `predictions.csv` stays the
provenance, while the recorded column carries what the engine actually served
after validation and — for a method with no native probability — after the
conversion band (the raw file cannot be re-derived into it).

## Files

- `mod.rs` — the `AppModule` (`ModuleEntry` order 49), init wiring, the
  module doc; `types.rs` — the typed request/response contract (PROV-EE-2..9,
  the closed state-machine vocabularies, the `TxrRunEvent` SSE vocabulary via
  `sse_event_enum!`); `envmanifest.rs` — the embedded-data seam (manifest
  model + boot validation + lookups + the catalogue-facts shim); `bundle.rs` —
  the contract-bundle assembly (canonical rows → the `/input` files +
  `params.json`, the package contract 2.0 port of `prepare.cpp`, pure
  functions) plus per-method marker sets (the package's count rule: a method
  named on a fixed marker list gets exactly its markers; a method without one
  takes the file's markers or refuses) and the task-compatibility check (the
  provider's reason codes verbatim) — and the module's ONE CSV codec
  (`parse_csv`/`parse_number`, the package's `table.cpp` port, used to write
  the bundle files and to read the methods' outputs); `predictions.rs` — the
  method-output ingest and the U2 recalibration band: parse + validate
  `/output/predictions.csv` and `/output/run.json` against the contract 2.0
  `method_output` rules, the per-method chance-column selection
  (`p_<outcome>_H<h>` for the survival outcomes, `p_<outcome>` for the
  response ones), the per-patient abstention notes and coverage, the
  `PREDICTION_INVALID` failure typing (pure functions; the port of
  `method.cpp::validate_method_output`), and the risk→probability conversion
  for the methods that write no native probability (the port of
  `conversion.cpp`): a weighted logistic regression on the standardised
  training score — the weighted event rate when the scores do not vary or do
  not rise with the event — with IPCW weights at the survival horizon, an
  inner 3-fold cross-fit for the methods that learn from outcomes, and the
  `RECALIBRATION_FAILED` typing when no usable (risk, label) pair exists;
  `repository.rs` — the persistence seam: the typed repository over the four
  tables (runs with their JSON facts, per-method rows, the run-scoped log with
  one global `seq` per run + the `MAX_LOG_LINES_PER_RUN` oldest-trim, the
  per-state aggregate counts query, the sticky analysis-config singleton,
  delete/clear with the schema's cascade) and the `produced_models` seam the
  saved-model consumer binds (a method row is a produced model only when its
  record is complete — digest, dir, env pair, trained cohort, size);
  `reconcile.rs` — the boot reconcile (DEC-17): a run the previous process
  left in `creating|preparing|running|finishing` turns `failed` +
  `INTERRUPTED` at boot, its in-flight method rows fail with the code, a
  finished method's result stays readable, one "interrupted on restart" line
  lands, nothing auto-reruns (idempotent; armed exactly once per process);
  `runtime.rs` — the per-run SSE + run-stop registry (the `jobs::runtime`
  mirror for one analysis run: the module-installed broadcaster the stream
  route subscribes to and the run-stop channel the drive loop selects on,
  capped at `TxrLimits::SSE_CLIENTS_MAX`); `routes.rs` — the 16 `Txr.*`
  endpoints (PROV-EE-2..EE-8 + the at-a-time GROWTH): thin transport over
  the repository + the orchestrator seams, the typed-body extractor (the
  named-400 mapping), the SSE replay contract and the predictions read
  engines over the recorded `chance.csv` columns;
  `orchestrator.rs` — the run
  drive: `start_run` (validate the request, validate + canonicalize the
  in-memory tables once per run, persist the `preparing` row, write the run
  dir + input snapshot, classify every selected method — the providers'
  verdicts + the env-manifest entry — then spawn the detached drive task),
  the lane gate (`at_a_time` permits, mid-run lane change, never a revoked
  permit), the env phase (base + layer `ensure` with the `downloading` state
  and the 500 ms status poll driving the row counters and the SSE frames),
  the admission wrapper (`admit_within`, job_type `"sandbox"`, cancel
  registered before the admit, `close_slot` in the finally-shaped tail),
  stop/skip on the queue, and `StackMethodExecutor` — the ITEM-9 executor:
  per-method bundle writes + the sandbox call sequence (fit →
  training scores over the cohort — the 3-fold cross-fit for a `fitted`
  method — → the final predict over the surface), the conversion band
  application (`prob_source` native/recalibrated/none, INV-3), the live
  log/progress frames (the drainer appends to `txr_run_logs` + broadcasts
  the SSE frames), result capture (duration/exit code/digests), the
  produced-model facts (`save_models` only), the reuse path (one verified
  `ReuseModel` call against the asset), the create-time estimate, the
  `rerun_of` record + prune path and the run finalize
  (`finishing → finished`); `migrations/2026102600{01..06}_*.sql` —
  the four module-owned tables the consumers bind (`txr_runs`,
  `txr_run_methods`, `txr_run_logs`, `txr_app_config`) + the additive `0005`
  produced-model columns of `txr_run_methods` + the additive `0006` run
  estimate column of `txr_runs`.

## Data hygiene rules

- No data of any kind is committed: run workspaces, bundles, logs and model
  outputs live under the app data directory (never the repo).
- No network I/O in this module; no telemetry; no host literal in source
  (the registry refs are manifest data, scheme-less).
- The module's strings use the app vocabulary (`analysis`, `cohort`,
  `patients`).
- No new crate, no new permission, no guard edit: the engine reuses the jobs
  module's admission/cancel machinery, the sandbox module's run seam and the
  providers' typed in-process surfaces.
