# P7 — Visualization integration (Round 1, blind)

**Scope:** adopt live3's `feat/visualization` deck.gl framework as the workbench center-canvas engine, then
perform the **core refactor**: replace its closed `switch(cell.kind)` dispatch with an OPEN
`registerViewKind` registry (the platform `plotTypes` contribution point), publish its conformance battery in
`@cyto/workbench-api`, add **viewer-keyed-by-datatype** dispatch, wire the existing coordination/linked-views
(small multiples + synced brushing), and generalize overlays. **Desktop + 1-box.** Genome/structure/network
viewers = later datatype-contributed families; keep the seam open, do not build them.

**Grounding (verified in live3 code):** the dispatch is genuinely closed — `CellView.tsx::ChartBody` is a
`switch(cell.kind)` EXHAUSTIVE over the closed union `CellKind` (`gridModel.ts` lines 15-25: scatter · image ·
grid · violin · box · bar · dotplot · heatmap · volcano · histogram), each `case` hard-imports a chart View
(`ViolinView`/`BoxView`/…). `CELL_KIND_OPTIONS` (`CellChrome.tsx` lines 18-29) is a hand-maintained copy of the
same union; `isDenseKind()` (`gridModel.ts` line 35) hard-codes `scatter||image`; the conformance battery
(`viewKindBattery.test.ts`) is a `Record<CellKind, KindRunner>` table (compile-time exhaustive over the union).
`showcase/registry.ts` is a *story* catalog only (not a view-kind registry). So: **library-extensible via a
closed union, NOT platform-extensible.** The refactor to an open registry is the P7 headline.

## Items

### A. Adopt live3 as-is (land the framework under the workbench)
- **ITEM-1** Vendor `modules/visualization/viz-core/**` into the analysis-workflow tree unchanged (it is
  deliberately `@ziee/*`-free except the two `adapter/*.store.ts` files). Keep `viz-core` framework-agnostic;
  the `adapter/` layer is the ziee/workbench binding. Confirm the build (`tsc` + the existing vitest suites)
  is green before any refactor — establishes a known-good baseline (per feedback: study the current tree,
  land before refactor).
- **ITEM-2** Re-home the module: today `module.tsx` registers a **standalone `/visualization` route** with a
  `sidebarNavigation` entry, fixture-seeded (`VisualizationPage` → `FixtureSource`, 250k pts). Convert it to
  contribute the grid workspace into the **workbench center-canvas slot** (P6) instead of owning a top-level
  route. Keep the standalone route behind a dev flag for the showcase/gallery.
- **ITEM-3** Replace the `FixtureSource` binding with the platform **data API** (`WorkbenchAPI.data`, P1) behind
  the *unchanged* `DataSource`/`DatasetCatalog` interface (`wire.ts` lines 108-120) — this is exactly the seam
  live3 designed for ("the SAME interface later points at the real octet endpoints"). Fixture stays as the
  gallery/test source.

### B. The core refactor — closed `switch` → open `registerViewKind` registry
- **ITEM-4** Define the **view-kind contribution type** + registry in `viz-core`:
  `interface ViewKind { id: string; dense: boolean; dataContract: DataContract; render(props): ReactNode |
  DenseMarker; conformance: KindRunner; title?; icon? }` and `registerViewKind(vk)` / `viewKindRegistry`
  (id→entry, list, has). Pure, DOM-free registry object (mirrors `showcase/registry.ts`'s shape, but for
  view-kinds and consumed at runtime).
- **ITEM-5** Rewrite `CellView.tsx::ChartBody`: delete the `switch(cell.kind)`; look up
  `viewKindRegistry.get(cell.kind)` and call its `render({ source, catalog, bindings })`. Unknown id → the
  existing `<Unsupported>` fallback (already present — keep). A dense entry renders nothing here (deck draws
  underneath, unchanged).
- **ITEM-6** Change `CellKind` from a closed union to `type CellKind = string` (a registered view-kind id).
  Replace `isDenseKind(kind)` with `viewKindRegistry.get(kind)?.dense ?? false`. Replace the hand-maintained
  `CELL_KIND_OPTIONS` (CellChrome switcher) with `viewKindRegistry.ids()` (optionally filtered by the cell's
  datatype — ITEM-11).
- **ITEM-7** **Register the 10 built-ins through the same API** (dogfood): a `builtinViewKinds.ts` in `viz-core`
  self-registers scatter · image · grid (dense/container) + violin · box · bar · dotplot · heatmap · volcano ·
  histogram, each wrapping its existing View component + its existing `aggregate`/`chartLayers` builders as its
  `render` + `conformance`. Net behavior byte-identical to the current switch; the switch is just data now.
  This is the acceptance proof that "our own built-ins use only the public contribution API."
- **ITEM-8** Each built-in's `dataContract` declares what it consumes from the platform data kinds
  (`coordinates` N×2 · a `values` column · a `matrix` rows×cols · `groups`) mapped to the data API — replacing
  the ad-hoc `defaultBindings(catalog)` (gridModel.ts lines 58-64) with a per-view-kind binding resolver
  (keeps `defaultBindings` as the fallback resolver).

### C. Publish the conformance battery as the acceptance gate (in `@cyto/workbench-api`)
- **ITEM-9** Move `viz-core/conformance/invariants.ts` (the pure structural predicates: `assertFiniteRange`,
  `assertMatrixShape`, `assertPartitionCoversAll`, `assertMonotoneTicks`, `assertByteQuad`, `assertMaskLength`,
  `assertQuartilesOrdered`, `assertCountsSumTo`, …) into the **published API surface** so third-party view-kinds
  are validated by the *same* gate the built-ins pass. Re-export from `@cyto/workbench-api` (P5).
- **ITEM-10** Refactor `viewKindBattery.test.ts` from a fixed `Record<CellKind, KindRunner>` table to
  **iterate `viewKindRegistry.ids()`**, running each registered view-kind's `conformance` runner over the same
  seeded fast-check fixtures. Add a **runtime host gate** `runConformance(viewKind): Result` the host calls on
  registration of a *contributed* view-kind (reject-on-throw), so a third-party plot that leaks NaN / misaligns
  a buffer / drops a facet point is rejected automatically without human review. Keep determinism knobs
  (`NUM_RUNS`, `FC_SEED`) + the degenerate/NaN/wire-path suites.

### D. Viewer-keyed-by-datatype dispatch (generalize `plotTypes` → viewer registry)
- **ITEM-11** Add a **`ViewerRegistry` keyed by datatype** (per DATA_MODEL §"Viewers are datatype-contributed"):
  the deck.gl view-kind registry is registered as **ONE viewer family** for `matrix`/`embedding`-shaped
  datatypes (single-cell/anndata, spatial/visium, bulk/counts — anything is-a `matrix`). The canvas resolves a
  grid cell's bound artifact → its datatype (P2) → the datatype's declared `viewers` → the candidate view-kinds;
  the CellChrome switcher lists only view-kinds valid for that datatype. Genome/structure/network viewer
  families are **not built** — the registry accepts them as later datatype-contributed entries (seam open).
- **ITEM-12** Wire the datatype→viewer resolution through the platform's **open datatype registry + subtyping
  lattice** (P2): `matrix`-family view-kinds are offered on any subtype of `matrix`. A cell whose artifact has
  no matching viewer family renders a typed "no viewer for datatype X" placeholder (extends `<Unsupported>`).

### E. Coordination / linked small-multiples (adopt + wire to platform selection)
- **ITEM-13** Adopt the **`Coordination` store as-is** (`adapter/Coordination.store.ts`) — it already implements
  shared `viewStates` (synced zoom/pan per scope, `GRID_SCOPE`), `pointSelection`+`selectionOrigin` fan-out
  (a selection in any cell highlights every cell in its own idiom), `gridLinked`, and linked `colorScales`
  (union domain across cells coloring by the same key). This IS small-multiples + synced brushing; no rebuild.
- **ITEM-14** Bridge `Coordination.pointSelection`/`setSelection` to the **platform shared selection API**
  (`api.selection`, P8) so a lasso on the shared canvas becomes the workbench-wide cell-set (consumed by
  annotation/DE/subcluster) and is stored as a provenance recipe (P4/P8). The Coordination store becomes the
  canvas-local mirror of `api.selection`, not a parallel selection model.
- **ITEM-15** Keep the grid workspace (`GridWorkspace.store` + `viz-core/grid/*`: split-tree, drag-swap,
  pop-out/pop-in, per-cell color-by + link-scale) as the small-multiples layout engine — already built; verify
  it composes inside the workbench center slot (P6) rather than a full-page route.

### F. Overlays (generalize the per-cell graph overlay into a contribution point)
- **ITEM-16** Generalize the existing **per-cell `graphOverlay`** (`GridCell.graphOverlay` flag +
  `viz-core/overlays/graphOverlay.ts` + `GraphScatterView` — draws LineLayer/ScatterplotLayer/TextLayer riding
  a dense cell's viewport on the shared deck) into an **`overlays` contribution point**: `interface Overlay {
  id; consumes: datatype; render(cell, api): DeckLayer[] }`. The graph overlay becomes the first registered
  overlay (dogfood), consuming a `graph`/`trajectory` datatype. Overlays render on the shared embedding and
  link with the shared selection — this is the seam interactive tools (annotation highlight, gate polygons,
  trajectory path — PLATFORM_ARCHITECTURE §4.4) contribute onto the canvas.

### G. Tests / gallery
- **ITEM-17** Keep + extend the **showcase gallery** (`showcase/**`, ~30 stories) as the visual-testing surface;
  add a "contribute a toy view-kind through the public registry + it passes the battery + renders in a grid
  cell" story as the end-to-end extensibility proof.
- **ITEM-18** Registry unit tests: register/lookup/duplicate-id/unknown-id-fallback; dense-flag via registry;
  switcher vocabulary = registry ids filtered by datatype; the host `runConformance` rejects a deliberately
  broken toy view-kind (NaN leak / buffer-length mismatch).

## Decisions

- **DEC-P7-1** `CellKind` becomes an open `string` (registered view-kind id), NOT an enlarged closed union.
  The compile-time exhaustiveness live3 relied on (`Record<CellKind, …>`) is replaced by the **runtime
  conformance gate** (`runConformance`) — the correct trade for an open ecosystem (you cannot type-check a
  third-party contribution at the host's compile time).
- **DEC-P7-2** Built-ins self-register through the **same public `registerViewKind` API** (no privileged
  path). This is the dogfood invariant (PLATFORM_ARCHITECTURE §0) and the migration is proven correct by the
  behavior-identical gate (existing tests stay green).
- **DEC-P7-3** The refactor is **behavior-preserving first** (ITEM-7 registers exactly the 10 existing kinds
  with identical render/aggregate). No new plots, no new data wiring, in the refactor step — de-risks it.
- **DEC-P7-4** The deck.gl view-kind registry is **one viewer family (matrix/embedding-shaped)**, registered
  into a datatype-keyed `ViewerRegistry`. Genome/structure/network are **out of P7 scope** — the seam is open
  (registry accepts new families) but no non-deck viewer is built (matches DATA_MODEL + the P7 scope note).
- **DEC-P7-5** Adhere to viz-core's **no-SVG / all-GPU law** (DEC-18/23) for view-kinds; the only SVG surface
  stays the vector `export/*`. A contributed view-kind renders deck.gl layers via `ChartFrame`/`chartLayers`,
  never Vega/SVG — so the safe declarative tier is **parameterize-a-built-in-view-kind**, NOT a Vega-Lite spec
  (PLATFORM_ARCHITECTURE §4.2 correction).
- **DEC-P7-6** The `Coordination` store is the **canvas-local mirror** of the platform `api.selection`, not a
  competing selection model — one selection representation across canvas / interactive tools / provenance.
- **DEC-P7-7** Keep the standalone `/visualization` route behind a dev/gallery flag; the *product* surface is
  the workbench center slot (ITEM-2).

## Risks / unknowns

- **R1 (refactor regression)** Opening `CellKind` from a union to `string` removes `tsc` exhaustiveness across
  the codebase (`gridModel`, `CellChrome`, the battery table, `swapCellContent`, tooltip). Every site that
  `switch`ed or `Record<CellKind,…>`'d must move to registry lookups. **Mitigation:** ITEM-7's behavior-
  identical gate + the existing ~30-story gallery + vitest suites; grep every `CellKind` reference before
  merge.
- **R2 (P5 type-shape coupling)** The `ViewKind`/`Viewer`/`Overlay` contribution types are co-owned with P5.
  If P5's manifest shape diverges from P7's runtime registry, rework. **Mitigation:** ITEM-4 is done *with* P5;
  treat the type as a shared contract, converge in planning.
- **R3 (dense-vs-chart partition leaks into the registry)** `isDenseKind` currently drives deep pointer-events
  + shared-deck-vs-own-ChartCanvas behavior in `CellView` (the pointer-transparency contract, drag-swap
  overlay). A registry `dense` flag must reproduce that exactly. **Mitigation:** keep `dense` as a first-class
  registry field; the built-in dense kinds (scatter/image) register `dense:true`; test the pointer contract.
- **R4 (datatype dispatch depends on P2 shape)** Viewer-per-datatype (ITEM-11) is only as good as P2's
  datatype registry + subtyping. If P2 slips, ITEM-11/12 degrade to "single matrix family for all artifacts"
  (acceptable interim — matches today's single-cell-only behavior). **Mitigation:** seam-open design; default
  family fallback.
- **R5 (conformance gate false-negatives)** The battery is CPU/pure-math (GPU variants proven only in the
  browser harness). A contributed view-kind's GPU layer could pass the pure battery yet mis-render. **Known
  limitation** (live3 documented it); the gate validates *structural* invariants, not pixels — the gallery +
  runtime-health pass covers the visual layer.
- **U1** Exact P6 center-canvas slot API (how the grid mounts + gets its data-API handle) — unknown until P6
  r1. **U2** Whether `api.selection`'s cell-set representation (P8) is bitmask vs index-array — Coordination
  uses `Uint32Array` indices + `IndexMask`; a bitmask bridge may need a converter. **U3** Whether the datatype
  registry (P2) lets a *view-kind extension* declare which datatypes it serves (view-kind→datatypes) vs only
  the datatype declaring its viewers (datatype→view-kinds) — DATA_MODEL says the latter; confirm the direction
  in P2/P5.

## Effort estimate

- **A. Adopt/land** (ITEM-1,2,3): S–M. Vendoring is mechanical; the center-slot + data-API swaps are gated on
  P6/P1 but small once those land. ~2–3 units.
- **B. Switch→registry core** (ITEM-4–8): **M–L, the headline.** Surgical but touches every `CellKind` site;
  behavior-identical gate is the cost. ~4–5 units.
- **C. Conformance publish** (ITEM-9,10): M. Mostly moving + inverting the battery to iterate the registry +
  the host reject-gate. ~2 units.
- **D. Viewer-per-datatype** (ITEM-11,12): M, gated on P2. ~2–3 units.
- **E. Coordination/selection** (ITEM-13,14,15): S adopt + M bridge (gated P8). ~2 units.
- **F. Overlays** (ITEM-16): S–M. ~1–2 units.
- **G. Tests/gallery** (ITEM-17,18): S, continuous. ~1 unit.

**Total ≈ 14–18 units.** The bulk of the *value* (a proven GPU framework + conformance battery + linked
small-multiples) is **reused**, not built; P7's genuine work is the **switch→registry refactor + publishing
the battery + datatype-keyed dispatch + overlay generalization** — everything else is adopt-and-wire.
