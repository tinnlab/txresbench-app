# P9 ai-mcp — Build Plan (r2)

**Scope:** the contribution-registry→MCP tools/resources GENERATOR (one P5 declaration → UI + MCP tool + REST) +
LLM metadata + safety hints + a per-study MCP server + approval/permission gating + chat integration.
**Deployment scope:** desktop + single-box server only (§BUILD_PLAN deployment table). No remote/cluster.

## Findings that anchor this plan (grounded in code)
- **The host chat + MCP + tool-approval substrate is ABSENT from CytoAnalyst.** `/data/pbya/ziee/tmp/cytoanalyst/src-app/server/src/modules/` has only `app, dataset, file, health, jobs, rootfs, sandbox, study, sync, user` — **no `mcp`, no `chat`, no `control_mcp`, no ai-providers.**
- **The SDK already anticipates this gap.** `sdk/crates/ziee-control-mcp/src/lib.rs` extracts ONLY the DB-free tool-dispatch core (`catalog`/`policy`/`tools`) and states verbatim: *"a fresh app can't self-expose control until the **Tier-1 `mcp` registry (v1.5)**"* — the JWT-forwarding `handlers`, `routes`, `mcp_servers`-row `repository`, and `chat_extension` **stay in ziee**. So P9's foundation = that Tier-1 substrate, not yet built for CytoAnalyst.
- **The generator is control_mcp re-sourced.** ziee `control_mcp` builds an in-memory `ControlCatalog` from the finished `aide::openapi::OpenApi` (`catalog::init_from_openapi` → `build_catalog`), classifies each op via `policy` (mutating/deny/secret), emits 3 tools (`list/describe/invoke_capability`), and `invoke` dispatches to the REAL REST route over loopback carrying the caller's JWT (re-authorized DB-side). **P9 replaces the OpenAPI source with the P5 contribution registry** and dispatches to the capability path (JobRunner / command / setByPredicate) instead of a REST op.
- **One declaration → three surfaces** (§0.4/§0.4.2): an `AnalysisContribution` already has `{description, when, examples, safety, ai?, params:JsonSchema, accepts, produces}` — an MCP tool IS name+description+JSON-schema, so the tool is generated for free; the same metadata powers the human form's help.
- **Two-level authz** (§0.4/§0.5): outer **study role** (owner/editor/viewer, live8 `EffectivePermission`) + inner per-contribution `gate:` permission. read-run auto-approved per policy; mutating/destructive gated by tool-approval.

## Items

- **ITEM-1 (BLOCKING · substrate)**: Land the SDK **Tier-1 `mcp` substrate** as `sdk/crates/ziee-mcp` — port ziee `modules/mcp` domain-stripped: `mcp_servers` table + built-in-server upsert seam, MCP client (`client/{session,manager,traits,http}`), `chat_extension` tool-collection + LLM injection, **tool-call approval** (`tool_use_approvals`, `ApprovalMode`), **tool_calls history** (`mcp_tool_calls` + prune), untrusted-content guard, `auto_attach_builtin_ids`/`is_builtin_server_id` seam. Drop ziee-domain coupling (chat-project extension, workflow/scheduled-task FKs — cf. SDK_GAPS N-1). This is what ziee-control-mcp's doc calls "v1.5."
- **ITEM-2 (BLOCKING · substrate)**: Land the **LLM call-loop + provider** substrate — `sdk/crates/ziee-ai-providers` (OpenAI-compatible chat/tool-use client) + a minimal **chat module** in CytoAnalyst (`modules/chat`: conversation + message store, streaming, hosts the chat_extension chain that injects MCP tools + runs the tool-approval loop). Decision-gated below (port-vs-minimal). Without a chat loop the generated tools have no driver.
- **ITEM-3 (P5 seam)**: Define the **backend-readable ContributionCatalog** — P5 must expose analyses/commands/selection-actions to the *backend* with LLM metadata (`id, title, description, when, examples, safety, ai, category, gate?, params:JsonSchema, accepts[], produces`). Built by `init_from_registry(...)` at boot (analogous to `catalog::init_from_openapi`), sourced from built-in registrations + manifest provisioners. **The generator ingests THIS, not OpenAPI.** (Owned by P5; P9 consumes.)
- **ITEM-4 (generator core)**: `modules/workbench_mcp/generator.rs` — pure builder that turns each AI-exposed contribution into an **MCP tool descriptor**: `name = contribution id`, `description = description (+when/examples appended)`, `inputSchema = params JsonSchema` with `accepts` artifact-refs rewritten to typed `"artifact id of type <kind>"` params, `annotations = {readOnlyHint, destructiveHint}` from the safety hint. Mirrors `control_mcp/tools.rs` shape but generated per-contribution. Reuse the `ziee-control-mcp` crate by extracting a **generic `ToolGenerator` trait** (or a sibling `ziee-mcp-generator`) so control's OpenAPI generator and the workbench's registry generator share the projection code.
- **ITEM-5 (dispatch)**: `handlers.rs::invoke` — resolve tool id → contribution → dispatch to the REAL capability path carrying the caller's JWT + `study_id` scope: **analysis** → enqueue P3 `JobRunner` (produces a P4 run node); **command/selection-action** → the command handler; **`selection.setByPredicate`** → P8 predicate evaluator. Re-authorizes DB-side (never reimplements authz), exactly like control_mcp's loopback REST dispatch. Produces the same run node a human click would (§0.4 co-drive).
- **ITEM-6 (LLM metadata mapping)**: One metadata set → tool surface: `description/when/examples` → tool description + LLM routing hint; per-param `doc` → param schema `description`; `ai:false` → contribution **omitted** from the generated tool list; safety `read-run|mutating|destructive` → tool annotations + approval class (ITEM-10). Same strings power the human form (§0.4.2) — no separate LLM copy.
- **ITEM-7 (resources — the AI's world model/planner)**: `resources.rs` — expose as MCP resources: the **typed-artifact catalog** (P1 `analysis_results` + P2 datatypes → the planner graph), the **current selection** (P8), the **data-API schema** (obs/var columns, N/G, embedding ids — P1), and the **cell-set DSL operator vocabulary** (P8). All study-scoped + owner/role-filtered.
- **ITEM-8 (per-study MCP server)**: One workbench MCP server **scoped per study** — deterministic base id + study id → the server row; tools/resources filtered to that study's artifacts. The study is the tenancy unit (§0.5). Register the built-in row per study (or one row, study passed as tool context) — Decision below.
- **ITEM-9 (two-level authz filter)**: `policy.rs` — outer **study role** (P10 `EffectivePermission`: viewer→only `read-run` tools exposed; editor→+mutating; owner→+destructive) AND inner per-contribution `gate:` permission filter, so **the model never sees a forbidden tool** (control_mcp's per-user filter pattern). Re-check both at dispatch (defense-in-depth).
- **ITEM-10 (safety→approval flow)**: Map safety hint to the ITEM-1 tool-approval workflow: `read-run` auto-approved per conversation policy; `mutating`/`destructive` require explicit approval; destructive additionally surfaces a confirm. read-analyses auto-approve / destructive gated (§0.4).
- **ITEM-11 (untrusted-content guard)**: Analysis results + any fetched content injected as tool results carry the untrusted-content guard note (results are DATA; never follow embedded instructions). Reuse the substrate guard (ITEM-1).
- **ITEM-12 (chat integration/auto-attach)**: `chat_extension.rs` (order before the mcp tool-collector) — sets `attach_workbench_mcp` when a study is open + the model is tool-capable; the two substrate edits (`auto_attach_builtin_ids` + `is_builtin_server_id`) auto-attach the per-study workbench server and bypass per-call approval for `read-run` tools. Injects a one-line study-context + DSL-vocabulary system note.
- **ITEM-13 (provenance + co-drive)**: Every AI tool call → a **run node** (§0.6, P4) + a `mcp_tool_calls` history row (ITEM-1). The result-write emits **study-scoped sync** (P10) so a collaborator's live workbench updates — human + AI co-drive one shared state (§0.4).
- **ITEM-14 (worked-example tools)**: Verify the §0.4.1 compound flow end-to-end as two generated tools: `selection.setByPredicate(<DSL>)` (P8 evaluator, in-process, stores predicate as recipe) → `annotate.assign(label, selection)` (permission-gated mutating, writes an `annotation` artifact + run node). The DSL is a bounded structured arg (no code) so an AI selection can't harm; assign is the gated action.
- **ITEM-15 (frontend)**: `src-app/ui/src/modules/workbench-ai/` — a chat/AI **panel** as a `ViewContribution` in a workbench dock (P6), streaming assistant + **tool-approval UI** (approve/deny pending tool calls, show tool + args + safety badge) + a "what the AI did" provenance link. Reuse ziee chat UI kit if the chat substrate ports its FE; else minimal.
- **ITEM-16 (registration + kill-switch)**: `mod.rs` module registration (order after the mcp substrate so the table/client exist), deterministic `workbench.cyto.internal` server id, deploy-level `workbench_mcp.enabled` kill-switch gating init + routes + row upsert (control_mcp §16 pattern), loopback-pinned URL.
- **ITEM-17 (tests)**: Unit (generator maps a contribution→tool incl. artifact-ref rewrite; safety→annotation; `ai:false` hidden; role/permission filter). Integration (per-study tool list filtered by viewer/editor/owner; `invoke` dispatches + re-authorizes + 403s a viewer's mutating call; tool_calls recorded; provenance run node created). Real-LLM (a chat drives cluster→select-by-predicate→annotate end-to-end — gated on API key). E2E (chat panel + approval UI).

## Decisions
- **D1 — Substrate lands as SDK Tier-1 crates, not an app-local port.** `ziee-control-mcp`'s own doc names "Tier-1 `mcp` registry (v1.5)" as the unblock, and SDK_GAPS is the coordination channel. Extract `ziee-mcp`+`ziee-ai-providers` (+ a minimal chat) into the SDK so app #3 inherits them too. Fallback if live1 can't land it in time: port ziee's `modules/{mcp,chat}` + `ai-providers` **into CytoAnalyst app modules** (domain-stripped) and file the extraction as a gap.
- **D2 — Chat is a minimal in-app module, not a full ziee `chat` port.** CytoAnalyst needs only conversation + message + streaming + the chat_extension tool loop. Skip ziee's projects/loop-settings/title/export machinery. Reduces scope; add later if needed.
- **D3 — The generator is SHARED code with control_mcp** (a generic `ToolGenerator` projection), not a fork. control = OpenAPI-sourced; workbench = contribution-registry-sourced; both emit MCP tool descriptors + the same JWT-forward invoke discipline.
- **D4 — One workbench MCP server row, study passed as tool CONTEXT** (not N per-study rows) — simpler registration; the handler resolves the active study from the conversation/session and scopes there. (Alternative: per-study rows for isolation — heavier; revisit if a conversation must bind multiple studies.)
- **D5 — Default AI-exposed set = analyses + commands + selection-actions**; views/renderers/field-providers are internal (§0.4.2). `ai:false` opts a contribution out.
- **D6 — Dispatch reuses the capability path, never a shadow executor.** An AI analysis call enqueues the SAME `JobRunner` a human click does → identical run node/provenance/sync. No AI-specific compute path.
- **D7 — Safety mapping:** `read-run`→auto-approve (per policy) + `readOnlyHint`; `mutating`→approval; `destructive`→approval + `destructiveHint` + confirm.

## Risks
- **R1 (highest) — the substrate gap.** No mcp/chat/ai-providers exists; P9 is ~50% "build the AI substrate" before any generator work. Mitigate: land ITEM-1/2 as SDK crates early, coordinate with live1, stub the generator against a fake catalog meanwhile.
- **R2 — P5 backend-readability.** The contribution registry is TS/frontend-first; the backend generator needs a backend-readable manifest catalog. If P5 keeps contributions frontend-only, the generator has nothing to ingest. Mitigate: ITEM-3 must be a firm P5 seam (manifest → backend catalog at boot).
- **R3 — sqlx compile-time vs a runtime contribution store.** If contributions live in a runtime table (Phase-5 provisioners), the generator reads runtime rows — fine — but the migration-merge glob leaks (SDK_GAPS N-1/N-2): hand-scope which SDK crate migrations merge.
- **R4 — Approval UX for agentic chains.** A cluster→select→annotate chain may fire several mutating tools; a per-call approval storm harms UX. Mitigate: read-run auto-approve + batch/"approve this plan" affordance; destructive always explicit.
- **R5 — Study-scope leak.** A generated tool must not reach another study's artifacts. Mitigate: study id is server-derived from the conversation (never a tool arg the model supplies), + owner/role filter at both list and dispatch (mirror control's per-user filter + CytoAnalyst's `get_by_id_and_user` 404-on-foreign discipline).
- **R6 — Provenance completeness.** An AI call that bypasses the JobRunner path (e.g. an in-host builtin) must still record a run node; enforce via D6 (single capability path).
