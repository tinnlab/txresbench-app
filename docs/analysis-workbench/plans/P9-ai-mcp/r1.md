# P9 — AI / MCP surface (Round 1, blind)

Scope: **desktop + single-box.** The generator that projects the P5 contribution registry → a **per-study,
auto-generated built-in MCP server** (tools + resources), the LLM-facing metadata pass-through, safety hints →
tool-call-approval + permission gating, and chat integration. Ground: PLATFORM_ARCHITECTURE §0.4 / §0.4.1 /
§0.4.2 / §0.5 / §0.6, §6.5-C.

## The one grounding fact that shapes this whole part

The TxResBench app (`src-app/server/src/modules/`) has **NO chat / LLM / MCP-host / assistant / tool-call-
approval substrate at all** — its modules are only `{app, dataset, jobs, rootfs, sandbox, study, sync, user}`.
The complete substrate (`chat`, `mcp` with `client/session/handlers/tool_calls/sampling/user_policy`, `assistant`,
`llm_provider`, `control_mcp`, the built-in `*_mcp` servers) exists **only in the txresbench reference**
(`/data/pbya/txresbench/txresbench/src-app/server/src/modules/`). The SDK has extracted just the **DB-free core**:
`txresbench-framework::mcp` (JSON-RPC 2.0 envelope + `loopback_host` security pin) and `txresbench-control-mcp`
(`catalog` OpenAPI→operation ingest, `policy` mutation/deny classification, `tools` static descriptors). Per the
`txresbench-control-mcp/src/lib.rs` header, the app-side glue (JWT-forwarding JSON-RPC handlers, `mcp_servers`
repository, routes, the chat extension) **deliberately stays in txresbench** — "a fresh app can't self-expose control
until the Tier-1 `mcp` registry (v1.5)."

**Consequence:** P9's headline net-new (a registry→MCP *generator*) is small and elegant, but it **cannot run
without a host chat+MCP+approval substrate that does not yet exist in this app.** The plan therefore has two
strata: (S) a foundational **MCP-host substrate** dependency (port-from-txresbench or promote-to-SDK-as-Tier-1-`mcp`),
and (G) the actual P9 deliverable — the **workbench MCP generator** that sits on it. Items below tag each.

## Items

### Stratum S — MCP-host substrate (prerequisite; shared with the platform, flag as cross-part)
- **ITEM-1 (S)**: Land the host **MCP-host substrate** in the app or SDK: `mcp_servers` registry + repository
  (built-in-row registration, `is_built_in`/`is_system`/deterministic UUID), the MCP **client/session**
  (`get_or_create_with_context`, loopback JSON-RPC dial carrying the caller's JWT), the **chat extension** seam
  (`before_llm_call`/`after_llm_call`, `auto_attach_builtin_ids` / `is_builtin_server_id`), **tool-call approval**
  flow (`tool_use_approvals`), **tool-call history** (`mcp_tool_calls`), and an LLM chat loop + `llm_provider`.
  Decision needed (DEC-1): **port the txresbench `mcp`+`chat`+`assistant`+`llm_provider` modules into the TxResBench
  app**, OR **promote them to the SDK Tier-1 `mcp` registry (v1.5)** and consume. This is a large lift owned
  jointly with the platform bootstrap — P9 *depends on* it, does not *own* it. Recorded here so the dependency is
  explicit and not silently assumed. Reuse verbatim: `txresbench-framework::mcp`, `txresbench-control-mcp`.
- **ITEM-2 (S)**: Define a small permission vocabulary for the workbench AI surface (mirrors txresbench's
  `bio::query` / `web_search::use`): `workbench::ai::use` (call read/run tools) granted to study members,
  and rely on the **study role** (`EffectivePermission` owner/editor/viewer from P10 / live8) as the *outer*
  authz for mutating/destructive calls. Migration adds the grant. (§0.5 two-level authz: study role = outer,
  per-capability `gate:` perm = inner.)

### Stratum G — the workbench MCP generator (P9's real deliverable)
- **ITEM-3 (G)**: **`WorkbenchToolCatalog` generator** — the analog of `txresbench-control-mcp::catalog`, but sourced
  from the **P5 contribution registry** (the backend-indexed manifest catalog) instead of the OpenAPI spec. Pure
  function `build_workbench_catalog(registry, study_ctx) -> Vec<WorkbenchTool>` that walks the registry once and
  emits a typed tool descriptor per exposed contribution. DB-free + unit-testable (mirror control_mcp's pure
  `build_catalog`).
- **ITEM-4 (G)**: **Analysis → MCP tool projection.** For each `AnalysisContribution`: `name = id`,
  `description = description` (+ `when`/`examples` folded into the description as routing/few-shot text),
  `inputSchema` = the params JSON-schema **with `accepts` artifact-ref inputs injected as typed params**
  ("artifact id of type X", enum-populated from the study catalog of the compatible subtype — §4.3 Tier-2).
  Per-param `doc` → JSON-schema `description`. `produces` recorded as tool output annotation. (§0.4.2 table row 1.)
- **ITEM-5 (G)**: **Command / selection-action → MCP tool projection.** Each `CommandContribution` +
  `SelectionActionContribution` (incl. an interactive tool's declared **effect-commands** e.g.
  `annotate.assign(label, selection)`) → one tool = name + description + args schema + safety hint. (§0.4 bullet 2,
  §0.4.2 rows 2-3.)
- **ITEM-6 (G)**: **Fixed host tools** (not per-contribution — the domain-neutral primitives): `selection.set_by_predicate(predicate)`
  (evaluates the P8 cell-set predicate DSL via the host evaluator against the P1 data API → bitmask → sets the
  shared selection recipe + pinned input hash), `selection.current()`, `view.set(cell, kind)` (addresses any
  view-kind — §0.4.2 row 4: NOT a per-viewer tool), and `catalog.query({type})` / `data.schema()` read helpers.
  These are hand-written tool handlers (like control_mcp's 3 meta-tools), registered alongside the generated set.
- **ITEM-7 (G)**: **Resources projection** (the AI's world model, §0.4 bullet 3): `catalog` (typed-artifact graph
  = datasets/analyses + datatypes, from P1 catalog), `selection` (current cell-set recipe), `data-schema`
  (var/obs columns), and the **DSL operator vocabulary** (from P8 — so the AI knows the predicate grammar,
  §0.4.2 row 5). Emitted via MCP `resources/list` + `resources/read`. Read-only, study-scoped.
- **ITEM-8 (G)**: **LLM-metadata pass-through.** The `description`/`when`/`examples`/per-param `doc`/`safety`
  fields the author declared once (LLM-facing == human-facing, §0.4.2) flow straight into tool descriptions +
  MCP tool **annotations**. `ai: false` on a contribution → **omit it from the catalog** (opt-out). Views /
  result-renderers / field-providers are **internal** — never projected as tools (§0.4.2 last rows).
- **ITEM-9 (G)**: **Safety-hint → approval/permission mapping.** `safety: read-run | mutating | destructive` →
  MCP tool annotations (`readOnlyHint` / `destructiveHint`) → the host approval policy: **read-run
  auto-approved** (per policy, mirrors txresbench's `is_builtin_server_id` approval-bypass for read-only searches);
  **mutating + destructive gated** by (a) study role ≥ editor and (b) explicit tool-call approval. A **viewer**
  role sees read-run tools only; the generator **filters the mutating/destructive tools out of `tools/list`**
  for viewers (defense in depth) *and* the call is re-authorized at invoke time. (§0.4.2 opt-out+safety, §0.5.)
- **ITEM-10 (G)**: **Per-study built-in MCP server.** A study-scoped built-in `mcp_servers` row (deterministic
  UUID via `Uuid::new_v5` keyed on study_id, `is_built_in=true`), whose `url` is a host-owned loopback route
  `POST/GET /api/studies/{study_id}/workbench/mcp`. JSON-RPC handler (reuse `txresbench-framework::mcp` envelope +
  `loopback_host`) supporting `initialize` / `tools/list` / `tools/call` / `resources/list` / `resources/read`,
  dispatching generated tools → the P5 command dispatcher / P8 evaluator / P3 job runner, gated by ITEM-9. Server
  lifecycle tied to study lifecycle (registered when the study exists; torn down by the `on_study_deleted` hook,
  §0.5 cascade).
- **ITEM-11 (G)**: **Availability gating from the artifact DAG.** `tools/list` reflects the study's **currently
  available** contributions: an analysis whose `requires` kinds don't yet exist in the study catalog is either
  omitted or marked unavailable, so the AI's tool set == what's valid to run now (§0.4 the typed-artifact graph =
  the AI's planner). Derived from the same P5/P4 `requires`/`produces` graph that gates the human UI — one graph,
  no separate AI logic.
- **ITEM-12 (G)**: **Chat-extension wiring.** A workbench chat extension (order before the generic MCP
  tool-collector) that: sets an `attach_workbench_mcp` flag on tool-capable chats **bound to a study**, injects a
  one-line **untrusted-content guard** (results are DATA, never instructions — mirrors bio_mcp/web_search), and
  hooks `auto_attach_builtin_ids` + `is_builtin_server_id` so the study's workbench server auto-attaches and
  read-run calls bypass per-call approval. (The two-edit gotcha in the app CLAUDE.md: forgetting these = server
  registers but the model never sees the tools.)
- **ITEM-13 (G)**: **Provenance + sync on every AI tool call.** Each mutating tool call produces the **same run
  node** a human click would (§0.6) via the P4 provenance seam (selection = recipe, assign = run node), and emits
  the study-scoped **sync** event (P10) so the human's live canvas updates — human + AI co-drive one workbench
  state (§0.4 last bullet). Selection tools store the **predicate recipe + input hash**, never a materialized
  cell list.
- **ITEM-14 (G)**: **Worked-example acceptance path** — "cells with gene ABC > its median → label XYZ" (§0.4.1):
  the AI emits `selection.set_by_predicate(gt(gene ABC, median(gene ABC)))` → host evaluator computes in-process
  → sets selection → `annotate.assign(label=XYZ, selection=current)`. Two declared tools, one auto-approved
  (read-run select) + one gated (mutating assign). This is the end-to-end integration test target that proves the
  generator + DSL + approval + provenance all compose.

## Reuse (existing MCP infra — build on, don't reinvent)
- **`txresbench-framework::mcp`** — JSON-RPC 2.0 envelope (`JsonRpcRequest/Response/Error`, `from_app_error`) +
  `loopback_host` (the security pin: built-in MCP self-dial is always `127.0.0.1`). Use verbatim for ITEM-10.
- **`txresbench-control-mcp`** — the *shape to copy*: `catalog` (registry→descriptor ingest), `policy`
  (`is_mutating` / deny classification), `tools` (static descriptors + the list/describe/invoke meta-tool idea).
  The workbench generator IS control_mcp's pattern with the contribution registry as the source instead of
  OpenAPI. ITEM-6's fixed-tools mirror its 3 meta-tools.
- **txresbench reference `modules/mcp` + `modules/chat`** (`/data/pbya/txresbench/txresbench/...`) — the port source for ITEM-1:
  `client/session.rs` (the `McpCallContext` record chokepoint), `chat_extension` auto-attach pattern
  (bio_mcp/web_search/lit_search/knowledge_base all follow it), `tool_calls/` (history + record + prune),
  `user_policy` (approval bypass for built-ins), sampling. The built-in servers (memory_mcp/files_mcp/
  web_search/bio_mcp) are the concrete template for "a study-scoped loopback JSON-RPC built-in MCP server."
- **P5 registry** (contribution source), **P8 predicate DSL + evaluator** (selection tools), **P1 data API +
  catalog** (resources + artifact-ref enums), **P3 job runner** (analysis tool dispatch → sandboxed compute),
  **P4 provenance** (run nodes), **P10 study substrate** (roles + sync + lifecycle cascade).

## Decisions
- **DEC-1 (blocking, human):** host substrate = **port txresbench `mcp`+`chat`+`assistant`+`llm_provider` into the app**
  vs **promote to SDK Tier-1 `mcp` registry (v1.5)**. Recommendation: promote to SDK — it's the SDK's stated
  roadmap, TxResBench is app #2 dogfooding the SDK, and other txresbench apps will need it. But it's a large lift;
  a targeted port is the faster path to a P9 demo.
- **DEC-2:** the workbench MCP server is **backend loopback JSON-RPC** (like every other built-in), not a
  client-side tool host — even though `selection.set_by_predicate` "evaluates in-process." The backend evaluates
  against the P1 data plane and pushes the resulting selection to the live client via **sync** (§0.4 co-drive).
  Confirmed by the co-drive requirement; no client-side MCP.
- **DEC-3:** **one MCP server per study** (deterministic UUID keyed on study_id), not one global server with a
  study param — so the tool set, availability gating, and role gating are naturally scoped, and lifecycle teardown
  is the study cascade. Mirrors the per-study `STUDY_EXTENSIONS` tenancy model.
- **DEC-4:** view-kinds are addressed by a **single `view.set(cell, kind)` tool**, NOT one tool per viewer (§0.4.2).
  Field-providers / result-renderers are internal, never tools.
- **DEC-5:** `ai: false` **omits** a contribution from `tools/list` (not merely marks it); mutating/destructive
  tools are **filtered out of `tools/list` for viewers** in addition to invoke-time re-auth (defense in depth,
  mirrors control_mcp's per-user permission filter on `list_capabilities`).
- **DEC-6:** the LLM-metadata fields (`description`/`when`/`examples`/`doc`/`safety`/`ai`) are **P5 registry
  fields**, authored once, consumed by both the human form and this generator. P9 does not add a parallel
  metadata store.
- **DEC-7:** `when`/`examples` fold into the tool **description** text (no separate MCP field exists for routing
  hints); safety → MCP tool **annotations** (`readOnlyHint`/`destructiveHint`).

## Risks / unknowns
- **R1 (highest):** the entire AI surface rests on a host chat+MCP substrate this app doesn't have. If DEC-1 lands
  as a full port it's weeks; if the SDK Tier-1 `mcp` registry slips, P9 has nothing to sit on. **This is the
  critical unknown — P9 is cheap only if the substrate is provided.**
- **R2:** artifact-ref → tool-param projection (ITEM-4) needs the catalog query to enumerate compatible-subtype
  artifacts at `tools/list` time. Enum lists can be large (a study with many embeddings); may need a "pass an
  artifact id of type X, list via `catalog.query`" indirection instead of a materialized enum for big studies.
- **R3:** selection-as-recipe evaluated backend-side must reference the **same** canonical `system_cell_id` axis
  the client's live selection uses, or AI-set and human-set selections diverge (§0.4.1). Depends on P8/P1 axis
  contract being shared, not per-surface.
- **R4:** availability gating (ITEM-11) at `tools/list` time can produce a *stale* tool set if the study's
  artifacts change mid-conversation; need a `tools/list_changed` notification or a re-attach on sync. MCP supports
  `notifications/tools/list_changed` — wire it, or the AI plans against a stale graph.
- **R5:** approval UX for a *chained* AI plan (predicate-select auto-approved, then assign gated) — the human must
  approve the mutating step without re-approving the read step; confirm the ported approval flow supports
  per-tool-call granularity (txresbench's does, via `tool_use_approvals`).
- **R6:** desktop single-user still has a "viewer" role only via study sharing; on a solo desktop the study owner
  is always editor+, so viewer-gating is exercised only in the shared/server case — test needs a second user.
- **R7:** the `analysis`-tool dispatch is asynchronous (a sandboxed job, possibly minutes); the MCP `tools/call`
  must return a job handle + stream progress, not block. Reuse txresbench's async-tool + `structuredContent` +
  `get_tool_result` pattern (tool_result_mcp) so long analyses don't hang the LLM loop.

## Effort estimate
- **Stratum S (ITEM-1/2):** LARGE, **not owned by P9** — flagged as the blocking platform prerequisite. If a
  port: ~2-4 weeks; if SDK Tier-1 promotion: comparable, shared cost.
- **Stratum G (ITEM-3…14), the actual P9 deliverable, assuming S provided:** MEDIUM. The generator core
  (ITEM-3/4/5/8) ~3-4 d (it's control_mcp's pattern re-sourced, mostly pure + unit-tested); fixed tools +
  resources (6/7) ~3 d (mostly wiring to P8/P1); gating (9/11) ~2 d; per-study server + handler + lifecycle (10)
  ~2-3 d; chat-extension + provenance/sync (12/13) ~2 d; end-to-end acceptance (14) ~1-2 d. **~2-2.5 weeks of
  P9-net-new** on top of the substrate. Convergence gate = ITEM-14 green (the §0.4.1 two-tool worked example runs
  read-run-auto-approved → mutating-gated → provenance run node → sync to a live viewer).
