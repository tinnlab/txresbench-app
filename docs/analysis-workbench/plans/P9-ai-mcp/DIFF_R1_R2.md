# P9 AI/MCP — r1 vs r2 convergence diff

## Substantively new in r2 (not in r1)
- **A frontend deliverable** (r2 ITEM-15): a `src-app/ui/src/modules/workbench-ai/` chat/AI panel as a `ViewContribution` in a P6 dock, with streaming assistant output, a **tool-approval UI** (approve/deny pending calls, show tool + args + safety badge), and a provenance link — plus a matching E2E test. r1 is backend-only and itemizes no frontend surface.
- **Factor a generic shared `ToolGenerator` projection** so ziee-control-mcp's OpenAPI generator and the workbench registry generator share the projection code (r2 ITEM-4 / D3), possibly a `ziee-mcp-generator` sibling. r1 says the generator "IS control_mcp's pattern" but proposes copying the shape, not extracting shared code.
- **`ziee-ai-providers` as its own SDK substrate crate** and a **minimal in-app `modules/chat`** as explicit items with a decision (r2 ITEM-2 / D2: minimal chat, skip projects/loop/title/export). r1 folds the chat loop + `llm_provider` into the ITEM-1 substrate blob without the minimal-chat scoping decision.

## Substantively new in r1 (not in r2)
- **One MCP server PER study** (deterministic UUID keyed on study_id) as the chosen decision (r1 DEC-3), with lifecycle tied to `on_study_deleted` cascade. r2 chooses the **opposite** (D4: one server row, study passed as tool *context*, per-study rows only as a revisit alternative). A real, consequential, contradicting decision on server tenancy.
- **`notifications/tools/list_changed` wiring** for stale-tool-set mid-conversation (r1 Risk R4). r2 does not raise the stale-availability-notification problem.
- **Async analysis tool-call must return a job handle + stream progress** (reuse `get_tool_result`/`structuredContent`) so long jobs don't hang the LLM loop (r1 Risk R7). r2 dispatches analyses to JobRunner but does not flag the async-return/streaming requirement.

## Shared substance
Both plans converge on the same architecture: the host chat+MCP+tool-approval substrate is **absent** from CytoAnalyst (only app/dataset/jobs/rootfs/sandbox/study/sync/user exist), the SDK's `ziee-control-mcp` already names the missing "Tier-1 `mcp` registry (v1.5)", so P9 splits into a **blocking substrate dependency** (port ziee `mcp`/`chat`/`ai-providers` vs promote to SDK Tier-1 — both recommend SDK promotion with an app-port fallback) and the **real deliverable: a generator that is `control_mcp` re-sourced from the P5 contribution registry instead of the OpenAPI spec**. Both project each AI-exposed contribution (analysis/command/selection-action) into an MCP tool (name=id, description+when+examples, params JSON-schema with `accepts` artifact-refs rewritten to typed params, safety→annotations), add fixed host tools (`selection.setByPredicate` via the P8 evaluator, `selection.current`, `view.set`, catalog/data-schema helpers), project resources (typed-artifact catalog/planner graph, current selection, data schema, P8 DSL vocabulary), pass LLM metadata through with `ai:false` omitting a contribution and views/renderers/field-providers internal, enforce two-level authz (study role outer + `gate:` perm inner, viewer sees only read-run, filter forbidden tools out of `tools/list` + re-auth at dispatch), a per-study-scoped built-in MCP server on a loopback JSON-RPC route dispatching to the real capability path (JobRunner/command/evaluator) carrying the caller's JWT, chat-extension auto-attach (`auto_attach_builtin_ids`+`is_builtin_server_id`) with the untrusted-content guard, provenance run-node + study-scoped sync on every AI call (human+AI co-drive one state, selection=recipe+hash), and the §0.4.1 "gene ABC > median → label XYZ" two-tool (read-run auto-approved select + gated mutating assign) end-to-end acceptance as the convergence gate. Same dominant risk (the substrate gap makes P9 mostly substrate-build), same P5-backend-readability risk, same study-scope-leak mitigation.
