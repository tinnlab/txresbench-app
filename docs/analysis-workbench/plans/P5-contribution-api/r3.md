# P5 — Contribution API (`@txresbench/workbench-api`) — r3

Blind/independent round. Grounded in PLATFORM_ARCHITECTURE §0.4/§1–§4/§5.5/§7/§8.5, DATA_MODEL, BUILD_PLAN
(Phase 1 + 5a), and real code: the interface-round `analysisRegistry` (`modules/analysis/{registry,types}.ts`),
live3 `viz-core` (`switch(cell.kind)` in `grid/CellView.tsx`, `conformance/invariants.ts`), the txresbench
study-extension seam (`STUDY_EXTENSIONS` linkme slice + `on_study_deleted`; FE `study/core/extensions/*`), the
`import.meta.glob('./*/plugin.tsx')` discovery, txresbench `@txresbench/framework` `createModule`, `store-kit`
(`defineStore`/`defineExtensionStore`), and `modules/control_mcp` (catalog/tools/policy). Scope: **desktop +
single-box server only** — build the local arm behind the open seams.

**P5 is the CONTRACT layer.** It sits *above* the impls (P1 data, P2 datatypes, P3 compute, P8 selection/DSL,
P10 study) and is *consumed* by P6 (shell renders from registries), P9 (MCP generated from registries), P11
(three modules built against it). P5 owns the *public surface + registries + manifest + provisioner contracts +
loader*; it does **not** own the data/compute/datatype/selection implementations — it facades them.

## Items

- **ITEM-1**: Generic `Registry<T>` primitive — generalize the existing `analysisRegistry` (`register`/`get`/
  `all` stable-id-sorted/`byCategory`/`availability(produced)`/`standardRecipe`) into a reusable
  `class Registry<C extends Contribution>` with `register` (idempotent-by-id, HMR-safe), `all`, `get`,
  `byArea`/`byCategory`, `order` sort, and a pure `availability(c, availableTypes)` that delegates type-matching
  to P2's subtyping lattice. The interface-round class is the literal template.
- **ITEM-2**: The **eight contribution registries** as singletons on the public surface — `analyses`,
  `plotTypes` (== P7 view-kind registry; P5 exposes the *contribution point*, P7 implements it), `fieldProviders`,
  `views`, `commands`, `selectionActions`, `resultRenderers`, `collections` — matching `Contributions` (§1).
- **ITEM-3**: Cross-cutting `Contribution` base type — `id` (namespaced), `extensionId`, `apiVersion`, `when?`,
  `requires?`/`accepts?` (typed artifact-ref selectors, subtyping-aware per DATA_MODEL), `order?`, `category?`,
  `title`, `icon?`, plus **LLM-facing declaration fields** (`description`, `when`(NL hint), `examples`, `safety:
  read-run|mutating|destructive`, `ai?:boolean`) — the *same* strings power the human form help AND the MCP tool
  (§0.4.2); P9 consumes them, P5 only declares them.
- **ITEM-4**: `AnalysisContribution<P>` — generalize the interface-round `AnalysisPlugin`: `category`,
  `accepts: TypeSelector[]` / `produces: ResultKind[]` (typed refs, replacing the closed `Kind` enum with P2
  datatype ids), `params: JsonSchema`, `defaults`, `run: RunSpec` (sandbox script | in-host builtin fn),
  `schedule?: {class, resources}` (§4.1.1; class only, single pool for now), `methodsText(p)`,
  `inStandardRecipe?`/`recipeOrder?`. The current `SimpleForm/AdvancedForm/ResultView/buildResult` React fields
  are **dropped** (host renders from `params` JSON-schema per §4.3; ResultView → resultRenderers registry).
- **ITEM-5**: The other contribution types — `ViewContribution` (`area:left|right|bottom`, `render: ViewSpec |
  {component} | {iframe}`, `when`), `CommandContribution`, `SelectionActionContribution` (`command` ref +
  `when:"has-selection"`), `FieldProviderContribution` (left-rail color/select-by sources),
  `ResultRendererContribution` (result-kind → panel), `PlotType/ViewKindContribution` (thin delegate to P7's
  `registerViewKind`), `CollectionContribution` (§5.5-C: `schema`, `scope`, `indexes`, `gate`).
- **ITEM-6**: `WorkbenchAPI` runtime interface (§2) — `version` string + `registry: Contributions` + the API
  facades (below), constructed **per-extension, capability-scoped** by study role (P10) + inner `gate:`
  permission. This is the *only* object an extension touches.
- **ITEM-7**: `data` API facade (§2/§5) — `catalog()`, `embedding(id)`, `obs(col)`, `geneColumn(gene,layer)`,
  `clustering(id)`, `deTable(id,page)`, `writeAnnotation(...)`, `writeResult(kind, artifact)`. **Delegates to
  P1/P2** (typed-binary reads over the authed byte-range endpoint; writes → catalog row). P5 defines the
  interface + type shapes; P1/P2 implement. Study/selection-scoped.
- **ITEM-8**: `selection` API facade (§0.4.1/§4.4) — `current()`, `onChange(cb)`, `set(s)`, `useCurrent()`
  (React), `setByPredicate(pred)`, plus `brush`/`pick`. **Ownership split (see Decisions):** P5 owns the
  **`CellSetPredicate` AST types + DSL-operator registry contract** (public, part of `@txresbench/workbench-api`);
  **P8 owns the evaluator + the selection/brush/pick runtime** behind this facade.
- **ITEM-9**: `compute` API facade (§4.1) — `run(spec: RunSpec, inputs, params): Promise<JobHandle>` with
  streamed progress. **Delegates to P3** (`ComputeBackend`/`JobRunner`→bwrap, single pool + interactive/batch
  priority). P5 defines `RunSpec`/`JobHandle` types; P3 implements.
- **ITEM-10**: `commands` (`register(id,handler)`/`execute(id,...args)`) + `ui` (`notify`/`openView`/
  `progress<T>`) facades — commands registry is the tool list P9 projects; `ui` delegates to P6 shell services.
- **ITEM-11**: Per-extension `storage: KeyValue` (namespaced by `extension_id`+scope-key) + `events: EventBus`
  facade (on txresbench's existing EventBus) — scoped so one extension can't read another's KV.
- **ITEM-12**: **Manifest schema** — the `extension.yaml` JSON-schema (§3): `id`, `name`, `publisher`,
  `version`, `apiVersion` (semver range), `activation[]` (lazy events), `contributes:{analyses, plotTypes,
  views, selectionActions, fieldProviders, resultRenderers, commands, collections, settings, jobs, resultKinds,
  sidecar}`. **This schema is itself a versioned published contract.** JSON-schema'd + validated at load.
- **ITEM-13**: Manifest parser/validator — parse (YAML or JSON), validate against ITEM-12 schema, **check
  `apiVersion` semver range against `WorkbenchAPI.version` (refuse incompatible)**, and **index contributions
  WITHOUT executing extension code** (contributions appear in UI gated by `requires`/`when` from the manifest
  alone; code activates lazily on `activation` events).
- **ITEM-14**: **FE extension host** (`ui/src/core/workbench/`) — instantiates the registries, builds the
  per-extension `WorkbenchAPI` object, wires capability scoping, and does **build-time discovery of built-in
  extensions via `import.meta.glob`** (mirrors `analyses/index.ts`; each built-in registers as a side-effect
  import). No external loader yet (seam only).
- **ITEM-15**: **BE extension-host kernel module** (`server/src/modules/extensions/`) — mirrors the
  `STUDY_EXTENSIONS` `linkme` distributed-slice + trait pattern: scans staged manifests, validates
  `apiVersion`, dispatches the declarative provisioners (ITEM-16..19), and fans an **`on_study_deleted` /
  uninstall cascade** over all provisioned data (collections + catalog rows + artifacts) via the shared study
  delete chokepoint (P10). The kernel is byte-identical regardless of how many extensions exist (§8.5).
- **ITEM-16**: Declarative provisioner — **collections** (§5.5-C): `schema→` a **generic runtime store**
  (`ext_records(extension_id, collection, scope_key, doc JSONB, …)` + GIN indexes on declared paths, OR
  table-per-collection by host DDL) + generated typed **CRUD REST** + a **bounded query DSL** (filter/sort/
  paginate, **never raw SQL**) + JSON-schema write-validation + a sync entity + a `gate:` permission. **No sqlx
  compile-time macros** (runtime-provisioned) — the hard boundary.
- **ITEM-17**: Declarative provisioner — **settings** (§6.5-A): `schema→` an admin settings card + a gated
  `GET/PUT` endpoint + a sync entity, using the app's existing settings + sync machinery. No server code.
- **ITEM-18**: Declarative provisioner — **jobs**: a declared `{cron|trigger, run:{kind:sandbox,...}}` → the
  host scheduler runs it in the sandbox (via P3). No server code.
- **ITEM-19**: Declarative provisioner — **result-kinds**: declare a new artifact kind (`{id, layout}`) → the
  host catalogs it + typed-binary-streams it. Coordinates with P1/P2 (the kind becomes a datatype entry /
  storage-layout binding).
- **ITEM-20**: **Publish P7's conformance battery** (`viz-core/conformance/invariants.ts`) through
  `@txresbench/workbench-api` so third-party view-kinds are validated by the *same* gate the built-ins pass (§4.2
  reconciliation TODO). Re-export, not re-implement.
- **ITEM-21**: **Dogfood** — rebuild the built-in analyses (the interface-round `analyses/<name>/plugin.tsx`)
  against the public API ONLY (Phase 1b "if our own analyses only use the public API, an outsider can build
  anything we can"). Coordinated with P11 (the three real modules) — P5 proves the surface, P11 ships it.
- **ITEM-22**: **Package + namespace setup** — create `@txresbench/workbench-api` as a workspace package on the
  `@txresbench/*` SDK (`@txresbench/framework`+`@txresbench/shell`); enforce an **acyclic** package graph (workbench-api is the
  leaf public surface that *re-exports types* from P2/P7, never imports their runtimes); wire npm workspaces +
  syncpack; define the semver versioning policy for the published API.
- **ITEM-23 (deferred, seam only)**: External manifest loader (from a per-deployment extensions dir / the
  `tinnlab/hub`) + the sidecar gateway (`/api/ext/<id>/*`, bio_mcp model). **Not built now** (BUILD_PLAN Phase
  5b/6); the manifest contract (ITEM-12) is authored forward-compatible so this drops in without changing it.

## Decisions
- **`@txresbench/*` namespace, on the `@txresbench/*` SDK** (resolves §10 open Q). `@txresbench/workbench-api` is the single
  public import surface for extensions; internal `@txresbench/*` packages (`@txresbench/viz`=P7, `@txresbench/datatypes`=P2,
  `@txresbench/kit`=design system) provide runtimes, and workbench-api **re-exports their public TYPES only** (keeps
  the package graph acyclic — workbench-api is the leaf). Extensions import **`@txresbench/workbench-api` and nothing
  else**. (Not `@txresbench/…`: this is app #2's workbench, built ON the txresbench SDK, not part of it.)
- **Datatype registry lives in P2, consumed by P5** (resolves the P2/P5 dispute). P2 owns the `Datatype`
  registry impl + subtyping lattice + storage layouts + viewers-per-datatype. P5's contribution surface
  *references datatype ids* and re-exports the P2 *types* (`Datatype`, `TypeSelector`, `accepts`/`produces`) so
  extensions declare against them. P5 does not implement the lattice; `Registry.availability` calls P2's
  subtype check.
- **Cell-set predicate DSL — ownership SPLIT** (resolves the P5/P8 dispute). The **`CellSetPredicate` AST +
  the DSL-operator registry contract** are part of the **public `@txresbench/workbench-api`** (P5): they're a
  declared contribution point (extensions add operators/`metadata-column` features per §0.4.2), `selection.
  setByPredicate` takes this type, and the AI reads the operator vocabulary as a resource. The **evaluator**
  (in-process TS + optional Rust) and the **selection/brush/pick runtime** are **P8**. Rationale: the DSL is a
  *contract* (many drivers: AI, cell-set widget, lasso, provenance) → belongs in the versioned API; its
  *execution* is a selection-subsystem concern → P8. Physically, the AST types live in
  `libs/workbench-api/dsl/predicate.ts` and P8 imports them (not vice-versa) to keep the graph acyclic.
- **Contribution registries generalized from the existing `analysisRegistry`** (not designed top-down) — the
  interface-round class is the proven shape (BUILD_PLAN "extract the framework from features").
- **Collections runtime store = generic `ext_records` JSONB (+ GIN)**, NO sqlx compile-time macros (§5.5-C hard
  boundary; matches the txr sqlx-macro constraint). Query = a bounded DSL, never raw SQL → no injection.
- **Manifest = YAML (napari-style), JSON also accepted; JSON-schema validated; indexed-not-executed; lazy
  activation.** `apiVersion` = semver range; host refuses out-of-range extensions.
- **Params form engine = JSON-schema→form (RJSF-style)** (resolves §10). React `ParamsForm` is the Tier-4
  escape hatch only.
- **Declarative view flavor = parameterize-a-P7-view-kind, NOT Vega-Lite** (§4.2 correction: viz is deck.gl-only,
  no SVG). New view-kinds = code, conformance-gated (ITEM-20).
- **Built-in discovery now (glob + linkme); external dir/hub loader deferred** (ITEM-23) — seam kept.
- **Provisioners are data-driven kernel code, not per-extension Rust** — one `modules/extensions/` kernel module
  provisions from the manifest; extensions add zero Rust (§8.5). Must respect desktop-embedded-server gating
  (config flag + CORE_MODULE_BLOCKLIST).

## Risks
- **Type-surface churn**: extracting the API before P1/P2/P3/P8 impls stabilize risks rework — mitigate with
  interfaces + local stubs and dogfooding (ITEM-21) as the early forcing function.
- **sqlx compile-time vs runtime collection store** (BUILD_PLAN's flagged "trickiest DB detail") — the generic
  `ext_records` store bypasses `query!`; needs careful scope/permission enforcement + additive-only migration
  discipline.
- **DSL ownership split** (P5 types / P8 evaluator) requires the AST to live in one place (workbench-api) or it
  duplicates + drifts — enforce the import direction (P8→P5, never reverse).
- **The manifest schema is a published contract** — every field is a forward-compat commitment; version it and
  keep ITEM-23's external path in mind now.
- **Package-graph cycles** — workbench-api must re-export *types* from P2/P7, never their runtimes, or the graph
  cycles (P6 renders from registries, P7 registers into `plotTypes`, P2 supplies datatypes). Guard with a
  dependency-cruiser/lint check.
- **Desktop parity** — collections/settings/jobs provisioners must work with the desktop-embedded server (both
  sides: config flag + blocklist per the desktop-embeds-server rule).
- **Over-building the framework before features exist** (BUILD_PLAN ⚠️ re-sequencing) — keep P5 to what the
  three real modules (P11) actually need; defer external extensibility.

## Effort
**Large.** Rough split: type surface + package + registries (ITEM-1..6, 22) ≈ S–M (the `analysisRegistry` is a
head start); API facades (ITEM-7..11) ≈ M but mostly thin over P1/P2/P3/P8; manifest + FE host (ITEM-12..14) ≈
M; **BE extension-host kernel + 4 provisioners (ITEM-15..19) ≈ L** (the generic runtime store + generated
CRUD/settings/jobs/result-kinds is the bulk, and the sqlx-boundary is delicate); battery-publish + dogfood
(ITEM-20, 21) ≈ S–M. External loader/sidecar (ITEM-23) deferred. Critical dep to unblock first: **P1/P2
data-foundation + datatype registry** (the types the entire contribution surface references).
