# P5 — contribution-api (`@cyto/workbench-api`) · r2

Scope: extract the versioned contribution-API package — the contribution registries, the
data/selection/compute/commands host APIs, the manifest + validator, the declarative provisioners
(collections/settings/jobs/result-kinds — no per-extension Rust), the extension discovery/loader seam, the
registry→MCP projection — and **dogfood** it by rebuilding the built-ins on it. Deployment scope: **desktop +
single-box server only** (seams open, only the local arm implemented). Grounded in: the interface-round
`analysisRegistry` (`src-app/ui/src/modules/analysis/{registry,types}.ts`), live3's viz `switch(cell.kind)` +
conformance battery, live8's study substrate, and the `@ziee/framework` SDK (store-kit / module-system / events)
+ ziee host `control_mcp` catalog/policy.

## Items

- **ITEM-1**: Scaffold the `@cyto/workbench-api` workspace package. New dir `sdk/packages/workbench-api/`
  (auto-included by the root `workspaces: ["sdk/packages/*", ...]` glob), `package.json` name
  `@cyto/workbench-api`, `exports` subpaths (`.`, `./registry`, `./data`, `./selection`, `./compute`,
  `./manifest`, `./conformance`, `./mcp`), tsconfig. Wire consumers: add `@cyto/workbench-api` + `/*` to
  `src-app/ui/tsconfig.json` paths and the vite alias (mirror the `@ziee/framework` wiring), add the dep +
  syncpack entry. Export `WORKBENCH_API_VERSION = "1.0.0"` + `isApiVersionCompatible(range)` (semver gate an
  extension's declared `apiVersion` against the host — refuse on exclusion).

- **ITEM-2**: The registry substrate. A standalone `workbenchRegistry` singleton holding **parallel typed Maps**
  (the `ChatExtensionRegistry` model, cleaner than declaration-merging for a package export), one per
  contribution point: `analyses · plotTypes · fieldProviders · resultRenderers · views · commands ·
  selectionActions · collections`. Each Map keyed by `id`, HMR-idempotent (last-wins + `console.warn`, per
  `ProjectExtensionRegistry`), with pure selectors (`all()`/`get()`/`byCategory()`/`ordered()`). A `Contribution`
  base carries the cross-cutting fields (`id`, `extensionId`, `apiVersion`, `when?`, `order?`, `category?`,
  `title`, `icon?`, `ai?`, `safety?`). Gating (`permission`/`when`) is a **render-time** concern the host
  filters on (per `RenderedSlotEntry`), never inside the registry.

- **ITEM-3**: The 8 contribution descriptor types (generalize `AnalysisPlugin` → typed contributions):
  `AnalysisContribution` (JsonSchema `params` + `defaults` + typed `accepts`/`produces` + `run: RunSpec` +
  `methodsText` + `inStandardRecipe`/`recipeOrder` + `ai`/`safety`); `PlotTypeContribution` (== a view-kind:
  `dataContract` + deck.gl `render` + `conformance` — bridges live3, ITEM-15); `FieldProviderContribution`
  (left-rail color/select-by source); `ResultRendererContribution` (result-kind → bottom panel);
  `ViewContribution` (`area: 'left'|'right'|'bottom'|'center'` + `render: ViewSpec | {component} | {iframe}` +
  `when`); `CommandContribution` (`handler` + args + `safety`); `SelectionActionContribution`
  (`when:'has-selection'` + `command`); `CollectionContribution` (`schema`/`scope`/`indexes`/`gate`). Retires
  the closed `Kind` union → typed datatype refs (ITEM-4).

- **ITEM-4**: Open datatype registry + subtype lattice (DATA_MODEL correction of the closed `DataKind` enum).
  `Datatype { id, extends?, schema, storage, viewers, capabilities? }`; `isSubtypeOf(a,b)` over the `extends`
  chain; typed `accepts`/`produces` selectors (`subtypesOf`-aware). The **availability / type-match engine**
  (generalizes `analysisRegistry.availability` from `Set<Kind>` to a lattice match over the study's artifact
  catalog) — computes which analyses light up given the artifact graph, and drives artifact-ref pickers +
  fieldProviders + viewer dispatch. Seed 2–3 types (`single-cell/anndata extends matrix extends tabular`,
  `embedding`, `clustering`) with the seam open; bulk/spatial/variant/structure are later entries.

- **ITEM-5**: `data` API — the typed data contract client. `catalog()`, typed-array reads
  (`embedding`/`obs`/`geneColumn` sparse fast-path/`clustering`/`deTable`), `artifacts.query({type})` for
  pickers, `writeAnnotation`/`writeResult(kind, ref) → analysis_id`. Binds to the Phase-0 kernel endpoints
  (authed study-scoped byte+Range serving + Tier-2 chunked slicing, DATA_MODEL); client-side decode
  (zarrita/DuckDB-WASM) is the extension's, the host is a dumb range server. Single-box = local-FS range server
  (same code path a future MinIO/worker uses).

- **ITEM-6**: `selection` API + the **cell-set predicate DSL** (§0.4.1, a first-class platform primitive).
  `CellSet` bitmask over the canonical cell axis; `current()`/`onChange()`/`set()`/`setByPredicate()`. The
  bounded, typed DSL (gene/obs/QC values + reductions median/mean/quantile/MAD + comparisons + boolean/set ops)
  + an **in-process evaluator** → bitmask (reads columns via ITEM-5). **Selection-as-recipe**: store the
  predicate + pinned input hash (never a materialized cell list) so it's reproducible + provenance-ready. One
  representation shared by the AI (`setByPredicate`), the `cell-set-selector` widget, and a lasso.

- **ITEM-7**: `compute` API — `run(spec: RunSpec, inputs, params) → JobHandle` (progress via SSE). The
  `ComputeBackend` seam with **only the local bwrap arm implemented** (scope); wraps the Phase-0
  jobs+sandbox path. The content-addressed-code + path-agnostic `inputs.json` contract stays (so a run is a
  provenance node by construction) even with one backend. Infers priority from trigger (interactive vs batch);
  single-box = one pool + interactive priority.

- **ITEM-8**: `commands` / `ui` / `storage` / `events` host services. `commands.register/execute` (the command
  registry doubles as palette + the MCP tool list, ITEM-14); `ui.notify/openView/progress`; per-extension
  scoped `storage` KeyValue; `events` EventBus bridged to the framework EventBus (`on/watch` auto-cleanup) +
  `sync:<entity>` refetch. All are thin wrappers over `@ziee/framework` store-kit/events.

- **ITEM-9**: The manifest + validator. Publish the JSON-schema for `extension.yaml` (`contributes` set +
  `apiVersion` range + `activation` events) as part of the API contract. A **load-time validator**: parse
  YAML/JSON → schema-validate → semver compat gate (ITEM-1) → index contributions **without executing extension
  code** (contributions appear gated-by-`when`/`requires` from the manifest alone; code activates lazily).
  Manifest TS types shared with the loader (ITEM-13).

- **ITEM-10**: Collections provisioner (Layer-C, §5.5-C) — the generic runtime store. Kernel Rust in
  `server/src/modules/extensions/`: a shared `ext_records(extension_id, collection, scope_key, doc JSONB,
  created_at, ...)` table (+ GIN indexes on manifest-declared JSON paths) OR table-per-collection DDL from the
  schema; JSON-schema write validation; a **bounded query DSL** (filter/sort/paginate — *not* raw SQL); scope
  namespacing (study/user/global); generated typed CRUD REST + a sync entity + a permission gate. **The sqlx
  boundary** (flag): runtime-provisioned tables **cannot** use `query!` compile-time macros — reach them through
  a generic parameterized layer validated by the JSON-schema + scope filter (no injection surface). Client:
  `api.store.collection(id).query({...})`, never SQL.

- **ITEM-11**: settings / jobs / result-kinds provisioners (Tier-A declarative backend, §6.5-A) — all generic
  host mechanisms reading the manifest, zero per-extension Rust. `settings` (schema → admin card + gated
  GET/PUT + sync entity); `jobs` (cron → the kernel scheduler, runs in the sandbox; single-box one-pool);
  `resultKinds` (register a new artifact kind → catalog row + typed-binary stream). These reuse the app's
  existing migration/jobs/settings/sync machinery generically.

- **ITEM-12**: Lifecycle cascade + teardown. Provisioned collections + host-written catalog rows + artifacts are
  cascade-cleaned via the study `on_study_deleted` / `on_study_duplicated` hooks through the shared
  `delete_study_with_extensions` chokepoint (live8 substrate) — a study delete atomically removes every
  provisioned layer; duplicate deep-copies them. Extension uninstall drops its collections/settings/jobs.
  Collection schema bumps = **additive-only** auto-migration; destructive needs a declared step.

- **ITEM-13**: Extension host — discovery + loader. **Build-time glob** of built-in extensions (FE
  `import.meta.glob('./**/module.tsx', {eager:true})` per `loader.ts`; staged compute assets for the sandbox),
  topo-sorted by declared `dependencies` (the loader's cycle-detecting DFS). The **external manifest loader is
  the SEAM**: parse a per-deployment extensions dir/package → validate (ITEM-9) → register → stage compute —
  scaffolded + tested with a fixture, but built-ins are the near-term target (Phase-1 rule: no external loader
  yet).

- **ITEM-14**: Registry → MCP projection (§0.4; `control_mcp` catalog/policy model). A **pure generator** that
  walks `workbenchRegistry` and emits the AI surface: `analyses → MCP tools` (input schema = the params
  JsonSchema; `accepts` → typed artifact-ref params), `commands`/`selectionActions → tools`,
  `catalog`/`data`/`selection` → resources. Per-contribution `ai:false` opt-out + a `safety` hint
  (`read-run`|`mutating`|`destructive`) → MCP tool annotations + the approval flow (read/run auto-approved,
  mutating/destructive gated). A pure, unit-tested `isAiExposed(contribution)` / denylist gate (mirrors
  `control_mcp` `is_denied`/`is_mutating`/`has_secret_field`). **Seam boundary (flag)**: P5 owns the
  generator + safety-mapping (the registry is the SoT); the per-study MCP *server* wiring + JWT boundary belongs
  to the kernel/MCP part — P5 exposes the projection it consumes.

- **ITEM-15**: Publish the conformance battery + open the view-kind registry. Move live3's
  `viz-core/conformance/{invariants.ts, viewKindBattery}` into `@cyto/workbench-api/conformance` as the
  **acceptance gate** for a `plotTypes` contribution. Do the **bounded refactor** the BUILD_PLAN re-sequencing
  flags: replace live3's closed `switch(cell.kind)` + `CellKind` union + `CELL_KIND_OPTIONS` + `KIND` drift-triple
  → an open `registerViewKind({ id, dense, dataContract, render, conformance })` registry that the center-canvas
  dispatches through; registration runs the battery so a non-conforming third-party kind is auto-rejected.

- **ITEM-16**: Dogfood — rebuild the built-ins on the public API ONLY (the VS Code dogfood rule; the real proof
  the API is sufficient). Replace `analysisRegistry.register(AnalysisPlugin)` in the 8 interface-round plugins
  with `workbenchRegistry.analyses.register(AnalysisContribution)`; move the mock `buildResult` behind the real
  `compute.run` seam; consume `data`/`selection` for color-by + type-match gating; register the built-in plots
  as view-kinds (ITEM-15). Delete the ad-hoc `modules/analysis/{registry.ts, types.ts Kind-union}` superseded by
  ITEM-2/3/4. Any built-in that needs a shell internal = an API gap to close before Phase 1 is done.

## Reuse

- **Registry pattern**: `ProjectExtensionRegistry` (`modules/projects/core/extensions/registry.tsx`) — cleanest
  Map-keyed-by-id, HMR-idempotent, order-sorted, render-time-gated template; `ChatExtensionRegistry` for the
  parallel-Maps-per-surface shape; `analysisRegistry`/`studyExtensionRegistry` as the direct seeds.
- **Discovery**: `modules/loader.ts` `import.meta.glob('./**/module.tsx')` + topo-sort by `dependencies` (reuse
  verbatim; note: glob needs a **relative literal**, not `@/`).
- **Store/events**: `@ziee/framework` `store-kit` `defineStore`/`init(ctx){on,watch,onCleanup}` +
  EventBus `sync:<entity>` (the `McpUserPolicy.store.ts` shape) for reactive registry-driven state + refetch.
- **MCP projection**: ziee host `control_mcp/{catalog.rs, policy.rs}` — `Operation` (operation_id / required_permission
  / mutating / has_secret_field) + pure `is_denied`/`is_mutating` gate = the exact model for the
  contribution→tool projection with safety hints.
- **Compute/data**: Phase-0 kernel `jobs`+`sandbox` (`run_analysis`+`ExtraMount`) + the working-store/catalog
  data endpoints. Study substrate (live8): scoping, `EffectivePermission` (owner/editor/viewer), sync,
  `delete_study_with_extensions` cascade. Viz (live3): view-kinds, `ChartFrame`/`chartLayers`, `Coordination`
  store, conformance battery.
- **Provisioners** reuse the app's existing per-module migration / jobs / settings / sync machinery generically.

## Decisions

- **Package namespace/location**: ship as `@cyto/workbench-api` physically at `sdk/packages/workbench-api`
  (reuses the existing `sdk/packages/*` workspace glob) — app-specific name now, with a documented promotion
  path to `@ziee/*` if other ziee apps host workbenches (arch §10). *Recommend `@cyto/` now.*
- **Registry shape**: a standalone `workbenchRegistry` singleton with parallel typed Maps (package-export
  friendly) over the module-system `Slots` declaration-merging seam (which is app-internal, not exportable).
- **Params contract**: JSON-schema → host-rendered form (RJSF-style), artifact-ref fields → auto-populated
  type-filtered pickers (§4.3 Tier 1/2), host-shared widgets for compound inputs (Tier 3), React code-form as
  the escape hatch (Tier 4). **One `params` declaration serves the human form AND the MCP tool input schema.**
- **`accepts`/`produces` typed with subtyping** (open datatype registry), replacing the closed `Kind`/`DataKind`
  enums. Availability = subtype match over the artifact catalog.
- **Compute scope**: `ComputeBackend` trait present, **only local bwrap** implemented; content-addressed +
  path-agnostic `inputs.json` contract kept regardless (provenance-by-construction).
- **Collections DB discipline**: generic runtime store (`ext_records` JSONB + declared GIN indexes) reached via a
  parameterized query DSL — **never `query!` macros** (runtime-provisioned). Additive-only migrations by default.
- **MCP boundary**: P5 owns the registry→tool/resource *projection* + safety mapping; the MCP *server* +
  JWT/approval wiring is the kernel/MCP part's — coordinate the interface.
- **Manifest format**: YAML (napari precedent) with a JSON-schema; the schema is part of the published contract.

## Risks

- **Foundation gate**: data/compute/provisioner implementations are blocked on Phase-0; if P5 is scheduled before
  it, land the pure items first and stub the wire (mitigation: the pure/impl split in Sequencing).
- **Dogfood exposes API gaps late** (ITEM-16) — expected and *desired* (it's the proof), but budget iteration:
  a built-in needing a shell internal means an API change rippling back through 2–8.
- **live3 view-kind refactor**: the closed `switch`+`union`+`CELL_KIND_OPTIONS`+`KIND` drift-triple is
  battery-enforced in lockstep; opening it to a registry must preserve (or replace) that drift guard or
  third-party kinds silently mis-dispatch.
- **sqlx compile-time vs runtime store** (ITEM-10) is the trickiest DB detail (BUILD_PLAN honest-risk) — the
  generic parameterized layer must stay injection-safe under the bounded DSL.
- **Selection DSL scope creep**: keep it bounded (no arbitrary code); heavy computed features reify as
  artifact-producing analyses the predicate references, not DSL operators (§0.4.1).
- **Registry-as-SoT coupling**: three surfaces (UI/MCP/API) project from one registry — a descriptor field
  change touches all three; hold the descriptor types stable behind the semver'd `apiVersion`.

## Effort

- Pure API core (ITEM-1/2/3/4/6-DSL/8/9): **M** (mostly TS, generalizes existing registries; well-templated).
- Data/compute clients (ITEM-5/7): **M**, gated on Phase-0 (thin once endpoints exist).
- Provisioners + lifecycle (ITEM-10/11/12, Rust kernel): **L** (runtime store + query DSL + cascade is the
  heaviest, most novel backend).
- Loader + MCP projection (ITEM-13/14): **M** (glob is trivial; external seam + projection are bounded).
- Conformance publish + view-kind refactor (ITEM-15): **M** (bounded but battery-lockstep-sensitive).
- Dogfood (ITEM-16): **M**, plus a variable convergence tail as gaps surface.
- **Total: L** — the platform's central abstraction; sequence pure-core → provisioners → dogfood, don't big-bang.
