# P5 — contribution-api + extension host (Round 1, blind)

Scope: **desktop + single-box**. Build the `@txresbench/workbench-api` package (contribution registries + the
data/selection/compute/commands/ui API surface types), the extension **manifest** format + JSON-schema
validator, the **declarative form renderer** (Tier 1–3 of §4.3) + artifact-ref pickers, built-in
**discovery/loader** (build-time glob), a backend **extension-host module** running the **settings** +
**result-kind** provisioners. Collections (runtime store) + jobs provisioner are later items; external/
marketplace loader DEFERRED.

Grounding (verified in code, worktree `/data/pbya/txresbench/tmp/analysis-workflow-wt`):
- FE analysis registry to generalize: `src-app/ui/src/modules/analysis/registry.ts` (`analysisRegistry`,
  `AnalysisRegistry.availability/byCategory/standardRecipe`), descriptor `…/analysis/types.ts`
  (`AnalysisPlugin<P>`: `id/name/category/requires:Kind[]/produces:Kind/params-as-React-forms/defaults/
  buildResult/methodsText`), form primitives `…/analysis/analyses/shared.tsx`
  (`Field/RangeField/SelectField/NumberField/SwitchField` on `@txresbench/kit`).
- FE contribution seam to generalize: `src-app/ui/src/modules/study/core/extensions/`
  (`registry.tsx` name-keyed `StudyExtensionRegistry` + `collect(order)`; `types.ts` `STUDY_SLOTS` +
  `StudyExtensionRegistration{name,slots}`; `slots.tsx`; `index.ts` `import.meta.glob` auto-discovery).
- BE contribution seam to generalize: `src-app/server/src/modules/study/core/extension/registry.rs`
  (`linkme` `#[distributed_slice] STUDY_EXTENSIONS`, `StudyExtension` trait w/ `register_routes/
  on_study_deleted/on_study_duplicated/collect_summary/initialize`, `OnceCell` singleton), driver

## Items

### A. The `@txresbench/workbench-api` package (types + registries — the versioned surface)

- **ITEM-1 — Package scaffold `sdk/packages/workbench-api` (`@txresbench/workbench-api`).** New workspace member
  (glob already covers `sdk/packages/*`). `package.json` (peerDeps: react, `@txresbench/kit`, `@txresbench/framework`),

- **ITEM-2 — Contribution-point types.** Port + generalize `analysis/types.ts` into
  `src/contributions/types.ts`: the cross-cutting `ContributionBase` (`id`, `extensionId`, `apiVersion`,

  `ResultRendererContribution` / `ViewContribution` / `CommandContribution` / `SelectionActionContribution` /
  `CollectionContribution`. `AnalysisContribution<P>` generalizes `AnalysisPlugin<P>`: replace the
  hand-coded `SimpleForm/AdvancedForm` React components with a **`params: JsonSchema`** + `defaults` + an
  optional Tier-4 `ParamsForm?` escape-hatch component; keep `requires/produces/inStandardRecipe/recipeOrder/
  methodsText`; add `accepts: ArtifactRefSpec[]` (artifact-ref inputs, §4.3 Tier 2), `run: RunSpec`,
  `safety: 'read-run'|'mutating'|'destructive'`, `ai?: boolean` (LLM metadata for P9).
- **ITEM-3 — Generic `Registry<T>` + the `Contributions` object.** `src/contributions/registry.ts`:
  generalize `AnalysisRegistry` into a reusable `Registry<T extends ContributionBase>`

  `Contributions` interface (`analyses/plotTypes/fieldProviders/resultRenderers/views/commands/

- **ITEM-4 — The `WorkbenchAPI` runtime surface types.** `src/api/types.ts`: the §2 interface —

- **ITEM-5 — `WhenClause` + `DataKind`/`ResultKind` type re-export seam.** `src/data/kinds.ts`:

### E. Backend extension-host module + declarative provisioners

- **ITEM-14 — `extensions` compiled host module.** `server/src/modules/extensions/{mod,manifest,
  provisioners,permissions,routes}.rs` — one generic `AppModule` in `MODULE_ENTRIES` (§8.5 "one generic
  module"). At `init`: load indexed manifests, run the provisioners. **The kernel module that changes for no
  extension.** Also registers a `StudyExtension` (generalizing the study seam) so extension study-scoped data
  gets `on_study_deleted`/`on_study_duplicated` cascade for free (§0.5, §5.5 teardown).
- **ITEM-15 — Settings provisioner (generic runtime store).** From a manifest `settings:[{id,schema,scope,
  gate}]` → provision **without per-extension Rust/migration/central edit**. Because the kernel's canonical
  rule is **sqlx compile-time macros** (can't `query!` a runtime table) AND `SyncEntity` is a **closed enum**,
  use: ONE host-owned generic table `ext_settings(extension_id, setting_id, scope_key, doc JSONB, updated_at)`
  reached via **runtime `sqlx::query`** (not `query!`) — the §5.5.C-sanctioned exception to the compile-time
  rule (extension tables are runtime-provisioned). The extension-host module ships the table by **dropping
  `server/src/modules/extensions/migrations/*.sql`** — `build.rs`'s `compose_merged_migrations_from` already
  globs every module's `migrations/` dir, so no central migration list edit. Generic `GET/PUT
  /api/ext/{extId}/settings/{id}` gated by the manifest `gate:` permission, JSON-schema-validated on write;
  **one new generic `SyncEntity::ExtSettings` variant** (the single closed-enum edit + its snake_case string
  test, serving all extension settings, keyed by id in the payload) emitted via `publish(ExtSettings, Update,
  id, Audience::…, origin)`. FE: a generic **admin card auto-rendered from the settings JSON-schema** via
  `SchemaForm` (ITEM-8), registered into `settingsAdminPages` (`scope=admin`) or `settingsUserPages`
  (`scope=user`) — mirror `sandbox/module.tsx`'s `SettingsPageSlot` — with a `defineStore` gated on
  `hasPermissionNow(gate)` + `on('sync:ext_settings', reload)` (mirror `SandboxSettings.store.ts`).
- **ITEM-16 — Result-kind provisioner.** From `resultKinds:[{id,layout}]` → register the kind into the
  **P2 datatype registry** (`DataKind`/`ResultKind` + storage layout) + a default `ResultRendererContribution`
  so the host renders a standard result panel, + wire catalog `writeResult(kind,…)` typing. Depends on
  **P1 catalog + P2 registry** — confirmed both are **design-only today** (`docs/DATA_STORAGE_REDESIGN.md`
  specifies the fixed kind vocab `expression|embedding|clustering|annotation|de|enrichment|trajectory|
  metadata-column` + the Postgres catalog + `GET /studies/{s}/catalog`; NO `analysis_results` table / result
  registry exists in code). Thin here (a call into P2's registry + a renderer default) — but fully blocked on
  P1/P2 landing.
- **ITEM-17 — Jobs provisioner (LATER — needs net-new periodic-scheduling infra).** From `jobs:[{id,cron,
  run}]` → a scheduled sandbox job. **Grounding correction:** the `jobs` module is a **FCFS enqueue-run-once
  work queue** — NO cron / `schedule_at` / `next_run` / periodic infra exists, `job_type` is free-text with
  **no job-type registry**, and there is a **single injected `JobRunner`** (no per-type dispatch table). So a
  cron/periodic jobs provisioner requires: (a) net-new periodic-scheduling (a cron table + a tick loop that
  enqueues), (b) a `job_type → RunSpec` dispatch registry the provisioner registers into, on top of P3's
  `runner::JobRunner`→`sandbox::run_analysis`. Firmly deferred within P5 (after P3); larger than the other
  provisioners.
- **ITEM-18 — Collections provisioner (LATER / DEFERRED-runtime-store).** From `collections:[{id,schema,
  scope,indexes,gate}]` → a generic `ext_records(extension_id, collection, scope_key, doc JSONB)` + GIN
  indexes + generic CRUD + a bounded query DSL (filter/sort/paginate, **no raw SQL**), `api.store.collection()`
  surface (§5.5.C). Per the task, **build later** (none of the 3 target modules need Layer C).

## Decisions

- **Package namespace: `@txresbench/workbench-api` under `sdk/packages/`** (not `@txresbench/…`), matching the SDK
  dogfooding convention; resolves doc §10. Single-cell terms (`DataKind`) enter as a P2-owned registry, not
  hard-baked, keeping the package hostable by other txresbench apps.
- **Settings/collections runtime store, NOT sqlx macros.** The kernel's compile-time `query!` discipline
  can't touch a runtime-provisioned table, so extension settings/collections use a **generic JSONB store
  reached via runtime `sqlx::query`** + JSON-schema validation + a bounded query DSL (exactly §5.5.C). No
  per-extension migration or Rust.
- **`SyncEntity` closed-enum ⇒ ONE generic `ExtSettings` (+ later `ExtRecord`) variant**, keyed by id in the
  payload — the single closed-enum edit that serves all extension settings/collections without a variant per
  extension.
- **Form engine = JSON-schema → form (RJSF-style) on `@txresbench/kit`**, reusing `shared.tsx` (doc §10
  recommendation). Artifact-ref fields are a first-class schema `type`, unified with `accepts` gating.
- **Manifest format = YAML with a JSON-schema** (napari model; the schema is published API). JSON also
  accepted by the loader.
- **Built-ins only this round**: build-time `import.meta.glob` (FE) + build-helper staging (BE). No runtime
  external-dir / hub loader (§7 deferred).
- **Compute is always a sandboxed script; the form is declarative-first with a Tier-4 code escape hatch** —
  P5 owns the form/manifest/registry; the sandbox run itself is P3.
- **Collections + jobs provisioners deferred within P5** (settings + result-kind first; none of the 3 target
  modules need Layer C).
- **Permission gating for manifest `gate:` strings = a generic runtime check, NOT a compile-time unit
  struct.** The kernel's permission system is compile-time-typed (a unit struct impl'ing `PermissionCheck`
  with `NAME/PERMISSION/DESCRIPTION/MODULE` consts, whose `*_docs` `with_permission::<(P,)>` is *load-bearing*
  — it's how the OpenAPI→TS emitter generates the FE `Permissions.X` constants). An extension-declared `gate:`
  is a runtime string, so the generic ext endpoints check it via a **runtime permission resolver** against the
  user's grants, and the extension-host module registers extension permission descriptors so admins can grant
  them. (Built-ins may also declare a compile-time permission the ordinary way.) Flag the OpenAPI-emitter
  interaction — generic ext routes won't auto-produce typed FE `Permissions.X`; the FE reads the gate string.
- **Unify onto ONE FE contribution mechanism.** Today two coexist: the module-system `Slots`
  declaration-merge map (`@txresbench/framework/module-system`) and the bespoke name-keyed registries
  (`studyExtensionRegistry`/`analysisRegistry`). `@txresbench/workbench-api`'s `contributions` generalizes the
  **registry** flavor (richer: `when`/`requires`/`availability` selectors the flat `Slots` map lacks); host
  settings/nav slots keep using the framework `Slots` map. Document the boundary so the two don't fork further.

## Risks/unknowns

- **P1/P2 not built yet** — the `data.*` impl, catalog, and `DataKind`/subtyping the artifact-ref pickers +
  result-kind provisioner need don't exist. Mitigation: P5 ships the **types + a desktop stub** and a local
  `Kind`-union fallback; pickers/renderers wire to real impls when P1/P2 land. P5's type surface must not
  block on them.
- **Closed `SyncEntity` + compile-time sqlx** force the generic-JSONB-store design; a future need for a
  per-extension typed sync entity would require re-touching the enum. Accept for built-ins; document the seam.
- **`@txresbench/workbench-api` vs `@txresbench/framework` boundary** — risk of duplicating the module/slot/EventBus
  surface. Decision: workbench-api **depends on** `@txresbench/framework` (reuses EventBus/Slots), adds only the
  workbench contribution registries + data/selection/compute API. Keep the split clean.
- **RJSF-style renderer scope creep** — conditional/dependent fields (`nCluster_{embeddingId}`,
  method-dependent) can balloon. Mitigation: declarative covers `when`/`if-then`/`repeat-per`/templated
  defaults; anything past that is Tier-4 code-form (explicit boundary, per §4.3).
- **Legacy `analysisRegistry` coexistence** — the shell + gallery + e2e read the old registry today; the
  flip is a transitional adapter (ITEM-19) to avoid a big-bang break; full removal is P6/P11.
- **`plotTypes` overlaps P7** — P5 defines the *contribution point*; P7 supplies the deck.gl view-kind
  registry + conformance battery behind it. Boundary: P5 = the interface, P7 = the impl. Coordinate the
  `PlotTypeContribution`/`view-kind` type so they don't diverge.
- **build.rs staging** — a fresh worktree missing staged extension assets could panic (cf. hub-seed
  worktree gotcha in memory); fail-soft to zero-extension like pgvector.
- **No periodic/cron infra exists** — the jobs module is FCFS-enqueue-once with a free-text `job_type`, no
  job-type registry, single `JobRunner`. The `jobs:` manifest provisioner (ITEM-17) is therefore net-new
  scheduling infra, not a thin wrapper — kept deferred; don't under-scope it.
- **Compile-time vs runtime permission surface** — generic ext endpoints can't mint typed FE `Permissions.X`
  the way the OpenAPI emitter does for kernel routes; the FE must consume the runtime `gate:` string. Small
  friction, isolated to the generic ext route family; document it so no one expects auto-generated constants.
