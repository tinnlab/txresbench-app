# P10 — Study Substrate (tenancy · access · sharing · transfer · lifecycle-cascade · sync) — r2

**Role.** P10 is the *platform-scoping wrapper*. It does not invent tenancy/authz/sync — live8 already built
that (`feat/study-management` + `feat/study-admin` + `feat/study-extensions`). P10 (a) **consolidates and lands
those three branches on main**, and (b) **extends** the substrate with the small set of reusable seams the
platform data layers consume so every artifact (P1 catalog), job (P3), provenance node (P4), Layer-C collection,
and per-study MCP server (P9) inherits study tenancy, owner/editor/viewer access, collaborator sync, and
delete/duplicate/transfer lifecycle **for free**. The study is the container the whole workbench is scoped by.

Scope: **desktop (single-user) + single-box server (multi-user, 1-box admin) ONLY.** Sharing/transfer are live
on 1-box; gated off on desktop.

## Grounding (actual code read on the live8 branches)
- **Access model — `EffectivePermission { Owner, Editor, Viewer }`** (`study/models.rs`): `can_edit()` =
  Owner|Editor, `is_owner()` = Owner, `from_share_level("editor"|"viewer")`. Resolver
  `StudyRepository::effective_permission(study_id, user_id) -> Option<EffectivePermission>` (`repository.rs:70`)
  — owner short-circuits, else looks up `study_shares` where `status='accepted'`; `None` = invisible.
- **DEC-3 authz shape:** ONE RBAC verb `studies::use` gates all study CRUD; the *per-study ACL*
  (ownership + shares) governs edit/delete — NOT a second RBAC verb. `study::settings::manage` (Administrators
  via `*`) gates the deployment transfer toggle. Admin cross-user management lives on `feat/study-admin`
  (`study::admin::*`).
- **Gating is inline, NOT reusable:** every handler re-calls `effective_permission(...)` then `.can_edit()` /
  `.is_owner()` (`handlers.rs:147/180/248/308/353/436/532`). **No axum extractor exists** — this is the primary
  gap P10 fills for the platform.
- **Registry (`feat/study-extensions`):** `STUDY_EXTENSIONS` `linkme` distributed slice + `StudyExtension` trait
  (`study/core/extension/registry.rs`) with default-noop hooks `on_study_deleted(study_id, &mut tx)`,
  `on_study_duplicated(src, dst, &mut tx)`, `collect_summary`, `register_routes`, `initialize`;
  `auto_register_study_extensions(pool)` sorts by `order`; process-wide `OnceCell`. Delete chokepoint
  `delete_study_with_extensions(pool, study_id)` (`study/lifecycle.rs`) fires `fire_on_study_deleted` in the SAME
  tx as the row delete (atomic). Duplicate fires `fire_on_study_duplicated` **inline in the `duplicate_study`
  handler** (`handlers.rs:216`) — NOT via a shared lifecycle chokepoint. `DatasetStudyExtension` (order 40) is
  the reference consumer (`dataset/study_extension/extension.rs`) — owns a route, deletes/deep-copies rows,
  contributes a `"N datasets"` summary tag.
- **Sync:** entities `Study | StudyShare | StudyTransfer | StudySettings` (`sync/event.rs`). Study-change events
  fan to owner + `accepted_recipient_ids(study_id)` (`repository.rs:~430`) — the "collaborator audience",
  computed manually per emit site. `StudyDto` projects `effective_permission: String` + `dataset_count`.
- **study_datasets** = the per-study catalog precursor (SDK-adopted real upload; join `sd.study_id`). P1's
  `analysis_results` catalog is study-scoped the identical way.

## Items

- **ITEM-1**: **Consolidate the three study branches → main.** Reconcile the layering
  `feat/study-management` (base: studies/shares/transfers/settings/datasets/grants migrations
  `202607160001..07`) → `feat/study-admin` (cross-user `study::admin::*` twin: change-owner/share/revoke/
  delete/reassign + bulk) → `feat/study-extensions` (`STUDY_EXTENSIONS` registry + `DatasetStudyExtension`).
  Produce ONE merged `modules/study/*` on main. **Adopt wholesale**; the only edits are conflict resolution +
  ensuring the admin-delete path routes through `delete_study_with_extensions` (the shared chokepoint the
  admin twin's delete must call — already noted in `lifecycle.rs`).
- **ITEM-2**: **Reusable `StudyScope` axum extractor** (`study/scope.rs`, new) — resolves the acting user's
  `effective_permission` on a path `study_id` **once**, yields `StudyScope { study_id, user_id, perm }`, and
  exposes `require_role(min: EffectivePermission) -> Result<(), AppError>` (403 on insufficient, 404 on `None`
  so a foreign study is invisible). This is the SINGLE study-authz chokepoint the platform endpoints
  (P1 data API, P3 jobs, P4 provenance, P9 MCP) use instead of re-implementing `effective_permission + can_edit`.
  Include the **admin override**: root-admin / `study::admin::*` holders resolve to `Owner`-equivalent so the
  admin twin works uniformly through the same guard. Refactor the existing study handlers onto it (reduces the
  7 inline re-fetch sites; behavior-preserving).
- **ITEM-3**: **Study-scope FK + gate contract for the data layers.** Define (as an enforced convention +
  compile-time-checked FKs) that every platform table holding extension data —
  P1 `analysis_results`/artifacts/working-store index, P3 `jobs`, P4 provenance run-nodes/edges/`code_blobs`,
  Layer-C collections, P9 per-study MCP registration — carries `study_id UUID NOT NULL REFERENCES studies(id)`
  and is reached **only** through `StudyScope`. P10 OWNS the contract + a doc/test asserting the FK exists; the
  owning parts (P1/P3/P4/P9) add the column (cross-part dependency). **Data layers are study-scoped, never
  owner-scoped** (Decision D3) — so ownership transfer is a single `owner_id` update, no data cascade.
- **ITEM-4**: **Platform data-layer STUDY_EXTENSIONS registrations (delete cascade).** Each platform data layer
  registers a `#[distributed_slice(STUDY_EXTENSIONS)]` entry (mirroring `DatasetStudyExtension`) implementing
  `on_study_deleted` — delete its study-scoped rows AND the physical working-store blobs/provenance artifacts
  the DB `ON DELETE CASCADE` won't reach. P10 provides the pattern + the *catalog/artifact* extension
  (the working-store cleanup is inherently platform, not a feature module); P3/P4 provide their job/provenance
  impls (dependency). All fire atomically via the existing `delete_study_with_extensions`.
- **ITEM-5**: **`on_study_duplicated` deep-copy for the data layers + a `duplicate_study_with_extensions`
  chokepoint.** Add the symmetric lifecycle chokepoint (`study/lifecycle.rs`) so duplicate fires over one tx
  the same way delete does (harden the current inline-in-handler firing). The catalog/artifact extension's
  `on_study_duplicated` re-links content-addressed working-store blobs into the destination study (dedup: blobs
  are content-addressed → copy = new catalog rows pointing at the SAME blobs, not byte copies) and deep-copies
  provenance edges. P4's provenance extension copies its graph nodes.
- **ITEM-6**: **Reusable study-collaborator sync audience** (`study/scope.rs`): `study_audience(pool, study_id)
  -> Audience` = owner ∪ `accepted_recipient_ids`. Extension result-writes (P1 catalog-row Create, P4
  provenance-node Create) emit study-scoped sync through this ONE helper so every collaborator's shared
  workbench refreshes live — replacing the manual owner+recipients fan. Add sync entities as needed for the new
  data layers (owned by P1/P4; P10 provides the audience they publish to).
- **ITEM-7**: **Two-level authz for the extension data API** (the read/write derivation §0.5). The workbench data
  API (P1) composes: **outer** = `StudyScope.require_role` (write path ⇒ `can_edit()` / Editor+; read path ⇒
  any access / Viewer+), **inner** = the per-capability `gate:` permission the contribution declares. A **viewer**
  gets the whole workbench + all extension results **read-only** (every write/Run endpoint 403s). P10 supplies
  the outer gate helper (`require_can_edit(&StudyScope)`); P1/P5 compose it with the inner permission.
- **ITEM-8**: **Per-study MCP role gate (P9 boundary).** P9's per-study MCP JWT boundary resolves the caller's
  `effective_permission` on the study via `StudyScope`: read/recall tools require Viewer+, mutating/destructive
  tools require Editor+ (matching the chat approval-bypass rule for read-analyses). P10 exposes the check;
  P9 consumes it. The per-study MCP *registration row* is a data layer under the ITEM-3 contract (cascades on
  delete via ITEM-4).
- **ITEM-9**: **Frontend study-scope context.** `study/context/StudyScopeProvider.tsx` +
  `useStudyPermission(): 'owner'|'editor'|'viewer'` (reads `StudyDto.effective_permission` from
  `Studies.store`/`StudyDetail.store`) + `useCanEdit()`. The workbench shell (P6) consumes `useCanEdit()` to
  hide Run/write/assign affordances for viewers (the read-only handoff surface = share-as-viewer, no new
  feature). Wire platform summary tags (analysis/artifact counts) into the existing `card_tags` slot via each
  data layer's `collect_summary`.
- **ITEM-10**: **Desktop single-user degradation.** On the embedded desktop server, share/transfer routes +
  UI are gated off both sides (config flag + `CORE_MODULE_BLOCKLIST`, per the desktop-embeds-server rule); the
  study still scopes all data (one implicit owner). Extend the existing `study/desktop-gating.spec.ts` to the
  new platform data layers (studies + catalog + provenance exist on desktop; only sharing/transfer hide).
- **ITEM-11**: **Selection/recipe + result writes are study-scoped, provenance-linked.** Confirm the
  selection-as-recipe rows (P8) and every result write carry `study_id` and emit via ITEM-6, so a shared
  collaborator sees a co-worker's clustering/DE appear live. (Contract assertion + a cross-device e2e.)
- **ITEM-12**: **Tests.** Unit: `EffectivePermission` gate matrix, `StudyScope` resolves owner/editor/viewer/
  none(→404)/admin-override, `study_audience` membership. Integration: delete cascades all registered platform
  layers (catalog+provenance+jobs rows + blobs gone), duplicate deep-copies (blob re-link, not byte copy),
  transfer moves `owner_id` with data intact (no owner-scoped orphan), viewer write→403, editor write→200,
  cross-user study→404, per-study MCP viewer-vs-editor tool gate. E2E: share-as-viewer→read-only workbench,
  transfer accept→ownership moves + collaborator sync, desktop share/transfer hidden.

## Decisions
- **D1 — Adopt, don't rebuild.** live8's substrate is the answer; P10 wraps, never reimplements authz/sharing.
- **D2 — One `StudyScope` chokepoint for all platform endpoints.** Replace the 7 inline `effective_permission`
  re-fetches; every P1/P3/P4/P9 endpoint gates through the extractor. (Fixes the reusability gap.)
- **D3 — Data layers are study-scoped, never owner-scoped.** Every catalog/artifact/job/provenance/collection
  row FKs `study_id`, not `owner_id`. ⇒ transfer = single `owner_id` update, delete/duplicate cascade via
  `study_id`, and access derives purely from `EffectivePermission`. No `on_study_transferred` hook needed.
- **D4 — Two-level authz.** Outer = study role (owner/editor/viewer) via StudyScope; inner = per-capability
  `gate:` permission. Viewer = full read-only workbench. Keep DEC-3: `studies::use` is the RBAC verb; per-study
  ACL is the resource-level authz (no per-analysis RBAC verb explosion).
- **D5 — Content-addressed duplicate = re-link, not byte-copy.** `on_study_duplicated` copies catalog rows
  pointing at the SAME content-addressed blobs (P1 object store dedups); only DB rows/edges are cloned.
- **D6 — Study audience = owner ∪ accepted shares**, one helper; all extension result-writes publish through it.
- **D7 — Desktop hides sharing/transfer only.** Studies + all data layers exist on desktop (single implicit
  owner); share/transfer routes+UI gated off — the study scoping code path is identical, just single-tenant.

## Risks
- **Three-branch reconciliation (ITEM-1).** `feat/study-management`, `feat/study-admin` (on the provenance
  worktree), `feat/study-extensions` overlap; wrong merge order loses the admin twin or the registry. Determine
  the correct base→admin→extensions order; the shared-delete-chokepoint note in `lifecycle.rs` is the invariant
  to preserve (admin-delete MUST call it). Mitigate: land base first, then admin, then extensions; run the
  merge-gate.
- **Owner-scoped leak (D3).** If any part adds an `owner_id` column to a data layer instead of `study_id`,
  transfer orphans it and viewers may see nothing / editors lose access. Mitigate: ITEM-3 contract test asserts
  the FK is `study_id` on every platform table.
- **Cascade completeness.** A data layer that forgets to register a `STUDY_EXTENSIONS` entry leaks blobs/rows
  on study delete (the DB cascade drops DB rows but not physical blobs). Mitigate: a coverage test enumerating
  registered extensions vs. the known data-layer set; the working-store cleanup is a platform extension (not
  optional per-feature).
- **Sync audience drift.** Publishing to owner-only instead of `study_audience` breaks the shared-workbench live
  update. Mitigate: single helper (D6) + a cross-device e2e (ITEM-11).
- **`StudyScope` admin-override correctness.** The admin bypass must NOT widen a normal user's access; keep the
  override strictly behind `study::admin::*` / root-admin. Unit-test the matrix (ITEM-12).
- **Duplicate over large studies.** Re-linking is cheap (D5), but provenance-edge copy can be large; keep it in
  the single tx (atomic) but watch tx size — acceptable at 1-box scale.

## Effort
**Medium.** The substrate is *built* — P10 is ~30% land/consolidate (ITEM-1), ~40% new reusable seams
(StudyScope guard + study_audience + duplicate chokepoint + FE context, all small and self-contained), ~30%
cross-part wiring (cascade registrations + FK contract + per-study MCP gate) that rides along with P1/P3/P4/P9.
The hard cross-cutting concerns (authz, sharing, transfer, sync, delete cascade) are already solved by live8;
P10's real work is exposing them as clean seams and enforcing the `study_id` contract everywhere. Critical
dependency: **ITEM-1 (land the three live8 study branches on main).**
