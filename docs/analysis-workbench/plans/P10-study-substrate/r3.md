# P10 — Study Substrate (r3, blind)

Tenancy · access (owner/editor/viewer) · sharing · transfer · lifecycle-cascade · sync — as the platform
scoping boundary wrapping the working store (P1), catalog (P2), compute (P3), provenance (P4). Grounded in
live8's already-merged study code + the Phase-0 foundation the new layers build.

**Grounding fact that reframes this part:** `feat/study-management`, `feat/study-admin`, and
`feat/study-extensions` are ALL already ancestors of `main` (verified via `git merge-base --is-ancestor`). The
substrate, the admin cross-user twin, and the `STUDY_EXTENSIONS` registry + `on_study_deleted`/`on_study_duplicated`
+ the shared `delete_study_with_extensions` chokepoint (`study/lifecycle.rs`) EXIST on main. `feat/provenance` is
the only P10-relevant branch NOT merged (design-done, paused). So P10 is **not** "build the substrate" — it is
"make the merged substrate correctly scope + cascade the NEW platform data (catalog rows + object-store blobs +
provenance nodes), and close the blob-GC gap the substrate's transactional hook cannot close."

## Items

- **ITEM-1** (baseline reconcile): Treat the merged substrate as the P10 baseline — `study/{repository,lifecycle,
  handlers,admin_handlers,core/extension/registry}.rs`, `EffectivePermission{Owner,Editor,Viewer}`,
  `effective_permission()`, `can_edit()`, `STUDY_EXTENSIONS` slice, the 3 sync entities (`Study`/`StudyShare`/
  `StudyTransfer`) + `StudySettings`. No re-build; P10 owns EXTENDING it. Write a short SUBSTRATE_BASELINE note
  pinning the merged commit + the exact seams the new layers plug into.
- **ITEM-2** (the blob-GC gap — the headline): the `on_study_deleted(study_id, &mut tx)` hook is **transaction-
  scoped, so it can only delete DB rows** — it CANNOT (and must not) delete object-store blobs inside the tx.
  Proven gap: the shipped dataset extension's `delete_datasets_for_study` does `DELETE FROM datasets` only,
  **orphaning the uploaded matrix blobs** in the P1 file store. P10 OWNS the cascade that triggers P1 blob GC via
  a **collect-then-post-commit-sweep** seam: extend the extension hook contract so `on_study_deleted` (and dataset
  delete/detach) records the to-GC blob refs, and `delete_study_with_extensions` returns a `GcManifest` that a
  **post-commit** step hands to P1's blob-store delete primitive. Atomicity preserved (DB rolls back on hook
  error); blob deletion happens only after commit succeeds.
- **ITEM-3** (refcounted GC — safety): P1 blobs are **content-addressed (dedup)** — one hash can back rows across
  datasets/catalog/studies. GC MUST refcount: delete a blob only when **no surviving row references its hash**
  (dataset rows, catalog `analysis_results` storage-refs, provenance code-blobs, Layer-C collections). P10 defines
  the reference-count query/view (`SELECT ... WHERE hash NOT IN (any live storage-ref)`) that the post-commit
  sweep and a periodic background reaper (mirrors txresbench's mcp tool-call prune loop) both consult. This is the
  single guard against both orphan-leak and dedup-delete-corruption.
- **ITEM-4** (register the Phase-0 catalog/working-store as a StudyExtension): the new `analysis_results` catalog
  + working-store artifacts (P1/P2) plug into the substrate via a `#[distributed_slice(STUDY_EXTENSIONS)]` entry
  (NOT a study-core edit). Its `on_study_deleted` deletes catalog rows + emits blob refs into the GcManifest
  (ITEM-2); its `on_study_duplicated` deep-copies catalog rows and **re-references** (not re-uploads) the
  content-addressed blobs (ITEM-6); its `collect_summary` contributes an `"N results / M GB"` study tag.
- **ITEM-5** (study-scope the data API — the outer authz boundary): every Phase-0 data-API surface (catalog read,
  typed-binary/Zarr byte-range serve, `writeResult`, `writeAnnotation`) is gated by `effective_permission()`:
  owner/editor may write/mutate (`can_edit()`), viewer is **read-only** (workbench + all extension results). This
  is the outer of the two-level authz (study role = outer; per-capability `gate:` = inner). Every catalog row and
  blob key carries `study_id`; a read resolves the caller's role first. Cross-study/foreign study → 404 (mirror
  the substrate's `get_by_id_and_user` owner-scope pattern).
- **ITEM-6** (duplicate/transfer cascade semantics for the new data): `on_study_duplicated` copies catalog rows +
  provenance nodes into the dst study, re-referencing CAS blobs by hash (bumps refcount, no byte copy) — matching
  the dataset extension's deep-copy-rows pattern. **Transfer** (`accept_transfer`) moves `owner_id`, so the new
  data must have NO independent owner column — it's reached THROUGH `study.owner_id`, so transfer is free (no
  per-artifact re-owner). Verify catalog/artifact rows key on `study_id`, never a denormalized `owner_id`.
- **ITEM-7** (study-scoped sync for result-writes): extension result-writes (a clustering/DE landing in the
  catalog) emit a study-scoped sync event to the study's collaborators (`accepted_recipient_ids` + owner) so a
  shared workbench updates live — notify-and-refetch, no row data. Add `AnalysisResult` (owner+share-audience)
  as a `SyncEntity`; the write path publishes it through the host, reusing the substrate's share-audience fan-out
  (the same one `StudyShare` uses). Client self-gates refetch on `studies::use` (the no-403-reconnect rule).
- **ITEM-8** (provenance-substrate reconciliation — the ONE unmerged branch): `feat/provenance` is design-done,
  unmerged. Its execution model (run nodes + input/output edges + content-addressed code blobs, §0.6/§B3) is
  Phase-0c; it must land ON the merged substrate. P10's obligation: provenance nodes/edges/code-blobs are
  `study_id`-scoped, register their own `on_study_deleted` (rows → tx; code-blobs → GcManifest via ITEM-2/3) +
  `on_study_duplicated`, and emit study-scoped sync. Sequence provenance's merge THROUGH the substrate's
  extension seam (a StudyExtension entry), not as a study-core edit. Selections stored as recipes (predicate +
  input hash) inherit study scope for free.
- **ITEM-9** (admin cross-user twin — extend, don't rebuild): the admin twin (`admin_handlers.rs`:
  change-owner/share-on-behalf/reassign/delete/bulk/list/user-search/detail, gated `study::admin::{read,manage}`)
  is already merged and admin-delete ALREADY routes through the shared `delete_study_with_extensions` chokepoint.
  P10 EXTENDS the admin surface: (a) `admin_get_detail` surfaces per-study **storage/artifact/catalog usage**
  (result count + blob GB, from ITEM-4's `collect_summary`) so an admin sees a study's footprint before delete;
  (b) confirm admin-delete's GcManifest post-commit sweep fires (ITEM-2) so an admin delete reclaims blobs, not
  just rows; (c) an admin "orphan-blob / storage" read view backed by the ITEM-3 refcount query (surface leaked
  blobs for a manual reap). No new admin CRUD verbs.
- **ITEM-10** (workbench scoping contract → P6): expose the study role to the workbench shell so its `canEdit`
  and the data-API read/write scoping DERIVE from `EffectivePermission` (viewer ⇒ read-only workbench = the
  "hand a PI/reviewer an interactive read-only result" JTBD, no new feature). Provide a small
  `GET /studies/{id}/access` (or fold role into the catalog bootstrap) returning `{role, can_edit}`. WORKBENCH_IA
  does not yet reference the role — this item closes that gap; it is P10's single hard dependency edge INTO P6.
- **ITEM-11** (branch-merge + gate sequencing): only `feat/provenance` needs to land for P10's substrate story to
  be complete (ITEM-8). Merge protocol per the repo skill: staging worktree + independent clean build + merge-gate
  + lifecycle-check `--all`. The catalog/working-store StudyExtension (ITEM-4) + blob-GC seam (ITEM-2/3) land WITH
  the Phase-0 foundation (P1/P2), not as a standalone study PR — P10 is a cross-cutting scoping layer, so its
  code ships inside the layers it wraps, keyed by the `STUDY_EXTENSIONS` seam.

## Decisions
- **DEC-1 (blob GC is collect-then-post-commit, refcounted):** the transactional hook CANNOT delete blobs; it
  collects refs → post-commit sweep → P1 delete only when refcount hits zero. Rejected: synchronous in-tx blob
  delete (non-atomic, corrupts on rollback) and fire-and-forget delete (dedup-unsafe).
- **DEC-2 (P10 owns the cascade, P1 owns the primitive):** `on_study_deleted` decides WHAT to GC; P1's blob store
  decides HOW to delete + refcount. Clean seam split; matches the "keep the seam, ship local" rule (local FS now,
  MinIO later — same delete/refcount API).
- **DEC-3 (new data reached THROUGH `study.owner_id`, never a denormalized owner):** makes transfer free and
  keeps the study the single tenancy unit. All catalog/artifact/provenance rows key on `study_id` only.
- **DEC-4 (viewer = read-only, derived not re-implemented):** the workbench `canEdit` and data-API write-scoping
  DERIVE from `EffectivePermission`; extensions never re-implement access control (§0.5).
- **DEC-5 (P10 code ships INSIDE the layers it wraps):** the catalog StudyExtension + GC seam land with P1/P2,
  not as a standalone study PR. Only `feat/provenance` is a discrete branch merge.
- **DEC-6 (generic EntityExtensionRegistry / SDK G8 deferred):** keep `STUDY_EXTENSIONS` study-specific for the
  three-module target; the generic entity-parameterized registry is a flagged SDK gap, not built here.

## Risks
- **Dedup-delete corruption (HIGH):** a naive per-study blob delete corrupts another study/dataset sharing the
  hash. Mitigation: ITEM-3 refcount is a hard gate; add an integration test that shares a blob across two studies,
  deletes one, asserts the blob survives (mirror study-admin's cascade test that verified survival via list).
- **Orphan leak (MEDIUM):** a post-commit sweep that crashes leaks blobs. Mitigation: the background reaper
  (ITEM-3) is the backstop — it re-derives orphans from the refcount query, so a missed sweep self-heals.
- **Provenance-merge drift (MEDIUM):** `feat/provenance` was authored before the merged substrate; its tables may
  assume the old shape. Mitigation: reconcile onto the merged `STUDY_EXTENSIONS` seam during ITEM-8, real
  merge-base diff (not tip-vs-main).
- **Shipped dataset orphan (LOW, but live):** the current `delete_datasets_for_study` already orphans blobs on
  every study delete. Mitigation: ITEM-2 retrofit closes it; until then it's a known storage leak.
- **Workbench role contract lag (LOW):** WORKBENCH_IA doesn't yet reference the study role; ITEM-10 must be
  agreed with P6 or the workbench ships without viewer read-only enforcement.
