# P10 — DIFF r1 vs r2

## Substantively new in r2 (not in r1)
- **ITEM-1: Consolidate the three live8 study branches onto main** (`feat/study-management` → `feat/study-admin` → `feat/study-extensions`), with an explicit merge base→admin→extensions ordering, conflict resolution, and the invariant that admin-delete must route through `delete_study_with_extensions`. r1 treats the substrate as an *already-MERGED dependency* ("live8 substrate MERGED … HARD prerequisite"); r2 makes landing/reconciling it P10's own ITEM-1 with a dedicated three-branch-reconciliation risk. A real scope-ownership difference.
- **`feat/study-admin` cross-user admin twin as an adopted input + `StudyScope` admin-override.** r2 integrates the admin twin (`study::admin::*`, `/settings/studies`, bulk ops) and requires root-admin / `study::admin::*` holders to resolve to Owner-equivalent through the same guard. r1 never mentions `feat/study-admin`, the admin twin, or an admin override in its access seam — its reuse list is management + extensions only.
- **`duplicate_study_with_extensions` chokepoint hardening (ITEM-5).** r2 adds a symmetric duplicate lifecycle chokepoint because live8 fires `fire_on_study_duplicated` *inline in the handler*, not via a shared chokepoint. r1 explicitly says the duplicate handler "already calls fire_on_study_duplicated … Nothing to change here."
- **Explicit `study_id` FK contract + coverage/enforcement test (ITEM-3, R "owner-scoped leak").** r2 makes "every platform table FKs `study_id NOT NULL REFERENCES studies(id)`, reached only through StudyScope" an owned, test-asserted contract across P1/P3/P4/P9, plus a cascade-coverage test enumerating registered extensions vs. the known data-layer set. r1 implies study-scoping but does not elevate the FK/coverage assertion to an owned deliverable.
- **P3 jobs treated as a first-class cascaded data layer** under the contract (alongside catalog/provenance). r1's cascade items cover workstore (Layer A+B) + collections (Layer C) but not P3 jobs.

## Substantively new in r1 (not in r2)
- **Content-addressed blob GC design as the headline risk (DEC-5 / R2 / R3).** r1 explicitly forbids in-tx blob unlink (a file delete can't roll back; a blob may be shared with a duplicated study), and mandates ref-counted mark-sweep GC scheduled outside the tx — calling it "the biggest unknown in the part." r2 says `on_study_deleted` simply "delete[s] the physical working-store blobs the DB cascade won't reach," without the ref-counting-across-duplicated-studies problem or an out-of-tx GC design.
- **Two distinct StudyExtension registrations with prescribed distinct `order` values (DEC-4).** r1 pins workstore `order:50` + collections `order:60` (vs dataset's `40`) for deterministic cascade firing. r2 describes a generic "each data layer registers one entry" pattern without the ordering prescription.
- **Explicit two-level authz precedence decision (DEC-3: capability-gate OUTER, study-role INNER) + double-403/404 confusion risk (R5).** r1 states and tests the ordering (capability 403 before study 404). r2 has two-level authz (D4) but frames the inner as a per-capability `gate:` without the same explicit precedence-ordering decision/risk.

## Shared substance
Both agents converge on the same spine: adopt live8's `EffectivePermission {Owner,Editor,Viewer}` + sharing + transfer + the `STUDY_EXTENSIONS`/`StudyExtension` registry + `delete_study_with_extensions` chokepoint verbatim (P10 never re-implements authz). Both build the single reusable study-authz chokepoint — an axum extractor/guard wrapping `effective_permission` that resolves once and replaces the ~7 inline `.can_edit()`/`.is_owner()` re-fetch sites, with the 404-on-foreign / 403-on-insufficient idiom. Both wire data-API two-level authz (reads=Viewer+, writes=`can_edit`/Editor+, viewer→full read-only workbench). Both register platform-data-layer STUDY_EXTENSIONS impls for delete cascade + `on_study_duplicated` deep-copy that RE-LINKS the same content-addressed blobs (copy index rows, not bytes). Both build one reusable `study_audience` = owner ∪ `accepted_recipient_ids` helper feeding study-scoped notify-and-refetch sync for collaborator live updates. Both add the FE `StudyScope`/`useStudyRole`/`useCanEdit` context derived from `StudyDto.effective_permission`, gating mutation affordances (the share-as-viewer read-only handoff = no new feature). Both hand P9 a per-study MCP role gate (Viewer=read, Editor+=mutating/destructive). Both treat transfer as an `owner_id`-flip only (data is study-scoped, no cascade) and both handle desktop single-owner by gating sharing/transfer off while keeping the scoping code path identical.
