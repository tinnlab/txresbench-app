# P10 — Study-substrate integration (r1, blind)

**Scope of THIS part:** how the analysis-workbench platform *uses* live8's study-management
(`feat/study-management` + `feat/study-extensions` + `feat/provenance`) as the
tenancy / access / lifecycle / realtime boundary. This is **integration wiring, NOT rebuilding
study-management** — the access model, sharing, transfer, the `StudyExtension` hook seam, the
delete chokepoint, and sync fan-out are all **already built** (see `## Reuse`). P10 = the four
seams that hook the platform's data layers into that substrate:
(a) `canEdit` + data-API read/write scoping derive from `EffectivePermission`;
(b) the read-only-viewer hand-off (PI/reviewer JTBD);
(c) the lifecycle cascade over all extension data layers (artifacts + catalog + collections) via
    `on_study_deleted` / `on_study_duplicated`;
(d) extension result-writes → study-scoped sync events.
Deployment scope: **desktop (single owner) + 1-box server (multi-user + sharing)**.

The generic `EntityExtensionRegistry` (SDK G8) generalization is a NOTE, not a build item.

## Items

- **ITEM-1 — Study-role resolution seam (`StudyAccess`) for every extension backend.**
  A thin shared guard/extractor wrapping the ALREADY-BUILT resolver
  `StudyRepository::effective_permission(study_id, user_id) -> Option<EffectivePermission>`
  (`study/repository.rs:70-96`, owner short-circuit + `study_shares` `status='accepted'` level).
  Generalizes the existing per-handler helper `resolve(repo, study_id, user_id) -> (Study,
  EffectivePermission)` (`study/handlers.rs:34-50`: 404 on `None`, then `perm.can_edit()` /
  `perm.is_owner()` checks) into a reusable platform guard. Returns the acting user's
  `Owner|Editor|Viewer` (or `None` → **404**, no-leak idiom). Every platform data-API / catalog /
  collection endpoint calls it before doing anything. Single chokepoint so no extension
  re-implements access control (PLATFORM_ARCHITECTURE §0.5).

- **ITEM-2 — Data-API read/write scoping from `EffectivePermission`.**
  Wire ITEM-1 into P1's data-API surface: **reads** (`catalog()`, `embedding()`, `obs()`,
  `geneColumn()`, `clustering()`, `deTable()`) require any resolved role (`Viewer+`); **writes**
  (`writeResult(kind,…)`, `writeAnnotation()`, catalog inserts, Layer-C collection mutations)
  require `EffectivePermission::can_edit()` (Owner/Editor). Viewer → **403** on any mutation. This
  is the server-authoritative half of "the workbench's data-API read/write scoping derives from
  the study role" (§0.5). The FE gate (ITEM-4) is UX-only; this 403 is the real boundary.

- **ITEM-3 — Two-level authz composition (study role × capability gate).**
  Every extension endpoint enforces BOTH layers (§0.5 "two-level authz: study role = outer;
  per-capability `gate:` permission = inner"): the app RBAC capability gate
  (`RequirePermissions<(P,)>`) establishes "is this user allowed the feature at all," THEN ITEM-1
  establishes "and do they reach this study, at what level." NOTE the study module itself uses a
  SINGLE `studies::use` verb for every endpoint (the per-study ACL is the edit/delete boundary —
  `permissions.rs` DEC-3); the platform's inner capability layer is therefore for an extension's
  OWN declared `gate:` (§5.5-C, e.g. `pathways::use`), not for study edit/delete. Provide a
  combined guard helper (capability-then-role) + document precedence (capability 403 before
  study 404).

- **ITEM-4 — Central workbench `canEdit` context (FE).**
  Replace the ad-hoc per-component derivation — today re-derived at ≥4 sites: `StudyCard.tsx:19-20`
  (`isOwner = effective_permission==='owner'`, `canEdit = isOwner || ==='editor'`),
  `StudyDetailPage.tsx:34-35`, `StudyFormDrawer.tsx:22` (`readOnly = ==='viewer'`), and
  `dataset/study-extension/components/DatasetsPanel.tsx:21-22` — with ONE
  `useStudyRole()` / `WorkbenchStudyContext` exposing `{ role, canEdit, isOwner, isViewer }`
  derived once from `StudyDto.effective_permission`. The workbench shell (P6) and EVERY extension
  contribution (run buttons, selection-actions, annotation Assign, delete) read `canEdit` from it,
  so a Viewer gets a fully-rendered but read-only workbench. Refactor the three existing study
  components onto the context.

- **ITEM-5 — Workstore `StudyExtension` impl (Layer A artifacts + Layer B catalog) — the
  delete/duplicate cascade.**
  Register a `#[distributed_slice(STUDY_EXTENSIONS)]` entry for P1's workstore/catalog module
  (mirroring the dataset first-consumer `dataset/study_extension/`):
  - `on_study_deleted(study_id, tx)` — delete the study's `analysis_results` catalog rows in-tx;
    schedule content-addressed artifact blobs for GC (DEC-5, NOT an in-tx file unlink).
  - `on_study_duplicated(src, dst, tx)` — deep-copy catalog rows into `dst`, **re-linking** the
    same immutable content-addressed blobs (copy the index, not the bytes — DEC-5).
  Fires automatically through the built chokepoints (`delete_study_with_extensions`,
  `duplicate_study` handler already calls `fire_on_study_duplicated`). This is §5.5's
  "uninstall/study-delete cascade" for Layers A+B.

- **ITEM-6 — Collections `StudyExtension` impl (Layer C) — the cascade over extension-owned
  relational data.**
  Register a second `StudyExtension` for P5's generic collections store (§5.5-C, the
  `ext_records`/table-per-collection store): `on_study_deleted` drops all `scope:study` collection
  rows for the study across ALL extensions (one generic impl, since collections are host-owned);
  `on_study_duplicated` copies them into `dst`. Covers pathway-sets / annotation-history /
  saved-gates without each extension writing a hook.

- **ITEM-7 — Study-collaborator audience resolver (reuse + expose).**
  Reuse the built `StudyRepository::accepted_recipient_ids(study_id)` + the
  `publish_study_to_all(action, study_id, owner_id, &recipients, origin)` fan-out
  (`study/handlers.rs:61`) as the platform's **study-scoped sync audience**. Expose a shared
  `study_audience(study_id) -> (owner_id, Vec<recipient_id>)` the platform result-write path calls
  once (owner + accepted editor/viewer shares) instead of each module re-querying.

- **ITEM-8 — Extension result-write → study-scoped sync.**
  When an extension produces a result (a catalog row via `writeResult`, P1), the host publishes a
  study-scoped, notify-and-refetch sync event to the ITEM-7 audience — new `SyncEntity` variant(s)
  (`AnalysisResult` / `Catalog`) added to `modules/sync`. So a shared workbench updates live when a
  collaborator (or the AI, §0.4) produces a clustering/DE. Add the FE store subscription
  (`sync:analysis_result`) that **self-gates** on study access (per the sync no-403 rule) and
  refetches the study catalog.

- **ITEM-9 — Study-role → MCP capability scoping (produces the mapping P9 consumes).**
  The per-study MCP server (P9) derives its allowed tool set from the acting user's
  `EffectivePermission` × each contribution's declared **safety hint** (`read-run | mutating |
  destructive`, §0.4.2): Viewer → `read-run` only (read catalog/data/selection, run nothing that
  mutates); Editor → + `mutating` (run analysis, assign annotation); Owner → + `destructive`
  (delete). P10 owns this `role → max-allowed-safety-tier` map + the filter fn; P9 wires it into
  tool generation + the approval flow.

- **ITEM-10 — Viewer read-only hand-off (the PI/reviewer JTBD — an acceptance path, not a new
  feature).**
  Sharing a study as `viewer` yields the interactive read-only workbench (§0.5 "sharing a study as
  viewer *is* the hand-a-reviewer-an-interactive-read-only-result JTBD"): all result
  renderers/viewers render, selection/brush/pick work for exploration, but every mutation
  affordance is disabled (ITEM-4) and every write endpoint 403s (ITEM-2) and no mutating MCP tool
  is exposed (ITEM-9). Wire the "open shared study → its workbench section" nav (reuse
  `StudyDetailPage` `/studies/:id/:section` + STUDY_SLOTS). Verification/wiring over ITEM-2/4/9.

- **ITEM-11 — Ownership-transfer re-scoping.**
  On `StudyTransfer` accept, the data layers do NOT move — only `study.owner_id` flips (artifacts +
  catalog + collections are already study-scoped, not owner-scoped). Verify the transfer path
  re-derives access for both parties: re-emit `SyncEntity::Study` + fan to old+new owner so their
  workbenches re-compute `canEdit` from the fresh `effective_permission`. Mostly verification over
  live8's built transfer accept/decline + `keep_old_as_editor`.

- **ITEM-12 — Desktop degeneracy (single-owner).**
  On desktop (`isDesktop` = `window.__TAURI__`), the acting user is always `Owner`; sharing/transfer
  surfaces are already platform-gated OFF by live8; `canEdit` is always true; the lifecycle cascade
  (ITEM-5/6) + result-writes (ITEM-8) still run with an empty recipient list (fan-to-self). Verify
  the platform INHERITS live8's gating (no re-implementation) and that empty-audience sync/GC don't
  panic.

## Decisions

- **DEC-1** — Reuse `effective_permission` as the SINGLE authz resolver; the platform NEVER
  re-implements owner/editor/viewer (it's the only resolver in the tree).
- **DEC-2** — Foreign-study access → **404** (no existence leak), matching study's owner-scoped
  404 idiom; capability-denied → **403**.
- **DEC-3** — Two-level order: **capability gate (RBAC) OUTER, study role INNER** — feature-level
  allow before resource-level access. (State + test the precedence.)
- **DEC-4** — Cascade ownership: ONE workstore `StudyExtension` covers Layer A (artifacts) + Layer
  B (catalog) since the host owns both; Layer C gets ONE generic collections impl. So the platform
  registers **2** study-extensions (plus dataset's existing one at `order: 40`) — pick distinct
  `order` values (e.g. workstore `50`, collections `60`) so cascade fires deterministically.
- **DEC-5** — Artifact handling under cascade (IMPORTANT): catalog rows are deleted/copied **in-tx**
  (rollback-safe); content-addressed **blobs** are NOT unlinked in-tx (a file delete can't roll
  back, and a blob may be shared with a duplicated study). Delete → schedule blobs for **ref-counted
  GC** (mark-sweep, outside the tx). Duplicate → **re-link** the same immutable blobs (copy the
  index rows, not the bytes) — cheap + correct because content-addressed.
- **DEC-6** — Sync granularity: ONE `AnalysisResult`/`Catalog` entity (notify-and-refetch the study
  catalog) over per-datatype entities — cheaper, matches the notify-only wire.
- **DEC-7** — `canEdit` is **derived, never persisted**; single source = the server's
  `StudyDto.effective_permission`. The FE gate is UX; the authoritative gate is ITEM-2's 403.
- **DEC-8** — MCP role→safety map: Viewer=`read-run`, Editor=+`mutating`, Owner=+`destructive`
  (reuses the existing safety-hint vocabulary, §0.4.2).

## Risks/unknowns

- **R1** — P1's data-API / `writeResult` / catalog-row shape isn't built yet; ITEM-2/5/8 assume it
  (blind-round). Reconcile when P1 r1 lands.
- **R2** — Content-addressed blob GC (DEC-5): ref-counting across studies (duplicate shares blobs)
  is non-trivial; a naive in-tx unlink would corrupt the source study. Needs a GC design
  (refcount or mark-sweep) — the biggest unknown in the part.
- **R3** — `on_study_duplicated` deep-copy of a large catalog in-tx could be slow; may need to copy
  rows in-tx but stage any real blob work as a background job. Unknown until artifact volume is.
- **R4** — New `SyncEntity` variants require **OpenAPI regen in BOTH binaries** (server + desktop) —
  the known regen-both-binaries gotcha.
- **R5** — Two-level authz can produce confusing double 403/404; needs explicit precedence (DEC-3)
  + tests for each combination (no-capability, capability+no-study, capability+viewer-writes).
- **R6** — The workbench-as-study-section nav (ITEM-10) sits on the P6↔P10 boundary: is the
  workbench a `detail_panels` slot or a dedicated `/studies/:id/workbench` section? Settle with P6.
- **R7** — Transfer re-scoping (ITEM-11): CONFIRMED low-risk — `accept_transfer`
  (`repository.rs:575-621`) already, in one tx, flips `studies.owner_id`, deletes the new owner's
  residual self-share, AND **re-points remaining `study_shares.owner_id` to the new owner**. The
  platform data layers are study-scoped (owner_id-flip only, no row rewrite). Just verify the
  workbench re-derives `canEdit` from the re-emitted `Study` sync on both devices.
- **R8** — Desktop single-user still runs the sync fan-out with an empty recipient list
  (`accepted_recipient_ids` → `[]`); ensure no empty-audience panic (ITEM-12).
