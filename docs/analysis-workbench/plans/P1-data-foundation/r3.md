# P1 — Data Foundation (r3, convergence round)

**Part:** the shared critical-path substrate — content-addressed local-FS object store + `analysis_results`
catalog + canonical cell/gene axes & view-index + authed study-scoped byte-range data API + write-path
ingest of a run's `/outputs` manifest + study-lifecycle GC. Everything in P2–P11 stands on this.

**Scope (per `BUILD_PLAN.md#deployment-scope`):** desktop + single-box server. Build **only the local-FS arm**
behind an open `ObjectStore` seam (MinIO/S3 later, drop-in — same content-addressed keys + `get_range`
primitive). No remote workers, no distributed data plane.

This r3 is the **union of r1 + r2**, resolving the r1↔r2 divergence (`DIFF_R1_R2.md`): it **restores r1's
canonical-axes / dense view-index subsystem** (ITEM-3, absent from r2) **and keeps r2's standing Object-GC
sweep** (ITEM-13), and takes an explicit position on the three cross-part disputes (see **## Decisions**).

New host module: `src-app/server/src/modules/workstore/` (the "Working store" kernel piece named in
`PLATFORM_ARCHITECTURE.md §7`). It is compiled Rust, host-owned, no per-analysis logic.

## Items

- **ITEM-1**: `ObjectStore` trait + local-FS impl. A content-addressed blob substrate behind one seam.
  Primitive is `get_range(key, byte_range) -> impl AsyncRead` (range-native, the whole data plane rides it);
  plus `put(reader) -> ContentKey`, `stat(key)`, `exists(key)`, `delete(key)`, `open_write() -> staging
  handle`. Keys are `sha256:<hex>` (content hash; **Decision D3**). Local layout:
  `<app_data>/workstore/blobs/<aa>/<bb>/<full-hash>` (2-level fan-out). Writes are staged to a temp file,
  hashed while streaming, then atomically `rename`d into place (dedup: if the key already exists, drop the
  temp — same bytes ⇒ same key ⇒ one physical copy). The S3/MinIO arm is deferred but the trait shape
  (`Range` GET, opaque key) is chosen so it drops in unchanged.

- **ITEM-2**: `analysis_results` catalog table + repository (sqlx compile-time). One small Postgres row per
  produced typed artifact: `id uuid PK`, `study_id uuid FK` (tenancy), `run_id uuid` (the producing run;
  nullable for source/upload artifacts), `output_id text` (the manifest slot name, e.g. `expression`),
  `datatype text` (opaque to P1 — **Decision D1**, P2 owns its meaning), `storage_layout text`
  (`chunked-dense|chunked-sparse|columnar-table|chunked-1d|opaque`), `object_key text` (or manifest key for
  multi-file), `content_hash text` (merkle/manifest hash — **ITEM-9**), `shape jsonb`, `params jsonb`,
  `covered_axes jsonb` (which canonical-axis ranges this artifact spans — **ITEM-3**), `status text`
  (`pending|ready|failed`), `size_bytes bigint`, `created_by`, `created_at`. Study-scoped **natural key**
  `(study_id, run_id, output_id)` UNIQUE for idempotent re-ingest, plus the surrogate uuid for FK targets.
  Migration `202607200001_workstore_catalog.sql` (after the current max `202607190005`).

- **ITEM-3**: **Canonical cell/gene axes + dense view-index** (the r1 subsystem restored; `axes.rs` +
  migration `202607200002_workstore_axes.sql`). This is the mechanism that makes *any* extension's output
  align to *any* other's "by construction" (`PLATFORM_ARCHITECTURE.md §5`, `DATA_MODEL.md §"canonical axes"`).
  - `workstore_cell_axis(study_id, system_cell_id bigint, sample_id uuid, cell_local_index int, view_index
    int)` — `system_cell_id` is **study-unique + stable** (a surrogate, NOT the input barcode, which is not
    unique across samples); durable identity is `(sample_id, cell_local_index)`; `view_index` is a **dense
    `0..M-1`** packing used on the hot path (WebGL/binary slicing) with **prefix-sum `base_S` per-sample
    offsets** so a sample occupies a contiguous `[start,end)` range.
  - `workstore_gene_axis(study_id, gene_id, gene_index int)` — the gene column axis; `gene_index` dense.
  - `axes.rs` provides: assign/extend axes when a source dataset is ingested (append-only — a new sample
    extends the view-index tail, never renumbers existing cells → stable offsets); a sample→`[start,end)`
    range map; bitmask cell-set operations over the dense view-index; and **NA-fill outside covered cells**
    (an artifact that covers a subset writes its `covered_axes`, and readers/aligners fill NA for cells
    outside it). **View-index alignment is a first-class kernel concern, not per-extension** — an extension
    produces values indexed by *its* rows; the host maps them onto the canonical dense view-index via the
    artifact's declared coverage. **Decision D2.**

- **ITEM-4**: Write-path ingest of a run's `/outputs` produces-manifest (P3-co-owned contract). After a
  sandbox run, the host reads `<workspace>/outputs/manifest.json` = `[{output_id, datatype, from:
  <relative-path>, layout?}]` (the `produces` manifest, `DATA_MODEL.md §"one job → many output files"`).
  For each declared output: hash+`put` into the object store, insert one `analysis_results` row (one run →
  **N artifact rows**, the provenance fan-out), stamp `covered_axes`. **Undeclared files** (logs, temp) are
  **NOT promoted** to artifacts — captured only as run metadata (P4). `save` is atomic per run: all rows land
  `ready` or the run is `failed`. Exposed to P3 as `workstore::ingest_run_outputs(run_id, workspace) ->
  Vec<ArtifactRef>`.

- **ITEM-5**: JSON **control plane** REST — `GET /api/studies/{sid}/artifacts` (catalog list, filter by
  `datatype`/`run_id`/`output_id`), `GET /api/artifacts/{id}` (metadata row), gated by study
  `effective_permission` (viewer=read). This is the "what analyses exist, of what kind, pointing at which
  artifact" index (`§5.5-B`). Sync entity `Artifact` (owner/study-scoped) so a produced result live-updates
  collaborators (**ITEM-11**).

- **ITEM-6**: Binary **data plane** — authed, study-scoped **HTTP Range/206** byte serving.
  `GET /api/artifacts/{id}/data[/{path}]` with `Range:` → `206 Partial Content` streaming from
  `ObjectStore::get_range`; full-body `200` when no `Range`. **Not** a static file server and **not** routed
  through the uploads-only `ziee-file` download path — every byte is permission-checked + study-scoped
  (`Decision D4`; matches `DATA_MODEL.md` Tier-1 "authed range server" + `bio_mcp`/SSRF-free posture). The
  `{path}` suffix serves *inside* a multi-file artifact (a Zarr chunk key, a `.bai`) so client decoders
  (zarrita/igv.js/Mol*) range-read chunks. Response is `application/octet-stream`.

- **ITEM-7**: **Server-side typed slicing** over the generic chunked layouts (`DATA_MODEL.md` Tier-2 — the
  interactive fast path, e.g. color-a-500k-cell-scatter-by-gene = one sparse column). `POST
  /api/artifacts/{id}/slice` with a **layout-keyed, domain-neutral** selector (`{layout: chunked-sparse,
  column: <gene_index>}` / `{layout: chunked-dense, cols:[…]}` / `{layout: chunked-1d, range:[a,b]}`) →
  **raw typed-array binary** (`ArrayBuffer`, little-endian, `Content-Type:
  application/octet-stream` + an `X-Workstore-Dtype`/`X-Workstore-Shape` header), **not** Arrow/JSON-of-numbers.
  The slicer keys on the **storage layout, never the data domain** — single-cell is one consumer of
  `chunked-sparse`, not a privileged tier (`DATA_MODEL.md §Tier-2`). A datatype declares (via P2) which layout
  it uses + the semantic-selector→layout-index mapping; **the mapping uses ITEM-3's `gene_index`/`view_index`**
  to turn "gene X" / "cell subset" into layout indices. Zarr-served arrays can skip this (client range-decodes
  per ITEM-6); the slicer exists for the non-Zarr fast path and the sparse CSC gene-column.

- **ITEM-8**: Zarr(v3)/Parquet write helpers for the ingest path. When a declared output's `datatype` maps to
  a served-chunked layout, ingest stores it as **Zarr** (dense/sparse) or **Parquet** (columnar); self-indexed
  genomics/structure formats (`.vcf.gz+.tbi`, BigWig, BAM, mmCIF) are stored **as-is** (`DATA_MODEL.md
  §"storage technology"`). **No HDF5-specific Rust in the serving path** — HDF5→Zarr conversion, when needed,
  is a **sandbox precompute** (P3), not host code. P1 ships only the object-store put + the layout tag; the
  actual Zarr/Parquet *encoding* is done by the producing sandbox job (Python has the writers) — the host
  ingests the already-encoded bytes. (Keeps "no format-specific Rust" honest.)

- **ITEM-9**: Multi-file artifact identity — a **manifest/merkle content hash**. A Zarr store is a directory
  of chunk objects; a BAM is `.bam`+`.bai`. An artifact whose storage-ref is a *prefix* gets **one node, one
  content hash** = a merkle hash over its `(relative-path, blob-hash)` set (`DATA_MODEL.md §"content identity
  per artifact"`). `content_hash` (ITEM-2) holds it; the object store keys individual member blobs by their
  own `sha256`, and a small `manifest.json` (path→blob-hash) is itself a blob. Enables P4's set-valued
  output-signature re-run verification.

- **ITEM-10**: Frontend **thin binary client** (`src-app/ui/src/core/workstore/`): `fetchArtifactRange(id,
  path, range)` → `ArrayBuffer`, `sliceColumn(id, selector)` → typed array (zero-copy to WebGL), `catalog(sid)`
  → JSON. Works **around the FE-10 `emit_ts` gap** (the OpenAPI TS generator has no `responseType:
  'arraybuffer'` notion): the binary endpoints are called via a thin fetch wrapper that sets `responseType`/
  reads `arrayBuffer()` directly, **not** through the generated `ApiClient` (which only models JSON). The
  generated client keeps the JSON control-plane calls. (A proper `responseType` flag into `emit_ts` is
  **deferred** — noted as a P1 follow-up, not blocking.)

- **ITEM-11**: OpenAPI honesty for the binary endpoints. The `/data` + `/slice` routes declare an
  `application/octet-stream` `OperationOutput` (not a JSON schema) so `openapi.json` is truthful and the
  **`types_ts_parity` golden test stays green** (`CLAUDE.md §"Generate OpenAPI"`). Regen **both** binaries
  (`just openapi-regen` → `ui/` + `desktop/ui/`) after adding routes.

- **ITEM-12**: Study-lifecycle cascade — register a `workstore` cleanup with the study-deletion chokepoint.
  On `on_study_deleted(study_id)`: delete the study's `analysis_results` rows + axis rows + **decrement blob
  refs** for every `object_key`/manifest member; on `on_study_duplicated`: deep-copy catalog rows + axes +
  **re-reference** (not re-upload — content-addressing makes duplicate a cheap ref-add) the same blobs.
  Hooks into live8's shared `delete_study_with_extensions` chokepoint (**Decision D5**), the same seam the
  other study-extensions use.

- **ITEM-13**: **Standing Object-GC sweep** (`gc.rs`, r2's addition, kept). A boot-time + periodic
  (~6h, mirrors `mcp/tool_calls/prune.rs`) sweep that reclaims content-addressed blobs referenced by **no**
  live table — sweeping the **union** of all referencing tables: `analysis_results` (object_key + manifest
  members) ∪ `ziee-file` (files.checksum) ∪ P4 run-artifact links. This is the backstop to ITEM-12's
  delete-time refcount (a crash between row-delete and blob-delete, or an orphaned staging temp, is reclaimed).
  A blob is deletable iff its content-hash appears in no referencing table. **Decision D5** — the *chokepoint*
  is study delete (ITEM-12); GC is the *safety net*, and it is what makes cross-table dedup (ziee-file and an
  artifact sharing a checksum) safe to delete.

- **ITEM-14**: Config + boot wiring. `workstore.root` (default `<app_data>/workstore`), `workstore.gc_enabled`
  / `gc_interval_hours`, registered in the module boot list; the object store + catalog pool + axes are
  constructed at startup; a boot log line reports the store root + backend (`local-fs`). Desktop parity:
  the module is server-embedded, so it rides desktop the same as other kernel modules (no CORE_MODULE_BLOCKLIST
  entry — it's foundational, not connected-only).

## Reuse

- **`ziee-file`** (host SDK `modules/file`; extracted SDK crate `sdk/crates/ziee-file/`) — reuse the
  **auth-extractor + `FilesystemStorage { base_path }` handle pattern** (`storage/filesystem.rs`,
  `storage/manager.rs::get_file_storage`) and the `download_with_token()` JWT-unauth shape as templates.
  **Grounding correction (verified):** `ziee-file` is **NOT** a usable base for the hot path — it is
  **content-addressing / Range / streaming / cross-file-dedup GREENFIELD**: blob key is a UUID
  (`blob_version_id`), not a hash; its sha256 `checksum` column is stored+indexed but **never used for pathing
  or dedup**; every download handler (`http/handlers/download.rs::download_file`, sig
  `RequirePermissions<(FilesDownload,)>, Path<Uuid> -> Response`) loads a **full `Vec<u8>` into memory** — no
  `Accept-Ranges`/`206`/`Content-Range`/`Range` extractor, no `Body::from_stream`. So ITEM-1/6/7 build these
  fresh; do not expect to inherit them. **Do NOT** route artifact data through `ziee-file` — it is
  uploads/blob-only and not study-scoped. Its **sha256 `checksum`** is the precedent hash (aligns with
  **D3**); cross-table blob **dedup on shared checksum** with `ziee-file` is handled by ITEM-13's union-sweep GC.
- **`dataset` module** (cytoanalyst) — reuse its sqlx repository + migration + study-scoping pattern as the
  template for the `analysis_results` catalog. Verified: `dataset` links to a file via `datasets.file_id` FK
  (`ON DELETE SET NULL`, migration `dataset/migrations/202607150002_dataset_file_id.sql`); **no
  `analysis_results`/`artifacts` table exists anywhere yet** (confirms ITEM-2 is greenfield). The current
  `dataset` placeholder row becomes a **source artifact** (`run_id NULL`, produced by upload/import) in the
  unified catalog framing (**Decision D1**), rather than a parallel table.
- **study substrate** (live8 `feat/study-management`) — reuse `effective_permission` (owner/editor/viewer)
  for gating every workstore route, and the **shared `delete_study_with_extensions` chokepoint** +
  `on_study_deleted`/`on_study_duplicated` hooks for ITEM-12 (the same seam study-extensions already use).
- **sync** — reuse `SyncEntity` + `publish` (notify-and-refetch, study-scoped audience) for the `Artifact`
  entity (ITEM-5/11).
- **`mcp/tool_calls/prune.rs`** — the boot-time + periodic prune-loop shape is the template for ITEM-13's GC.
- **jobs/sandbox** modules — ITEM-4's `ingest_run_outputs` is called *by* P3's `JobRunner→sandbox::run_analysis`
  wiring; P1 provides the ingest fn, P3 provides the run.

## Decisions

- **D1 — Who owns the artifacts/catalog table: P1 owns the *table*, P2 owns the *type meaning*.** The single
  `analysis_results` table (framed as the future unified `artifacts` table) lives in **P1** (data-foundation),
  with `datatype` + `storage_layout` as **plain string columns opaque to P1**. **P2 (datatype-system) owns the
  registry that gives `datatype` meaning** (subtyping lattice, validators, viewers, and the
  selector→layout-index mapping ITEM-7 consumes). Rationale: `PLATFORM_ARCHITECTURE.md §5.5-B` is explicit —
  *"Extensions don't own catalog tables; the host writes the catalog row"* — so the **host/kernel (P1)** owns
  the physical table + write-path + sqlx compile-time queries; P2 is a **consumer/classifier**, not a second
  table owner. This resolves the P1↔P2 dispute (PLANNING_INDEX). The cytoanalyst `dataset` placeholder folds
  into this table as a **source artifact** (`run_id NULL`), not a parallel table.

- **D2 — Canonical axes + dense view-index are a first-class P1 kernel subsystem (r1 restored).** The r1↔r2
  divergence (`DIFF_R1_R2.md`) is resolved **in favor of building it**: a `system_cell_id` (study-unique,
  stable surrogate — **not** the input barcode) + `gene_id` axis, an **append-only dense view-index** with
  prefix-sum per-sample offsets, a sample→`[start,end)` map, bitmask set-ops, and **NA-fill outside covered
  cells**. **View-index alignment is the host's job, not each extension's** — an extension emits values in its
  own row order + declares `covered_axes`; the host aligns to the canonical dense index. This is the concrete
  mechanism behind `§5`'s "any extension's output aligns to any other's by construction." r2's bare
  `covered_scope` JSONB is insufficient (no ID registry, no view-index) — it is **subsumed** by
  `covered_axes` referencing the real axis registry.

- **D3 — Content addressing = `sha256:<hex>`.** Deterministic, dedup-enabling, matches `PLATFORM_ARCHITECTURE`
  "content-addressed code blob" language. (blake3 is faster but sha256 aligns with the existing provenance/
  cosign hashing vocabulary; the `ObjectStore` key is opaque so this is swappable if a hot-path profile demands
  blake3.)

- **D4 — Data-plane serving is a dedicated authed, study-scoped Range endpoint, NOT the `ziee-file` download
  path and NOT a static server.** Every byte is `effective_permission`-gated + study-scoped
  (`DATA_MODEL.md` Tier-1 posture). This is *why* the design keeps auth while dropping per-format server
  slicing.

- **D5 — Blob GC vs study deletion: study delete is the *chokepoint*, GC is the *safety net*.** Resolving the
  P1↔P10 dispute (PLANNING_INDEX): the **deletion chokepoint is P10/live8's `delete_study_with_extensions`**
  (P1 registers `on_study_deleted` into it, decrementing blob refs at delete time — ITEM-12); the **standing
  union-sweep GC (ITEM-13) is the backstop** that reclaims orphans a crash left behind and makes cross-table
  checksum dedup (ziee-file ↔ artifact) safe to delete. Two mechanisms, not a conflict: refcount-at-delete +
  sweep-the-orphans. Blob deletion is gated on "referenced by no live table across the union."

- **D6 — Zarr(v3) served arrays + Parquet tables + self-indexed formats as-is; no HDF5-specific Rust in the
  serving path.** HDF5→Zarr conversion, when needed, is a **P3 sandbox precompute**, not host code
  (`DATA_MODEL.md §storage-technology`). P1's Rust host is a **domain-neutral authed range server + generic
  layout slicer**; it "knows what single-cell is" nowhere.

- **D7 — Binary wire format = raw little-endian typed-array `ArrayBuffer`**, not Arrow/JSON-of-numbers, for
  the slice/data plane (zero-copy to WebGL); JSON only for the control-plane catalog. OpenAPI declares
  `application/octet-stream` to keep `types_ts_parity` green (ITEM-11).

## Risks

- **`DATA_STORAGE_REDESIGN` is a proposal, not built** — P1 is its first real implementation; expect discovery
  on the axis-alignment + sparse-CSC slicing details (`BUILD_PLAN.md §honest-risks`). Mitigate: build ITEM-3
  with the single-cell 2–3-type slice first, seam open.
- **sqlx compile-time vs runtime boundary** — the catalog is kernel-owned sqlx compile-time (fine); the risk
  is Phase-5 extension collections (out of P1 scope) — flagged, not P1's problem. P1 must use
  `provision_build_db` + `as "c: DateTime<Utc>"` casts for `timestamptz` (the known cyto sqlx gotcha).
- **FE-10 `emit_ts` gap** — the TS generator can't express `responseType: arraybuffer`; ITEM-10 works around
  it with a thin non-generated fetch wrapper. Risk: drift between the JSON client and the binary client; keep
  the binary surface tiny (range + slice + catalog).
- **View-index stability under sample add/remove** — append-only extension keeps existing offsets stable, but
  **sample deletion** would renumber. Mitigate: soft-delete / tombstone a removed sample's `[start,end)` range
  (NA it) rather than compacting the view-index, so downstream artifacts' `covered_axes` never dangle. (Flag
  for P4/P10.)
- **Multi-file artifact hash cost** — merkle-hashing a large Zarr prefix on ingest is O(chunks); acceptable at
  ingest (one-time), but do it streaming, not by re-reading. (ITEM-9.)
- **Cross-table dedup deletion hazard** — a blob shared by `ziee-file` and an artifact must not be deleted
  while either references it; ITEM-13's union-sweep is the guard, but the refcount union MUST include every
  referencing table or a live blob is reclaimed. Enumerate referencing tables in one place (a `blob_refs()`
  registry) so adding P4's link table can't be forgotten.
