# P1 — data-foundation · Round 1 (blind)

Scope (per PLANNING_INDEX): **working store + `analysis_results` catalog + data API + LOCAL-FS
content-addressed object store + authed byte-range serving.** Desktop + single-box server ONLY;
S3/remote seams stay open but only the local arm is built. This is Phase-0's critical path
(`BUILD_PLAN §Phase 0a`, live8 `DEC-FOUNDATION`) — provenance, workbench, viz, and the three modules
are all blocked on it.

Grounded in the ACTUAL code of `/data/pbya/txresbench/tmp/analysis-workflow-wt` (a TxResBench app on the
txresbench SDK at `sdk/crates/*`). Key facts established by reading the tree:
- `modules/dataset` is a **metadata-only placeholder** (`datasets` table: id/name/n_cells/n_genes/
  status; `upload` returns `UploadStubResponse`; `models.rs` comment: "Real matrix bytes land in the
  file store once `txresbench-file` is extracted"). Study↔dataset link = `study_datasets` (child-id PK).
- `modules/jobs` is real (FCFS queue + `runner::JobRunner` trait + `StubJobRunner` + SSE runtime +
  boot crash-safety). The runner is a **stub child process**; the real sandbox runner drops in behind
  the SAME trait (that wiring = **P3**, not P1).
- `modules/sandbox::service::run_analysis(pool, &AnalysisRequest, &[ExtraMount]) -> AnalysisResult`
  (linux-only, 503 elsewhere) already plumbs RO/RW mounts (`ExtraMount{host_path, sandbox_path,
  mode}`) — e.g. `/inputs/matrix.mtx` (RO) + `/outputs` (RW). This is the compute→results seam P1
  consumes.
- `sdk/crates/txresbench-file` IS the blob store — but it is **uploads-only**: keyed by `file_id` UUID
  (`originals/{user}/{id}.{ext}`), whole-file `load_original`/`save_original`, sha256 checksum,
  **NO byte-range/seek reads, NO content-addressed dedup, NO study scoping**. Confirms
  `DATA_STORAGE_REDESIGN §3/§5`: the results store must be **separate** (server-read, content-addressed,
  range-capable, study/perm-scoped). txresbench-file is reused ONLY for the raw *input* upload — **and it is
  NOT yet a server dependency**: `src-app/server/Cargo.toml` does not list `txresbench-file`, `init_file_storage`
  is never called, and its `migrations/` are not in `build.rs`'s glob. Wiring it in (add dep + register
  migrations + `init_file_storage(data_root().join("files"))` at boot + a **multipart upload receiver**,
  which exists nowhere server-side) is a discrete task — mostly **P11 data-io**, but P1 must know the
  input side isn't free.
- **No results store, no `analysis_results` catalog, no binary data-plane, and no HTTP-Range/streaming
  anywhere.** Downloads today (`txresbench-file` `download_file`) load the whole `Vec<u8>` into memory (legacy
  used `fs.createReadStream().pipe()`); ITEM-8 range serving is genuinely net-new (axum
  `Body::from_stream` + `Range`/`206`). The FE transport (`core.ts`) dispatches by `Content-Type` and
  returns a **Blob** for non-JSON (no `arraybuffer`/`responseType` toggle); `emit_ts` documents binary
  as the sentinel `Json<BlobType>` → FE type `Blob` (a real `application/octet-stream` content type
  falls through to `"any"`). So the FE-10 typed-`ArrayBuffer` gap (`DATA_STORAGE_REDESIGN §3.4.1`) is
  still open — ITEM-9's thin client is required.
- Config/data dir: `txresbench_core::app_state::get_app_data_dir()` (env override seen elsewhere as
  `TXR_APP_DATA_DIR` via `rootfs::data_root()`). Modules register via
  `#[distributed_slice(MODULE_ENTRIES)]`. Migrations: `YYYYMMDDNNNN_<module>_<name>.sql` (latest
  `202607190005_jobs_grants`). sqlx compile-time `query_as!` against a build DB; timestamptz read as
  `as "c: DateTime<Utc>"`.

## Items

- **ITEM-1 — `ObjectStore` trait + local-FS content-addressed impl.** A new `modules/workstore`
  submodule `object_store`: `trait ObjectStore { put(bytes)->Key; put_prefix(dir)->Key (merkle
  manifest hash for multi-file artifacts, e.g. a Zarr store); get(&Key)->bytes; get_range(&Key, start,
  end)->bytes; open_range_stream(&Key, Range)->AsyncRead; exists; delete; }`. `Key` = content hash
  (see DEC-hash). Local impl writes to `<app_data>/workstore/objects/<aa>/<bb>/<full-hash>[/…prefix]`
  (fan-out dirs). `get_range` is the primitive the byte-range serving (ITEM-8) and any remote S3
  backend reuse. **Content-addressing gives free dedup + cache + reproducibility.** S3 backend = a
  later impl of the same trait (not built).

- **ITEM-2 — `analysis_results` catalog (Postgres, host-owned).** Migration + `models.rs` +
  `repository.rs`. One row per **analysis id** (not per job): surrogate `id uuid` PK; natural key
  `(study_id, analysis_id)` where `analysis_id` is **study-local** (`§3.5`/`§3.8` portability);
  `run_id`, `job_id` (FK-ish to jobs, nullable — a manual/interactive result has none), `kind`
  (embedding|clustering|de|expression|annotation|enrichment|trajectory|metadata-column),
  `storage_key` (the ObjectStore key of the artifact), `storage_layout`
  (zarr-dense|zarr-sparse-csc|parquet|blob — the served layout, forward-compat with P2), `axis`
  (obs|var|both), `covered_cells` (JSONB: `all` | sample-set ref — NA-fill semantics), `shape` (JSONB),
  `params` (JSONB), `provenance` (JSONB: versions/seed/extension_id — a placeholder P4 supersedes with
  real edges), `status`, `created_at`. Indexes on `(study_id, kind)`, `(study_id, analysis_id)` unique.
  Repository uses `query_as!` with timestamptz `as "c: DateTime<Utc>"`.

- **ITEM-3 — Canonical axes: cell/gene registry + dense view-index (`§3.6`/`§3.9`).** The join keys
  every artifact aligns to. Per-study: `system_cell_id` axis (generated, study-unique, stable — NOT
  the input barcode) with durable identity `(sample_id, cell_local_index)` and a dense **view index
  0..M-1** over live samples (prefix-sum `base_S` offsets); `gene_id` axis. Store these as small
  host-written artifacts + a Postgres registry (`workstore_cell_axis`, `workstore_gene_axis`, or a
  `covered_cells`-resolver keyed off sample ranges). Provides `obs['sample']` as a categorical + a
  sample→`[start,end)` range map. This is what makes "merge every job's analyses with zero conflict"
  work by alignment (NA outside covered cells), and gives the data API integer-indexed reads +
  bitmask set-ops instead of string-hash joins.

- **ITEM-4 — Kind-typed artifact readers/writers (the working store).** `modules/workstore/artifact/`
  with a `trait ArtifactCodec { layout(); read_typed(selector)->TypedBytes; }` dispatched by `kind`
  (a **closed enum now**, but behind a trait so **P2** can swap it for the open datatype registry). Per
  kind: `expression` (CSC cells×genes, gene = column = contiguous chunk → the sparse gene-column slice
  `indptr[g..g+1]→indices/data`, `§3.7`), `embedding` (dense N×d f32), `clustering`/`annotation`
  (codes u16 + categories), `de` (columnar table), `obs`/`metadata-column` (categorical|f32). Chosen
  storage = **Zarr(v3) for served arrays + Parquet for tables** (see DEC-format) so the host is a dumb
  range server and the client decodes; a thin server-side typed slicer is the Tier-2 fast path for the
  gene hot path.

- **ITEM-5 — Ingest: `/outputs` manifest → object store + catalog (the compute→results handoff).**
  `modules/workstore/ingest.rs`: given a completed job's output dir (what the sandbox wrote to the RW
  `/outputs` mount) + a `manifest.json` (`produces[]`: `{id, kind, layout, from: outputs/<path>}` per
  `DATA_MODEL "one job → many typed artifacts"`), for each declared output: (optionally convert
  `.h5ad`→Zarr — a compute-side step, P1 ingests already-served formats), `put`/`put_prefix` into the
  ObjectStore, insert a catalog row, reindex onto the canonical axes (ITEM-3), fan out N artifacts from
  one run. Undeclared files (logs/temp) → run metadata, **not** promoted. **P1 defines + tests this
  contract against a fixture `/outputs` dir; P3 wires the real `JobRunner→sandbox::run_analysis`
  producer.** This is the "sandbox→results handoff" SDK seam flagged in `DATA_STORAGE_REDESIGN §5`.
  **Gotcha:** `sandbox::run_analysis` **deletes its per-job workspace on return**, so the `/outputs`
  RW `ExtraMount` host_path must point OUTSIDE the workspace (a `<app_data>/workstore/staging/<run>/`
  dir the ingest reads before cleanup) — P3 wires the mount, P1's ingest reads the staging dir.

- **ITEM-6 — Data API · control plane (JSON, normal OpenAPI/aide).** Study-scoped, permission-gated
  routes: `GET /studies/{s}/catalog` (samples, analyses `{kind,id,shape,layout}`, obs/var columns,
  N/G — list what's streamable without opening a file), `GET /studies/{s}/analyses/{id}` (typed
  metadata by kind), `GET /studies/{s}/analyses/{id}/de?sort&filter&page` (server-side
  sort/filter/paginate → small JSON page, `§3.4`). Full `types.ts` codegen + parity test.

- **ITEM-7 — Data API · data plane (raw typed-array binary).** The viz hot path.
  `GET /studies/{s}/expression?genes=A,B&layer=lognorm` → sparse `{n, row: u32[n], value: f32[n]}` CSC
  column slice; `GET /studies/{s}/analyses/{id}` for array kinds → `f32`/`u16` typed binary;
  `GET /studies/{s}/obs/{column}` → categorical(codes+categories)|f32. Wire = raw `ArrayBuffer`
  (`new Float32Array(buf)`), **NOT Arrow/JSON-of-numbers** (`§2·Q2`). Declared honestly in OpenAPI as
  `application/octet-stream` + `format: binary` via an aide `OperationOutput` (axum `Bytes`); golden
  parity test stays green.

- **ITEM-8 — Authed, study-scoped byte + HTTP-Range serving of any artifact (`DATA_MODEL Tier 1`).**
  `GET /api/artifacts/{id}` (+ `Range:` → `206 Partial Content` + `Accept-Ranges`/`Content-Range`) for
  format-agnostic client-side decode (zarrita/igv.js/Mol*/DuckDB-WASM). Backed by ObjectStore
  `get_range` (ITEM-1). **Permission + study scoped per request** (NOT a static file server) — the
  whole reason results don't route through txresbench-file. Reuse the txresbench-file **download-token** pattern
  (`DownloadTokenClaims`, `aud: txresbench-download`) for a short-lived scoped token so a viewer streaming
  many chunks doesn't re-auth each range but can't escape its study.

- **ITEM-9 — Frontend thin binary client (FE-10 workaround).** `src-app/ui/src/api-client/dataPlane.ts`
  (or `core/workstore/`): a purpose-built `fetch` helper reusing the SDK's token-inject / base-url /
  401-refresh but calling `response.arrayBuffer()` (not `JSON.parse`/Blob), with a hand-typed surface
  (`expression(genes)→{row:Uint32Array,value:Float32Array}`, `embedding(id)→Float32Array`,
  `obs(col)→…`). The **clean long-term** (flag to SDK/live1): teach `emit_ts` a per-response
  `responseType` (`json|arraybuffer`) + `callAsync` to honor it so the ONE generated `ApiClient` owns
  binary endpoints natively — designed but deferred (SDK enhancement, not P1-blocking).

- **ITEM-10 — Study scoping, lifecycle cascade + sync.** A `workstore` **study-extension** (mirror
  `dataset/study_extension/`): `on_study_deleted` drops the study's catalog rows + de-refs its
  ObjectStore keys (content-addressed → delete only unreferenced blobs); `on_study_duplicated`
  re-parents catalog rows under a new `study_id` copying files verbatim (study-local ids stay valid —
  `§3.8`, no in-file id rewrite). Emit study-scoped `sync` on artifact create/delete
  (notify-and-refetch) so a shared workbench updates live. Read/write gated by the study role
  (owner/editor mutate, viewer read-only) + a `workstore::{read,write}` permission.

- **ITEM-11 — Config + store bootstrap.** `modules/workstore/config.rs`: resolve store root
  `<app_data>/workstore/` via `get_app_data_dir()` (+ a `TXR_WORKSTORE_DIR`/`TXR_APP_DATA_DIR`
  override for per-worktree test isolation, matching `rootfs::data_root`); an `ObjectStoreKind`
  (local-fs now; s3 seam) selector. Register `WorkstoreModule` into `MODULE_ENTRIES` (order ~25, after
  study/dataset). Add Cargo deps (see Files).

- **ITEM-12 — Tests (unit + integration, scoped to the module).** Unit: content-address key stability +
  dedup, merkle prefix hash, CSC gene-column slice correctness (indptr/indices/data), Range header
  parsing/`206`, view-index prefix-sum + sample add/remove rebuild, NA-fill alignment. Integration
  (against build DB + a fixture `/outputs` dir, no real sandbox): ingest→catalog roundtrip, catalog
  list, DE page sort/filter/paginate, binary endpoint returns correct bytes, byte-range `206`, auth
  403 cross-study, study-delete cascade, duplicate re-parent. Follow the harness pattern in
  `jobs`/`dataset` integration tests (per-test UUID DBs).

## Decisions

- **DEC-format (the central one) — served store = Zarr(v3) arrays + Parquet tables, host = dumb
  authed range server; NOT server-sliced HDF5.** `DATA_STORAGE_REDESIGN` (single-cell, older) assumes
  HDF5 with a Rust server slicer; `DATA_MODEL` + `BUILD_PLAN` (newer, general) supersede it with **Zarr
  chunk-as-object → client range-decode, zero per-format Rust** (the Vitessce model). Resolve toward
  Zarr+Parquet: (a) no native-libhdf5 system dep, (b) format-agnostic range serving generalizes to
  P2's other datatypes, (c) client-side decode (zarrita) removes a whole Rust slicing surface. Keep a
  **thin server-side typed-binary slice** (ITEM-7) as the Tier-2 fast path for the gene hot path over
  the SAME Zarr-sparse-CSC store. **Flag to the human** — this is a genuine reversal of the redesign
  doc's HDF5 assumption and touches the compute side (jobs write Zarr/Parquet, `.h5ad→Zarr` on ingest).
- **DEC-hash** — content-address with **blake3** (fast on large artifacts) OR sha256 (already a dep,
  matches txresbench-file's checksum). Lean blake3 for the multi-GB artifact case; surface the tradeoff.
- **DEC-catalog-key** — surrogate `uuid` PK + natural key `(study_id, analysis_id)` with **study-local**
  `analysis_id` (portability/`§3.8`), so export/import/duplicate re-parents a self-contained bundle
  with no in-file id rewrite.
- **DEC-binary-openapi** — the existing convention is documenting binary responses as the sentinel
  `Json<BlobType>` (`txresbench-file`'s pattern) → `emit_ts` maps it to FE type `Blob`; a raw
  `application/octet-stream` content type currently falls through to `"any"` in `emit_ts`. So P1's
  data-plane routes return axum `(headers, Bytes)` documented as `Json<BlobType>` (spec stays honest,
  golden `types_ts_parity` green), and the FE consumes the typed `ArrayBuffer` off the thin hand-typed
  client (ITEM-9) — NOT the generated `Blob`-returning `ApiClient`. The clean long-term (deferred SDK
  enhancement, flag to live1) is teaching `emit_ts`/`callAsync` a per-response `responseType`
  (`json|arraybuffer`) so the generated client owns binary natively.
- **DEC-multifile-artifact** — a Zarr store (dir of chunk objects) is **one** artifact (one content
  identity = merkle/manifest hash over its files); a run producing several typed outputs is **N**
  artifacts sharing one run node (`DATA_MODEL "one job→many files"`). Don't conflate.
- **DEC-object-store-seam** — `ObjectStore::get_range(key,start,end)` signature is S3-byte-range shaped
  from day one; local-FS is the only impl built; `s3.rs` is a compiled stub.
- **DEC-scope** — every catalog read/write + range serve is study-scoped + role-gated (viewer=read,
  editor/owner=write) via the study substrate; no static/unauthed file surface.

## Risks/unknowns

- **Zarr-v3 Rust maturity.** `zarrs` is the leading crate — verify it covers v3 write + sparse/CSC
  chunking + the sharding we need; if immature, fall back to writing Zarr chunks as plain
  content-addressed blobs with a hand-written `.zarray`/`.zmetadata` (still client-readable by zarrita)
  or reconsider HDF5 (native-lib cost). **This is the top build risk.**
- **The redesign↔DATA_MODEL format tension (DEC-format)** ripples into P3 (rootfs must have
  `zarr`/`anndata` + the `.h5ad→Zarr` convert step) and P11 (compute writes Zarr not HDF5). Must be
  settled with P3 before compute lands.
- **HDF5 native-lib** — if DEC-format keeps any HDF5, the `hdf5` crate links libhdf5 → a host + rootfs
  system dep and cross-compile pain. Zarr-first avoids it.
- **Byte-range auth cost** — a viewer streams hundreds of chunk ranges; per-request JWT verify may be
  hot. The txresbench-file download-token model (one scoped token, re-used across ranges) mitigates; confirm
  it's study-scoped, not just user-scoped.
- **Axis rebuild on sample add/remove** (ITEM-3) — the view-index prefix-sum is O(#samples) but the
  per-cell view arrays are O(M) to re-concatenate; ensure it's once-per-live-set-change, not per read.
- **P3/P1 ingest-contract circularity** — P1 defines + tests the outputs-manifest against a fixture;
  the real producer is P3. Risk of drift if the manifest schema isn't co-owned. Mitigate: write the
  manifest JSON-schema in P1 as the shared contract.
- **P2 reopening the closed kind enum** — if the `ArtifactCodec` trait / `storage_layout` seam isn't
  general enough, P2 becomes a rewrite. Design the trait to key on *layout*, not *domain*, now
  (`DATA_MODEL Tier-2`: single-cell is not privileged).
- **`analysis_results` vs `datasets` overlap** — DATA_MODEL says *dataset ≡ analysis-output ≡ typed
  artifact* (one graph). P1's catalog may want to subsume the placeholder `datasets` table (a dataset
  = a source artifact `produced_by: upload`). Decide with P2/P11 whether `datasets` folds into the
  catalog or stays a thin view. Flagged, not resolved.
