# P1 — Data Foundation (r2)

Scope: the **critical-path substrate** everything else stands on — a content-addressed local-FS
**object store**, the **`analysis_results` Postgres catalog**, the **data API** (write a result →
catalog rows + blobs; read a kind → typed binary), **typed-binary streaming** to the client, and
**authed byte-range serving** of self-indexed formats. Desktop + single-box only; every remote/MinIO
concern lives behind an open trait seam. Grounded in `DATA_MODEL.md` (the general, format-agnostic model
that **supersedes** the single-cell-only `docs/DATA_STORAGE_REDESIGN.md`) — I build the generic
substrate, not the HDF5-privileged one.

## Items

- **ITEM-1** — **`ObjectStore` trait + local-FS content-addressed impl.** A domain-neutral blob store
  keyed by **content hash** (sha256 → `blake3`-style prefix-sharded path `objects/<ab>/<cd>/<hash>`),
  distinct from `txresbench-file` (which is user-scoped, uploads-only, and is NOT content-addressed).
  Operations: `put(bytes)->Key`, `put_stream`, `get_range(key, Range)->Bytes`, `stat(key)->{len}`,
  `open_multi(prefix)` for multi-file artifacts (Zarr chunk-dir / BAM+bai), `exists`, `gc(keep_set)`.
  Local impl writes under `<app_data>/working-store/`; reuse `txresbench-file`'s **`reject_if_symlink`** +
  `ensure_dir` hardening pattern. Range read via `tokio::fs::File::seek` + bounded read. The **seam**:
  the trait is the only thing callers touch, so MinIO/S3 is a drop-in impl later (same keys, same
  `Range`). Content-addressing gives dedup + the immutability the provenance/verification path needs.

- **ITEM-2** — **`analysis_results` catalog table + migration.** One row per **typed artifact**
  (= per declared output, NOT per job). Columns: `id UUID PK` (surrogate), `study_id UUID` (natural-key
  scope + FK), `run_id UUID` (producer run; nullable for source/upload artifacts), `output_id TEXT`
  (the `produces` manifest's stable output id, e.g. `expression`/`alignment`), `datatype TEXT`
  (registry id — `single-cell/expression`, `sequence/bam`, …; P2 owns the vocabulary, P1 stores the
  string), `storage_layout TEXT` (`chunked-sparse|chunked-dense|columnar-table|chunked-1d|opaque` —
  the generic Tier-2 layout, or `opaque` for Tier-1-only), `object_key TEXT` (content hash → object
  store; a **prefix** for multi-file artifacts), `manifest JSONB` (file layout for multi-file: chunk
  keys / `.bai` sidecar / Zarr `.zarray`), `content_hash TEXT` (merkle over the artifact's files —
  the per-artifact identity for verification), `shape JSONB`, `params JSONB`, `axis TEXT`
  (`obs|var|both|none`), `covered_scope JSONB` (all | sample-set ref, for NA-alignment), `status TEXT`
  (`pending|ready|failed`), `byte_len BIGINT`, `created_at/updated_at`. Partial-unique
  `(study_id, run_id, output_id)`. Migration under `modules/analysis_results/migrations/` following the
  `dataset` module's dated-filename convention.

- **ITEM-3** — **`analysis_results` module skeleton + repository.** New backend module
  `modules/analysis_results/{mod.rs,models.rs,repository.rs,routes.rs,permissions.rs}`, self-registered
  via `MODULE_ENTRIES`. Repository uses **sqlx compile-time `query_as!`** exactly per `dataset/
  repository.rs` (incl. the `timestamptz as "col: DateTime<Utc>"` chrono override gotcha documented
  there). CRUD: `insert_artifact`, `get`, `list_by_study`, `list_by_run`, `set_status`, `delete`
  (deletes row + schedules object GC — never touches an `is_referenced` blob).

- **ITEM-4** — **Write path: ingest an outputs-manifest → artifacts + catalog rows.** The single
  in-process function P3's job-completion calls:
  `ingest_outputs(study_id, run_id, manifest: OutputsManifest, workspace: &Path) -> Vec<Artifact>`.
  For each declared `{ output_id, datatype, from: <workspace-rel path> }`: read the file(s) from the
  run workspace, `ObjectStore::put` (content hash), compute the merkle `content_hash`, insert a catalog
  row (`status=ready`). Undeclared files (logs/temp) are **not promoted** — captured as run metadata for
  P4, not first-class artifacts. Multi-file artifacts (Zarr prefix, BAM+bai) become **one** row with a
  `manifest`. This is the **produce-atomically** half of DATA_MODEL's semantics. The manifest struct +
  the `/outputs` contract are **co-owned with P3**; P1 owns the ingest side.

- **ITEM-5** — **Read path control plane (JSON, typed).** OpenAPI/aide JSON endpoints on the normal
  `ApiClient`: `GET /studies/{s}/catalog` (list artifacts: datatype+shape+layout+status, without
  opening a blob), `GET /studies/{s}/artifacts/{id}` (one artifact's typed metadata). Every handler
  authorizes through **`study::repository::effective_permission(user, study_id)`** (Viewer+ to read,
  Editor+ to write/delete) — the same chokepoint the study module uses; a foreign study → 404. Wire
  types flow through `emit_ts` → `types.ts` as today.

- **ITEM-6** — **Data plane: authed byte-range serving (Tier 1).**
  `GET /api/studies/{s}/artifacts/{id}/blob` (+ optional `path` query for a multi-file artifact's member,
  e.g. a Zarr chunk key), honoring HTTP `Range:`. Returns `206 Partial Content` +
  `Content-Range`/`Accept-Ranges: bytes` (+ `200` full when no Range), `Content-Type:
  application/octet-stream`. This is the **dumb, domain-neutral range server** DATA_MODEL Tier 1
  requires — VCF+tbi / BigWig / BAM / mmCIF / Zarr chunks all serve through it; the browser viewer
  (igv.js / Mol\* / zarrita) owns the decoder. **No format-specific Rust.** Auth = study scoping via
  ITEM-5's chokepoint (this is why it's NOT a static file server and NOT routed through `txresbench-file`).
  Range parse + `206` assembly is new (txresbench-file's `download.rs` serves `200` octet only — no range).

- **ITEM-7** — **Data plane: typed-binary slice endpoints (Tier 2, generic layout slicer).**
  The interactive fast path keyed on the **generic storage layout, never the data domain**:
  `GET /studies/{s}/artifacts/{id}/slice?...` dispatches on `storage_layout` — `chunked-sparse` →
  CSC column slice (`indptr[g..g+1] → indices/data[start..end]`, the gene-column hot path);
  `chunked-dense` → N-D hyperslab; `columnar-table` → column/page; `chunked-1d` → range. Returns
  **raw typed-array binary** (a tiny header `n` + `Uint32Array` row/index + `Float32Array` value,
  back-to-back — NOT JSON, NOT Arrow). The **semantic-selector → layout-index mapping** (gene→column,
  cell→row, locus→range) is declared by the datatype (P2); P1 slices the layout. Single-cell is one
  consumer of `chunked-sparse`, **not** privileged.

- **ITEM-8** — **OpenAPI-correct binary responses (octet-stream + `format: binary`).** Declare the
  Tier-1/Tier-2 endpoints honestly: aide response with `content: application/octet-stream, schema:
  {type: string, format: binary}` (a ~3-line `OperationOutput` impl over axum `Bytes`/a range body if
  aide lacks it). Keeps the `types_ts_parity` golden test green (generation stays deterministic). Spec
  describes the *wire* (opaque bytes); the endpoint's `datatype` describes the *decoded* shape.

- **ITEM-9** — **Frontend thin binary data-plane client (FE-10 workaround).** The SDK's
  `createApiClient`/`callAsync` always `JSON.parse` — raw `ArrayBuffer` must not hit it. Ship a
  hand-written fetch helper (`src-app/ui/src/core/dataplane.ts`) that reuses the SDK's
  `getAuthToken`/`getBaseUrl`/401-refresh path but returns `response.arrayBuffer()`, with a typed
  surface (`Data.slice(artifactId, sel) -> {row: Uint32Array, value: Float32Array}`,
  `Data.blobRange(artifactId, range) -> ArrayBuffer`). Shape is fixed by the endpoint's datatype, so
  the typed wrapper is safe. Flag the clean long-term (teach `emit_ts` a `responseType`) to the SDK
  owner (live1) but do **not** block on it.

- **ITEM-10** — **Multi-file / merkle content identity.** A helper computing an artifact's
  `content_hash` as a merkle/manifest hash over its member files (Zarr prefix, BAM+bai), stored in the
  catalog. Enables P4's set-valued run output-signature + in-sandbox re-run verification (all N hashes
  match). Single-file artifacts = hash of the one blob.

- **ITEM-11** — **Sync entity + owner/study-scoped emit.** Add `SyncEntity::AnalysisResult` to
  `modules/sync/event.rs` (+ the `(variant, "analysis_result")` string mapping); the write path
  (ITEM-4) and delete emit `publish(AnalysisResult, action, id, Audience::study(study_id), origin)`
  so a study's collaborators' devices refetch the catalog live. Notify-and-refetch only (no row data on
  the wire), matching the platform's sync contract.

- **ITEM-12** — **Object GC (referenced-set sweep).** A boot-time + periodic sweep that deletes object
  keys no live `analysis_results.object_key` (nor `txresbench-file`, nor a P4 run-artifact link) references —
  the delete-is-safe backstop for content-addressed immutability. Deferred-safe: a row-delete marks a
  key eligible; GC reclaims only truly-orphaned blobs. Respects P4's `workflow_run` linkage so a run's
  outputs aren't reaped while the run node lives.

- **ITEM-13** — **Config + boot wiring + local `<app_data>` root.** `init_working_store(&working_root)`
  in `lib.rs::build_app` (mirrors the existing `txresbench_file::init_file_storage(&files_root)` call at
  lib.rs:52), installs `Extension(WorkingStoreContext { store: Arc<dyn ObjectStore>, catalog })` the
  handlers pull from. Config key for the store root (default `<app_data>/working-store`), an
  `object_store_backend: local|s3` seam field (only `local` implemented). Desktop and single-box read
  the same code path.

## Dependencies
- **P2 datatype-system** — provides the datatype **registry** + the `datatype→storage_layout` +
  semantic-selector→layout-index mapping ITEM-7 dispatches on. P1 stores `datatype`/`storage_layout` as
  strings and slices the generic layout; the descriptor lookup is P2. **P1 can build ITEM-1..6, 8, 11,
  12, 13 with a minimal placeholder layout enum, then wire ITEM-7 against P2's registry.** (Seam: a
  `LayoutResolver` trait P2 fills.)
- **P3 compute-scheduling** — provides the **outputs-manifest / `/outputs` produces contract** + the
  run workspace ITEM-4 reads from. The `OutputsManifest` struct is **co-defined P1↔P3**; P3 calls
  ITEM-4 on job completion. P1's write path is inert until P3 exists (testable with a synthetic
  manifest meanwhile).
- **P4 provenance** — consumes P1's `run_id`/`content_hash`/output-set for the graph + verification;
  P1 must expose the FKs + merkle hash (ITEM-2, ITEM-10) but does not build the graph.
- **P10 study-substrate** (live8, built) — provides `effective_permission` + `study_id` scoping. Hard
  dependency, already merged.
- **P11 three-modules** — first real *consumer* of the write + read + slice paths (validates the
  vertical slice); not a blocker.

## Decisions
- **Working store is a SEPARATE content-addressed object store, not `txresbench-file`.** `txresbench-file` =
  user-scoped uploads only (confirmed by its own docs); results/artifacts get their own store with
  study-scoped auth + content-addressing (dedup + provenance immutability).
- **Content-address by sha256 of blob bytes** (prefix-sharded path); multi-file artifact key = a
  prefix + a merkle `content_hash`. (blake3 acceptable if a faster hash is wanted; pin one in P4 for
  verification parity.)
- **Generic layout, never domain.** Tier-2 slicing keys on `chunked-sparse|dense|columnar|1d`, so
  single-cell is un-privileged — corrects `DATA_STORAGE_REDESIGN`'s HDF5-CSC-as-*the*-format assumption
  per DATA_MODEL. **No HDF5/VCF/BigWig-specific Rust in the serving path.**
- **Store served arrays as Zarr, tables as Parquet, self-indexed genomics/structure as-is** (DATA_MODEL
  §Storage-technology) — the store is format-agnostic; the datatype (P2) owns the format. P1 doesn't
  convert; a Tier-3 sandbox precompute (P3) does when needed.
- **Two planes on one surface**: JSON control plane on the generated `ApiClient`; binary data plane on a
  hand-written fetch helper until the SDK grows `responseType` (FE-10). Raw `ArrayBuffer` — **no Apache
  Arrow, no DuckDB-WASM** on the live wire (DATA_MODEL/§2·Q2 rationale).
- **Produce-atomically / consume-individually**: a run's N outputs are one atomic ingest (ITEM-4); each
  is an independently-addressable catalog row downstream binds to.
- **Auth on every byte**: range + slice endpoints go through `effective_permission`; never a static
  server. This is the whole reason the host mediates reads.

## Risks
- **P1↔P3 manifest contract drift** — the `OutputsManifest` shape is the seam between "job wrote
  `/outputs`" and "catalog ingested them". Co-define it once; a mismatch silently drops outputs. Mitigate
  with a shared struct + a round-trip test (synthetic manifest → ingest → catalog rows).
- **Range serving correctness** — off-by-one `Content-Range`, multi-range requests, `416` on unsatisfiable
  range, large-file streaming without buffering the whole blob. igv.js/zarrita are strict range clients;
  a subtly-wrong `206` breaks them silently. Test against a real igv.js/zarrita range pattern.
- **`DATA_MODEL` is a proposal, not built** — P1 is its first real implementation; expect discovery
  around Zarr multi-file layout + kerchunk-virtualize-HDF5 (defer kerchunk to a later item; convert-to-Zarr
  on ingest is the P3 path).
- **OpenAPI binary + `types_ts_parity`** — the golden parity test is byte-sensitive; the octet
  `OperationOutput` must generate deterministically or `just openapi-regen` diverges across the two
  UI workspaces.
- **GC vs live references** — deleting a blob still referenced by a P4 run node or a duplicated study
  (content-addressed dedup means two studies can share a key). GC must sweep the **union** of all
  referencing tables, not just `analysis_results`.
- **Study-scoped sync audience** — `Audience::study(...)` must exist in live8's sync (verify at merge;
  jobs module used owner-scope seams). If absent, fall back to owner-scope + collaborators fan-out.

## Effort
- **M–L.** ITEM-1/2/3/13 (store + catalog + boot) ≈ small-medium, well-patterned off `dataset`/
  `txresbench-file`. ITEM-4/5/8/11 ≈ medium (write path + control plane + OpenAPI binary + sync). ITEM-6
  (range serving) ≈ medium-fiddly (correctness-sensitive). ITEM-7 (Tier-2 slicers) ≈ the largest single
  item, gated on P2. ITEM-9/10/12 ≈ small each. Total ≈ 2–3 focused build-lifecycle passes; ITEM-7 can
  land in a second pass once P2's LayoutResolver exists. Critical path for the whole platform — build
  ITEM-1..6 + 13 first (unblocks P3/P11), ITEM-7 second.
