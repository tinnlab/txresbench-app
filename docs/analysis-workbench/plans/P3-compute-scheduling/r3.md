# P3 — Compute + Scheduling (r3, blind/independent)

Scope: **desktop + single-box server ONLY**. Local bwrap behind a `ComputeBackend` seam; one pool with
interactive/batch priority + per-user fair-share; content-addressed `inputs.json` / outputs-manifest contract;
scientific rootfs; cgroup v2 live metrics. Remote/HPC seam kept open, not built.

Grounded in ACTUAL code (`/data/pbya/txresbench/tmp/txresbench` = main; feature worktree server tree == main).
The app already has, REAL and working: `modules/jobs` (queue + executor + logs + metrics + SSE + stop +
settings), `modules/sandbox` (bwrap core + `service::run_analysis` + cgroup writer + `ExtraMount`),
`modules/rootfs` (docker-build→embed→squashfuse-mount), `modules/dataset` (canonical repo + `txresbench-file` blobs).
The ONE stub is `runner::StubJobRunner`; `run_analysis` is a standalone batch service fn NOT yet behind
`JobRunner`. P3 = wire those together + add the missing scheduling/metrics/contract layers.

## Items

- **ITEM-1**: Define the `ComputeBackend` topology seam — `trait ComputeBackend { async fn run(&self, spec:
  ComputeSpec, sink: &dyn ProgressSink) -> Result<ComputeOutcome, AppError>; fn probe(&self) ->
  BackendAvailability; }` in `modules/sandbox/backend/mod.rs`. `ComputeSpec` is **path-agnostic**: `{ command
  (or code_blob ref), inputs: Vec<MaterializedInput>, output_dir: PathBuf, params: Value, limits:
  ResourceProfile, class: PriorityClass, resource_class: ResourceClass }` — the script never learns *where* it
  runs. `ComputeOutcome { exit_code, timed_out, duration_ms, peak_metrics, manifest: OutputManifest }`. This is
  the §4.1.2 "compute is a swappable backend behind one seam" — distinct from `JobRunner` (the queue's spawn
  contract). Only `LocalBwrapBackend` is implemented; `RemoteWorkerBackend`/`HpcBackend` are `// SEAM` TODO stubs.

- **ITEM-2**: `LocalBwrapBackend` impl of `ComputeBackend` — wraps the existing bwrap core. Its `run()` calls a
  new **streaming** sandbox entry (ITEM-3), assembles the `ExtraMount` vec from `spec.inputs` (read-only) +
  `spec.output_dir` (read-write) + progress FIFO (ITEM-4), and returns the parsed manifest + peak cgroup
  metrics. Linux-only; 503/`BackendAvailability::Unsupported` off-Linux (mac/win VM backend is a future seam).

- **ITEM-3**: `sandbox::run_analysis_streaming` — a streaming variant of today's buffered `run_in_sandbox`.
  Spawns the bwrap child, reads stdout/stderr line-by-line and forwards each line to a `ProgressSink` (→ the
  jobs `job_logs` + SSE broadcast) instead of accumulating into `SandboxRunResult`. Keeps the existing batch
  `run_analysis` for the synchronous REST `POST /sandbox/execute`. Both share `build_bwrap_argv` + `CgroupScope`.

- **ITEM-4**: Progress-FIFO plumbing — extend the app's `build_bwrap_argv` to accept an optional
  `progress_fifo_src: Option<&str>` that binds a host FIFO onto `/txr/progress` and sets `$TXR_PROGRESS`
  (port of txresbench code_sandbox's proven `progress_fifo` pattern). The streaming runner drains the FIFO into
  structured `notifications/progress`-style frames (phase + pct + message) on the job SSE, so a scanpy script
  can emit real progress ("normalizing 40%") not just log lines. `None` → byte-identical to no-FIFO argv.

- **ITEM-5**: `SandboxJobRunner: JobRunner` — the real runner that replaces `StubJobRunner` in `JobsModule::init`
  (`runner: Arc::new(SandboxJobRunner::new(backend))`). Implements the EXISTING `JobRunner::spawn(&Job)` seam
  so the whole proven queue/executor/logs/metrics/stop/SSE pipeline is reused unchanged. It translates
  `Job.params` (JSONB) → a `ComputeSpec` (ITEM-9) and delegates to `dyn ComputeBackend`. The runner.rs doc
  comment already anticipates exactly this drop-in.

- **ITEM-6**: Content-addressed **input materialization** — host resolves a step's `requires` (artifact ids from
  the P1 catalog) → content-addressed blobs in the working store, hard-links/binds each read-only at a stable
  path (`/inputs/expression.h5`, `/inputs/embedding.h5`), and writes `/inputs/inputs.json` referencing inputs
  **by content hash + kind** (path-agnostic — the same file a remote backend will `fetch object sha256:… →
  scratch → bind`) plus `/inputs/params.json`. New `sandbox::inputs.rs::materialize_inputs(spec) ->
  Vec<MaterializedInput>`. Reuse `ExtraMount{mode: ReadOnly}`.

- **ITEM-7**: **Outputs manifest** contract — the script writes `/outputs/*` + `/outputs/manifest.json`
  (`{ produces: [{ id, kind, from: "outputs/result.h5" }] }`, per DATA_MODEL §"one run → N typed artifacts").
  New `sandbox::outputs.rs::parse_manifest(output_dir) -> OutputManifest` (strict: reject unknown paths, cap
  count/size). The runner content-hashes each declared output and hands `(kind, hash, bytes-ref)` to the P1
  ingest API → catalog rows + a run→artifact fan-out. Undeclared `/outputs` files are ignored (not promoted).
  Reuse `ExtraMount{mode: ReadWrite}` for `/outputs`.

- **ITEM-8**: **ExtraMount plumbing end-to-end** — assemble the full `ExtraMount` vec in `LocalBwrapBackend`:
  N read-only input binds + one read-write `/outputs` + one FIFO. `build_bwrap_argv` already maps
  `ReadOnly→--ro-bind`, `ReadWrite→--bind` (verified in `sandbox/sandbox.rs`, unit-tested at lines 650-651).
  This item is the wiring, not new argv surface.

- **ITEM-9**: `Job.params` → `ComputeSpec` translation — define the job payload schema an analysis extension
  submits: `{ entry_script | command, requires: [artifact_id], produces_hint, params, schedule: { class,
  resources } }`. `SandboxJobRunner::build_spec(job) -> ComputeSpec` validates + resolves it. This is the
  "params→analysis-command translation" the app is missing.

- **ITEM-10**: **Scientific rootfs** — extend `server/rootfs/Dockerfile` with a Python scientific manifest:
  `scanpy anndata leiden python-igraph harmonypy scikit-learn numpy scipy pandas umap-learn` via a pinned
  `uv pip install` (or `pip --require-hashes`) layer on the existing `python3` base; keep the fail-soft R
  layer. Bump `ROOTFS_SCHEMA_VERSION` (build_helper `ROOTFS_SCHEMA_VERSION: u32 = 1` + `ARG` in Dockerfile) so
  `is_fresh` re-stages. `mksquashfs` still runs in-container (DEC-9, host needs only docker). Watch the
  embedded-asset size grows ~1.5-2 GB (image `include_bytes!`).

- **ITEM-11**: rootfs schema/version lockstep — verify the bump flows: build_helper const == Dockerfile `ARG`
  == `/.txresbench-sandbox-rootfs-schema` marker == runtime `rootfs::version::is_fresh` re-stage trigger, so
  a scanpy-manifest edit forces a re-embed and the boot mount-probe refuses a stale rootfs. No new mechanism —
  confirm the existing `format_version(schema, dockerfile_bytes)` sha8 catches the Dockerfile edit.

- **ITEM-12**: Scheduling classes — add `priority_class TEXT` (`interactive|normal|batch`, default `normal`) +
  `resource_class TEXT` (`cpu-sandbox` only for now, seam-open) to the `jobs` table (new migration under
  `jobs/migrations/`), to `Job`, `CreateJobRequest`, and the `JobStatus`/enum module. A migration adds a CHECK
  constraint on the two vocabularies. `resource_class` exists so `gpu`/`highmem`/`cluster-batch` are later
  rows, not a schema change.

- **ITEM-13**: **Class-aware dispatch** — replace the FCFS `claim_next_queued()` (oldest-first) in
  `scheduler.rs::dispatch_ready` with class-priority claiming: **reserve K interactive slots** so an
  interactive job (a UI slider re-run a human is watching) never head-of-line-blocks behind a running batch
  job; `normal` fills the shared pool; `batch` fills only when non-batch demand is satisfied. Single pool,
  single cap (`max_concurrent_jobs`) + a `reserved_interactive_slots` setting. New
  `JobRepository::claim_next_by_class(class, exclude_owners)`.

- **ITEM-14**: **Per-user fair-share within a class** — `claim_next_queued_fair` rotates the owner it serves
  among queued same-class jobs (round-robin / least-recently-served owner, or weighted by a per-user weight) so
  one user's burst — or the AI agent's chained tool-call burst — can't starve others. On 1-box this is
  in-process WFQ over the queued set; the cross-node arm stays deferred. Tracks per-owner running counts from
  the `jobs` table (no new table needed).

- **ITEM-15**: Priority inference from trigger — at job-create, the host stamps `priority_class`:
  UI interactive controls (slider re-run, DE-on-selection) → `interactive`; explicit "run pipeline" / an
  AI-agent-submitted job → `normal`/`batch` (the AI defaults to `normal` unless a human is actively awaiting
  the result). Extension MAY override via `schedule.class`; host infers when absent. Lives in the job-create
  handler / the analysis-extension submit path.

- **ITEM-16**: **cgroup v2 live METRICS read-back** — extend `sandbox/cgroup.rs::CgroupScope` with
  `read_metrics() -> CgroupSample` that reads back `<scope>/memory.current`, `memory.peak`, `pids.current`,
  `pids.peak`, and `cpu.stat` (`usage_usec` → CPU% delta between samples). Today `cgroup.rs` only *writes*
  (`create`/`attach_pid`/`write_controller`); it never reads. This is the "report ACTUAL mem/cpu per job" ask —
  whole-subtree accounting, strictly more accurate than the single-pid `sysinfo` `ProcSampler`.

- **ITEM-17**: Wire cgroup metrics into the job metric loop — the executor's sampler tick (currently
  `ProcSampler::sample()` per-pid) reads `CgroupScope::read_metrics()` when a cgroup scope exists, falling back
  to `ProcSampler` when cgroup is unavailable (probe says no delegated slice). Persist to `job_metrics`
  (`cpu_pct`, `mem_bytes`; consider adding `mem_peak_bytes`, `pids_current` columns) + SSE metric frames, so
  the UI shows true per-job memory/CPU. Report `peak_metrics` in `ComputeOutcome` for the run record.

- **ITEM-18**: **Per-job resource profiles** — resolve a job's `schedule.resources { cpu, mem }` (or a
  per-class default: interactive=2cpu/4Gi, batch=higher) into the cgroup caps (`memory.max`,
  `memory.swap.max`, `pids.max`, `cpu.max`) + prlimit tail, **clamped to the admin ceiling** in
  `sandbox_settings` (a caller can only ask for LESS, mirroring `clamp_timeout`). The write path already
  exists (`write_controller`); this adds the class→profile→caps resolution.

- **ITEM-19**: **RESERVATION = SOFT admission, per-job caps = HARD** (the P3 decision; see §Decisions). The
  scheduler's slot/reservation accounting is best-effort (count running per class vs `max_concurrent` +
  `reserved_interactive_slots`); there is NO aggregate host-memory admission gate. Enforcement is the HARD
  per-job cgroup cap (ITEM-18) which physically prevents any single job from OOMing the box. Documented as the
  1-box multi-user posture.

- **ITEM-20**: Cancel → sandbox teardown — confirm the existing cancel path (`runtime::register_cancel` /
  `signal_cancel` watch channel + executor SIGTERM→grace→SIGKILL) kills the bwrap child AND its cgroup subtree
  (bwrap `--die-with-parent` + `PR_SET_PDEATHSIG`; `CgroupScope` cleans on Drop). Flush a final metric/log
  frame + partial `/outputs` are discarded (no half-manifest ingest) on cancel/timeout.

- **ITEM-21**: Non-Linux degrade — `run_analysis_streaming` + `LocalBwrapBackend` are `#[cfg(target_os =
  "linux")]`; other targets return `SERVICE_UNAVAILABLE` (matching the existing `run_analysis` cfg split). The
  mac libkrun-VM / win WSL2 backends are a future `ComputeBackend` impl behind the same seam, not built now.

- **ITEM-22**: Tests — unit: class-priority dispatch order (batch never preempts a reserved interactive slot),
  fair-share owner rotation, `inputs.json` shape + hash-reference, manifest parse (accept/reject),
  `clamp_timeout` reuse, cgroup metric parse (`memory.current`/`cpu.stat` fixtures), profile→caps clamping.
  Integration: a streaming job end-to-end running a tiny python script IN the scientific rootfs (writes

  Rootfs smoke: `python3 -c "import scanpy"` inside the mounted rootfs (Linux + rootfs-gated `#[ignore]`).

## Decisions

- **DEC-P3-1 — RESERVATION is SOFT (admission best-effort); per-job resource caps are HARD (cgroup-enforced).**
  On a single box shared by multiple users we CANNOT reliably predict a scanpy job's peak memory before it runs,
  so a *hard aggregate* admission gate (sum of declared `mem` ≤ host RAM) would either idle the box (jobs
  over-declare) or lie (jobs under-declare). Instead: the scheduler does **soft slot-based reservation** — K
  reserved interactive slots + a concurrency cap — which is cheap, predictable, and prevents head-of-line
  blocking without pretending to know memory. The **hard backstop is the per-job cgroup `memory.max`/`pids.max`/
  `cpu.max`** (ITEM-18): any job that exceeds its cap is OOM-killed by the kernel, so one runaway job can never
  take down the box or another user's job. This is the correct 1-box multi-user split: **soft where prediction
  is impossible (admission), hard where the kernel can enforce (per-job caps).** It also matches how the code is
  already shaped — the cgroup writer exists (hard caps), the scheduler is a slot counter (soft). (Resolves the
  r1 hard-reserve vs r2 soft-reserve divergence: reservation is soft, caps are hard — both, on their right axis.)
- **DEC-P3-2 — cgroup metrics are the primary source, `ProcSampler` (sysinfo/pid) the fallback.** cgroup
  `memory.current`/`memory.peak`/`cpu.stat` account the whole bwrap subtree (all forks), which single-pid
  sysinfo misses; fall back only when no delegated cgroup slice is available (probe-gated).
- **DEC-P3-3 — `ComputeBackend` (topology seam) is distinct from `JobRunner` (queue seam).** `SandboxJobRunner`
  implements `JobRunner` and *delegates* to a `dyn ComputeBackend`. Keeps the proven queue untouched and makes
  "run elsewhere" a backend swap, per §4.1.2.
- **DEC-P3-4 — one pool, three priority classes, cpu-sandbox only.** No multi-pool/backend routing now;
  `resource_class` column present so gpu/highmem/cluster are future rows, not a migration.
- **DEC-P3-5 — `inputs.json` references by content HASH, not path** (path-agnostic), even on 1-box where
  materialize = local hard-link. Same code path a remote backend fetches through; reproducible-anywhere.
- **DEC-P3-6 — scientific rootfs stays a single embedded flavor** (DEC-2, no multi-flavor), scanpy manifest
  pinned + fail-soft; schema bump gates re-embed.

## Risks

- **R1 — embedded rootfs bloat.** scanpy+deps push the squashfs to ~1.5-2 GB `include_bytes!`'d into the binary
  (compile time + binary size). Mitigate: zstd (already), consider a lazy-fetch seam later; acceptable for now.
- **R2 — P1 not ready.** ITEM-6/7/9 block on the catalog + working store. Mitigate: sequence the spine +
  scheduling + metrics first (no P1 dep); land the contract wiring last.
- **R3 — cgroup delegation absent on desktop.** Without a delegated cgroup-v2 slice (unprivileged desktop),
  hard caps + metrics degrade to prlimit-only + sysinfo. Mitigate: probe-gated fallback (ITEM-17), documented;
  hard caps become best-effort exactly where the OS can't enforce.
- **R4 — provenance chokepoint contention (P4).** P3 emits the manifest/inputs.json; P4 owns the graph. Risk of
  double-writing the run record. Mitigate: one write site — P3 hands the emitted artifacts to P4's ingest, P4
  records edges.
- **R5 — fair-share starvation edge cases.** Naive round-robin can starve a single-job user behind a
  many-job user if weights are wrong. Mitigate: least-recently-served ordering + unit test the rotation.
- **R6 — streaming back-pressure.** A chatty script flooding stdout could overwhelm the SSE/log insert path.
  Mitigate: reuse the jobs module's existing log cap + SSE subscriber cap; drop-oldest on the FIFO drain.
- **R7 — schema-bump / stale-rootfs mismatch.** Forgetting the `ROOTFS_SCHEMA_VERSION` bump when editing the
  Dockerfile ships a stale rootfs. Mitigate: `format_version` includes the Dockerfile sha8 → `is_fresh` catches
  a content edit even without a manual schema bump; the boot mount-probe refuses a mismatch.
