# P3 — Compute & Scheduling (Round 1, blind)

Scope (per `PLANNING_INDEX.md` P3 + `BUILD_PLAN.md#deployment-scope`, desktop + 1-box, LOCAL bwrap only behind
an open `ComputeBackend` seam): wire `JobRunner`→`sandbox::run_analysis` as a **streaming** runner; introduce the
`ComputeBackend` seam (local bwrap arm only, resource-class routing stubbed); provision the **scientific rootfs**
(scanpy/anndata/leiden/harmony); add **scheduling classes** (interactive vs batch, single pool, per-user
fair-share) over today's FCFS; and implement the **compute contract** (content-addressed code + path-agnostic
`inputs.json` → `/inputs` → sandbox → `/outputs` + a `produces` manifest).

Grounding: everything below builds on code already present on `feat/analysis-workflow`:
- `jobs/` — FCFS `scheduler.rs`, pluggable `runner.rs` (`JobRunner` trait + `SpawnedJob{child}` + `StubJobRunner`),
  `seams.rs` (no-op sync/notify), `runtime.rs`+`sse.rs` (per-job SSE, log/metric drain), `repository.rs`
  (`claim_next_queued` = oldest-`queued` FCFS, `count_running`, terminal transitions, boot crash-safety),
  `settings.rs` (`job_settings` singleton concurrency cap), `models.rs` (`Job`, `JobStatus`,
  `CreateJobRequest{job_type,name,params}`), migrations `202607190001..05`.
- `sandbox/` — `sandbox.rs::run_in_sandbox` (async, single-shot, owns its bwrap `Child` + capture + timeout +
  cgroup + seccomp) + `build_bwrap_argv` (OS-independent, `--unshare-net` network-BLOCKED, `ExtraMount` RO/RW binds,
  prlimit tail), `service.rs::run_analysis` (materialize workspace → run → cleanup, Linux-only, 503 elsewhere),
  `types.rs` (`ExtraMount`, `MountMode`, `SandboxContext`, `HardeningCapabilities`), `settings.rs`
  (`SandboxResourceLimits`), `cgroup.rs`, `probes.rs`, `config.rs` (self-enable + `SandboxState`).
- `rootfs/` — `mod.rs::ensure_ready` (lazy extract+squashfuse-mount), `embedded.rs`/`mount.rs`/`version.rs`
  (`ROOTFS_SCHEMA_VERSION`), `rootfs/Dockerfile` (minimal: debian + r-base-core + jsonlite + python3, **no**
  scanpy/anndata/leiden), `build_helper/sandbox_rootfs.rs` (docker-build → `include_bytes!`, fail-soft stub).
- Intended caller: `dataset` module + (future) the extension compute path. `service.rs` header says "the dataset
  pipeline will call `run_analysis`"; `jobs/mod.rs` says live5's `sandbox::run_analysis` "drops in behind the SAME
  `JobRunner` trait at integration".

## Items

### A. JobRunner ⇄ sandbox integration (the crux — reconcile two execution shapes)
- **ITEM-1 — Streaming sandbox spawn variant.** `sandbox::run_in_sandbox` is single-shot: it owns the bwrap
  `Child`, drains+caps stdout/stderr internally, applies its own timeout, and drops cgroup/seccomp/workspace at
  fn end. The jobs executor (`scheduler.rs::execute_job`) instead needs a *live* `Child` it drives (pipe drain via
  `drain_logs`, pid sampling via `ProcSampler`, cancel via `kill_child`, terminal persist). Add
  `sandbox::run_in_sandbox_spawn(...) -> Result<SandboxSpawn, AppError>` that does everything `run_in_sandbox`
  does **up to** `cmd.spawn()` (build argv, ensure identity, create cgroup scope, install seccomp pipe, spawn
  bwrap with `stdout/stderr=piped`, `kill_on_drop(true)`, attach cgroup pid) then **hands back** the spawned
  `tokio::process::Child` plus a **lifecycle guard** (owns `CgroupScope`, `SeccompPipe`, and the workspace-cleanup
  decision) so the executor drives + reaps the child and drops the guard on completion. Refactor
  `run_in_sandbox` to `= run_in_sandbox_spawn(...) + internal drive` so the REST `execute` path is unchanged.
- **ITEM-2 — Extend `SpawnedJob` with a lifecycle guard.** `runner.rs::SpawnedJob` currently carries only
  `child`. Add `keepalive: Option<Box<dyn Send + 'static>>` (opaque holder for the sandbox's cgroup scope +
  seccomp pipe + workspace guard) so a `JobRunner` impl can attach resources whose Drop must outlive the child.
  Executor holds `spawned.keepalive` for the child's whole life and drops it after the terminal persist. Stub
  runner passes `None`.
- **ITEM-3 — `SandboxJobRunner` (implements `JobRunner`).** New `jobs/runners/sandbox_runner.rs`. For an
  `analysis`-type job it: (a) parses the job's structured `params` (the analysis spec, ITEM-14), (b) materializes
  inputs + `/outputs` (ITEM-11/12), (c) builds the entry command (`Rscript /code/entry.R` or
  `python3 /code/entry.py` over `/inputs`+`/outputs`), (d) calls `run_in_sandbox_spawn` with the assembled
  `ExtraMount`s, and (e) returns `SpawnedJob{child, keepalive}`. Non-`analysis` job_types still route to the stub
  (kept for tests). Linux-only body; non-Linux returns the existing 503 (spawn error → job `failed`).
- **ITEM-4 — Wire the runner selection in `JobsModule::init`.** Replace the hardcoded
  `runner: Arc::new(StubJobRunner)` with a runner chosen from the sandbox availability
  (`sandbox::config::init_status()==Ready` → `SandboxJobRunner`, else keep stub with a boot warning). Idempotent
  scheduler spawn unchanged.
- **ITEM-5 — Cancellation correctness across bwrap.** Verify `scheduler.rs::kill_child` (SIGTERM→grace→SIGKILL on
  the bwrap **parent** pid) tears down the whole pid-namespace (bwrap runs `--unshare-pid --as-pid-1`, so killing
  pid-1 in the ns reaps the bash grandchild). Add `--die-with-parent` is already set; confirm `kill_on_drop` +
  guard-drop close the cgroup/seccomp fds. No new code expected beyond a test; note if a bwrap-specific reap is
  needed.

### B. ComputeBackend seam (local impl only; open for remote/HPC/GPU)
- **ITEM-6 — `ComputeBackend` trait.** New `jobs/compute/mod.rs` defining the platform seam from
  `PLATFORM_ARCHITECTURE §4.1.2` ("the `JobRunner`/`ComputeBackend` trait"): `trait ComputeBackend { fn id()
  -> &str; fn supports(&self, class: ResourceClass) -> bool; async fn spawn(&self, job:&Job, plan:&ComputePlan)
  -> Result<SpawnedJob,String>; }`. This sits **above** `JobRunner`: `JobRunner::spawn` becomes the local arm's
  method. Introduce `ComputePlan` (resolved inputs mounts + entry command + limits) so the backend is handed a
  ready plan, keeping fetch/mount logic backend-agnostic (the data plane, ITEM-11).
- **ITEM-7 — `LocalBwrapBackend`.** The only implemented backend: wraps `SandboxJobRunner`; `supports` returns
  true only for `ResourceClass::CpuSandbox`. `gpu`/`highmem`/`cluster-batch` are declared enum variants that route
  to a typed `BACKEND_UNAVAILABLE` error (seam open, deferred per BUILD_PLAN). A `BackendRegistry`
  (`Vec<Arc<dyn ComputeBackend>>`, local-only today) selects by `job.resource_class`.
- **ITEM-8 — `ResourceClass` enum.** `CpuSandbox` (default/only) + deferred `Gpu`/`Highmem`/`ClusterBatch`
  variants, serde snake-case, stored as `jobs.resource_class` text (ITEM-13). Everything defaults to `cpu-sandbox`
  so behavior is unchanged until later phases add pools.

### C. Scientific rootfs (scanpy/anndata/leiden/harmony)
- **ITEM-9 — Provision the scientific Python stack in `rootfs/Dockerfile`.** Extend the Stage-1 image with a
  reproducible, **fully-baked** scientific env (network is `--unshare-net`-BLOCKED at runtime, so NOTHING may be
  installed at run time — everything ships in the rootfs). Add `scanpy`, `anndata`, `leidenalg`,
  `python-igraph`, `harmonypy`, plus their compiled deps (`numpy`/`scipy`/`pandas`/`scikit-learn`/`numba`/`llvmlite`).
  Decision (ITEM-DEC-A): use **micromamba** (conda-forge) for a self-contained, pinned scientific stack rather than
  Debian apt + pip-from-source (avoids BLAS/llvmlite build pain; deterministic pins). Keep r-base-core for R
  analyses. Set thread env already handled by `build_bwrap_argv` (`OMP/OPENBLAS/MKL_NUM_THREADS=1`).
- **ITEM-10 — Bump `ROOTFS_SCHEMA_VERSION`** (`rootfs/version.rs`) so the runtime mount probe refuses a stale
  cached rootfs and the build helper (`is_fresh`) re-runs docker. Update the Dockerfile `ARG
  ROOTFS_SCHEMA_VERSION` default in lockstep (already `--build-arg`-driven). Add a build-time smoke assertion
  (import scanpy/anndata/leidenalg/harmonypy) baked as a Dockerfile `RUN python3 -c "import scanpy,anndata,
  leidenalg,harmonypy"` so a broken env fails the image build, not a runtime job.

### D. Compute contract (content-addressed code + inputs.json → /inputs → /outputs + manifest)
- **ITEM-11 — Input materialization (the local data plane).** Before spawn, the runner resolves each declared
  input artifact (by content hash/URI from P1's object store — on 1-box a local content-addressed file read) into
  the per-job workspace and produces `ExtraMount`s binding them **read-only** at stable paths
  (`/inputs/<name>.<ext>`), plus writes `/inputs/params.json` (baked params) and a **path-agnostic
  `inputs.json`** (declares each input's logical name → stable in-sandbox path + content hash; makes the entry
  script byte-identical across runs/boxes → content-addressable, per §0.6/§4.1.2). `/outputs` is a workspace
  subdir bound **read-write**. Uses the existing `ExtraMount{host_path,sandbox_path,mode}`.
- **ITEM-12 — Output ingestion + produces-manifest.** After the child exits 0, read
  `/outputs/manifest.json` (naming produced ids/kinds per §4.1) and **hand** the output dir + manifest to P1's
  catalog-ingest and P4's provenance-record (via a seam, ITEM-16) — the host ingests kind-typed artifacts into the
  working store + catalog, then the runner cleans the workspace (do NOT auto-remove before ingest — today's
  `run_analysis` removes the workspace at fn end, which is wrong for the analysis path). A missing/invalid manifest
  on a 0-exit → job `failed` with a clear error.
- **ITEM-13 — Content-addressed code blob execution.** The entry script is a **hashed content-addressed blob**
  (P4's `provenance_code_blobs`); the runner fetches it into the workspace at `/code/entry.<ext>` (read-only bind)
  and runs it. P3 owns the *execution* of the blob at a stable path + the `inputs.json` contract; P4 owns creating
  + storing the blob and recording the run node (dependency, ITEM-16). On 1-box the blob store is a local
  content-addressed dir.

### E. Scheduling classes (interactive vs batch, single pool, per-user fair-share)
- **ITEM-14 — Job spec + class/resource columns.** Migration adds to `jobs`: `job_class text NOT NULL DEFAULT
  'batch'` (`interactive|batch`), `resource_class text NOT NULL DEFAULT 'cpu-sandbox'`. Extend
  `CreateJobRequest`/`Job`/`models.rs` with typed `JobClass`/`ResourceClass` (serde snake-case, text-stored like
  `JobStatus`). Define the **analysis job spec** as the structured `params` shape (code-blob ref, input refs,
  params, produces-kinds) consumed by ITEM-3. The host **infers** `interactive` from the trigger (a UI slider
  re-run) and `batch` for explicit pipelines (§4.1.1); client may declare, server clamps.
- **ITEM-15 — Class-aware + fair-share dispatch.** Rework `scheduler.rs::dispatch_ready` +
  `repository.rs::claim_next_queued` from pure FCFS into a **two-phase, single-pool** policy:
  1. **Interactive priority / reserved slots** — dispatch eligible `interactive` jobs first up to the cap; batch
     jobs only fill while `running < cap - interactive_reserve` so a long batch job never head-of-line-blocks a
     just-arrived interactive one (reserve = new `job_settings.interactive_reserved_slots`, ITEM-17).
  2. **Per-user fair-share** within a class — replace "oldest `queued` first" with an ordering keyed on
     `(count of that owner's currently-running jobs ASC, created_at ASC)` so a user already consuming slots yields
     to a waiting user (simple weighted-fair-queuing approximation; true WFQ deferred). Implement as a
     `claim_next_for_class(class, exclude_saturated_users)` SQL variant using a `LEFT JOIN`/window on running
     counts, keeping `FOR UPDATE SKIP LOCKED`.
- **ITEM-16 — Ingest/provenance hand-off seam.** Add a `jobs`-side trait seam (mirrors `seams.rs`
  sync/notifier no-op idiom) `AnalysisResultSink { fn ingest(job, outputs_dir, manifest) }` with a no-op default,
  wired at merge to P1 (catalog ingest) + P4 (run-node/edge record). Keeps P3 decoupled from P1/P4's concrete
  APIs while making the contract's tail real + testable.

### F. Settings / plumbing
- **ITEM-17 — `job_settings` extension.** Add `interactive_reserved_slots int NOT NULL DEFAULT 1` (CHECK
  `0..=max_concurrent_jobs`) to the singleton; extend `JobSettings`/`UpdateJobSettingsRequest` +
  the settings admin route (partial COALESCE update, mirrors the existing cap). Scheduler reads it at-use with a
  safe fallback (matches `max_concurrent`).
- **ITEM-18 — Analysis job create surface.** `POST /api/jobs` already exists; extend `create_job` to accept the
  analysis spec + `job_class`/`resource_class` (validated + clamped), so an analysis run is a first-class job.
  Keep the stub `job_type` path for the existing tests.

## Decisions
- **DEC-A (rootfs toolchain):** micromamba/conda-forge for the pinned scientific Python stack (self-contained,
  avoids llvmlite/BLAS source builds) over apt+pip. R stays r-base-core.
- **DEC-B (streaming reconciliation):** add `run_in_sandbox_spawn` returning a live `Child` + a lifecycle guard;
  the jobs executor (not the sandbox) drives log-drain/pid-sample/cancel — so one drive loop, one runner contract.
- **DEC-C (`ComputeBackend` above `JobRunner`):** `ComputeBackend` is the platform seam; `LocalBwrapBackend`
  wraps `SandboxJobRunner`; non-cpu-sandbox classes are typed-unavailable (seam open, not implemented).
- **DEC-D (fair-share approximation):** order by running-count-per-owner then FCFS; NOT true WFQ (deferred).
- **DEC-E (reserved interactive slots):** batch fills only up to `cap - interactive_reserved_slots`; interactive
  may use the full cap. Single pool, 1-box.
- **DEC-F (contract ownership split):** P3 owns execution + `inputs.json`/`/outputs`-manifest mechanics; P1 owns
  catalog ingest, P4 owns code-blob store + run-node recording; the `AnalysisResultSink` seam is the boundary.
- **DEC-G (workspace lifecycle):** the analysis path ingests `/outputs` BEFORE workspace cleanup (unlike the REST
  `run_analysis`, which cleans immediately).

## Risks / unknowns
- **Rootfs embed size (HIGH).** A scanpy/anndata/leiden/harmony env is ~1.5–2 GB; `build_helper/sandbox_rootfs.rs`
  bakes it via `include_bytes!` → a multi-GB binary + heavy link/memory + slow build. Mitigation to evaluate:
  aggressive squashfs zstd, micromamba `--strip`/no-tests, or reconsider embed-vs-cache for the *scientific*
  layer specifically (the minimal layer stays embedded). Squares with the memory note "worktree needs hub-seed
  copied" (large embedded assets are already a pain point).
- **Trait/shape mismatch (MED).** `run_in_sandbox` owns its child + timeout; carving out a spawn variant while
  keeping the REST path byte-identical + preserving cgroup/seccomp/workspace Drop-lifetime past the child is
  fiddly (ITEM-1/2). The `keepalive: Box<dyn Send>` guard is the mechanism; verify no fd/scope leak.
- **Network-blocked provisioning (MED, mitigated).** `--unshare-net` means the rootfs must be 100% baked at build
  time — any run-time pip/CRAN fetch fails silently. Good (already blocked) but constrains ITEM-9 to a complete
  manifest; leiden needs `python-igraph`+`leidenalg` C-extensions present.
- **bwrap cancel semantics (MED).** Confirm SIGTERM/SIGKILL on the bwrap parent pid reaps the `--as-pid-1` bash
  grandchild (pid-ns teardown) and the cgroup scope; add a Tier-4 cancel test (ITEM-5).
- **Fair-share SQL (LOW-MED).** The per-owner running-count claim under `FOR UPDATE SKIP LOCKED` at the 500 ms
  poll must stay correct under concurrent dispatch; window-function ordering + skip-locked interplay needs a test.
- **Ingest boundary timing (LOW).** ITEM-16's no-op default means outputs are produced but not ingested until
  P1/P4 merge; end-to-end value is gated on that merge (documented, expected).
- **desktop non-Linux (LOW).** sandbox is Linux-only (`run_analysis` 503 elsewhere); on macOS/Windows desktop the
  analysis runner is unavailable — job → `failed` with a clear reason. Acceptable per scope (seam open).
