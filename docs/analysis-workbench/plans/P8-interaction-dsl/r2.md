# Plan — Interaction & Selection layer: the cell-set predicate DSL, shared selection/brush/pick primitives, host evaluator, and selection-as-recipe

**One-line goal.** Build the connective tissue of §0.4.1 + §4.4: a single **shared selection/brush/pick primitive set** that both declarative `selectionActions` and code-owning interactive tools (annotation, gating) consume, backed by a **small, safe, typed cell-set predicate DSL** with **two agreeing evaluators** (client TS for instant preview, server Rust for the AI/MCP + reproduce path), where **every selection persists as a recipe** (predicate + pinned input hashes), never a materialized cell list. This is the one representation shared by the human lasso, the AI's `selection.setByPredicate`, and provenance.

## Grounding (verified in code, not assumed)

**live3 visualization** (`/data/pbya/ziee/tmp/visualization-wt/src-app/ui/src/modules/visualization/`) already has most of the *runtime* selection machinery — this workstream must **adopt + generalize it, not rebuild**:
- Coordination store `adapter/Coordination.store.ts` (`Stores.Coordination`, `defineStore` from `@ziee/framework/store-kit`): selection is `pointSelection: Uint32Array | null` (dense indices); pick is `highlight: number | null` + `HoverInfo {index,x,y}` (`viz-core/DeckScatterCanvas.tsx`). Setters `setSelection(cellId, indices)` / `setCellSelection(indices)` / `clearSelection` / `setHighlight`.
- Packed bitmask `IndexMask` (`Uint32Array[⌈N/32⌉]`, union/intersect/difference/toIndices) in `viz-core/data/selection.ts` — the DATA_STORAGE_REDESIGN §3.9 cell-set representation, already built.
- Geometry→cells: `selectInPolygon` / `selectInBox` (d3 `polygonContains` + KD-tree `PointIndex`) in `viz-core/data/selection.ts`; per-cell unproject in `grid/gridSelection.ts`; area types `RectArea`/`PolygonArea`/`CombineMode` in `viz-core/selection/SelectionController.ts`; spatial ROI in `spatial/roiSelect.ts`; matrix column-brush → `heatmap-matrix/matrixSelection.ts` `columnRangeToPointIndices`.
- **Gaps for this workstream:** there is **no `CellSet` type**, **no persistent brush-range object** (brush is transient-local; histogram has no brush at all), **no predicate/recipe concept**, and selection is confined to the viz package (not exposed as a workbench-api primitive). `switch(cell.kind)` (`viz-core/grid/CellView.tsx`) is a closed union — its refactor to a `registerViewKind` registry is a **separate (viz-adoption) workstream** this one depends on for view-kind exposure but does not own.

**Provenance** (`/data/pbya/ziee/tmp/study-admin-wt/`, `feat/provenance`) is **design-only, zero code** — but the recipe model is fully specified in `.lifecycle/provenance/DESIGN_CANDIDATES.md` §B1/§B3.1/DEC-GRAPH: recipe = `{predicate} + {content-hash of the input artifact}` (~1 KB, O(1) in N); the GUI-gesture→captured-params→exported-code table (lasso→`points_in_polygon(obsm['X_umap'],poly)`; rect gate→bounds; threshold→`{column,op,value}`; pick-clusters→`clustering_ref+labels`; freehand→explicit id-list); planned tables `provenance_runs/artifacts/edges/code_blobs`; manual selections recorded as run nodes (`job_type="selection.*"`) via an **interaction chokepoint** ("the Explorer's record-selection API") — that chokepoint is a deliverable of *this* workstream, consuming live8's `ProvenanceCapture` seam.

**Working store + catalog + typed-binary data API** = **greenfield, the Phase-0 critical path** (`BUILD_PLAN.md` §Phase 0 / DEC-FOUNDATION; the `JobRunner→sandbox::run_analysis` runner is a stub). The evaluators' column reads (`geneColumn`, `obs`, `clustering`) bind to this API's read surface.

## Hard dependencies & where this sits

This layer **cannot fully land before** its substrate, but its self-contained core (DSL schema + both evaluators + parity) can be built early against the data-API *contract* with a fixture backend. Ordered dependencies:
1. **Working store + data API read surface** (Phase 0) — `data.geneColumn/obs/clustering/embedding` → typed arrays. Blocks the evaluators' real backend.
2. **`@cyto/workbench-api` extraction** (Phase 1) — the home for `api.selection/brush/pick`, the `CellSet` type, and the DSL types.
3. **live3 Coordination adoption as the shell canvas** (Phase 2) — the backing store for the primitives.
4. **live8 provenance graph + `ProvenanceCapture` seam** (Phase 0c) — the sink for selection recipes.
5. **MCP-tools-generated-from-registry** (§0.4 framework) — so `selection.setByPredicate` (a command) auto-emits as a tool.

Recommend building in this order *within* the workstream: DSL schema → evaluators + parity (fixture backend) → primitives/Coordination adoption → geometry→predicate compile → recipe capture → MCP tool + vocab resource → cell-set-selector widget → selectionAction/interactive-tool wiring.

## Items

- **PI-1** · Canonical `CellSet` contract + selection/brush/pick primitives in `@cyto/workbench-api`. Define `CellSet` as the workbench-wide selection type (wrap the existing `IndexMask` + `Uint32Array` dense-index duality; do **not** invent a third representation). Expose `api.selection {current(): CellSet; set(s); setByPredicate(pred); onChange(cb): Disposable}`, `api.brush {current(): BrushRange|null; set; onChange}` (the **new** persistent brush object live3 lacks — `{axis|column, lo, hi}`), `api.pick {current(): number|null; onChange}` (adopt `highlight`). Back all three by `Stores.Coordination`; add a `brushRange` field + `setBrush` action to the Coordination store. *Tests:* T-1a unit — CellSet set-ops round-trip (mask↔indices) parity with `IndexMask`; T-1b unit — brush object set/read/onChange fan-out; T-1c unit — pick channel adopts `highlight` without regressing existing hover.
- **PI-2** · The cell-set predicate DSL — one canonical schema (TS + Rust). A bounded, typed JSON expression: **field refs** `{gene, layer?}` / `{col}` (obs/metadata-column) / `{clustering, categories[]}` / `{embeddingDim}`; **reductions** `median|mean|quantile(q)|mad|min|max` over a field; **comparisons** `gt|lt|gte|lte|eq|neq|between`; **boolean/set** `and|or|not`; **geometric** `pointInPolygon(embeddingRef, verts[])` / `inBox(dims,bounds)` (for lasso/gate compilation); **literals** + `idList` (freehand escape hatch). Author **one JSON-schema** as source of truth; generate the TS type and the Rust type from it (mirror the app's `emit_ts.rs` golden-parity discipline). *Tests:* T-2a — JSON-schema validates the §0.4.1 worked example `gt[{gene ABC},{reduce median of gene ABC}]` + each gesture row from the provenance table; T-2b — malformed predicates (unknown op, arity error, unbounded recursion depth) rejected; T-2c — TS/Rust type golden-parity test (schema→both must match committed).
- **PI-3** · Client (TS) evaluator. Evaluate a predicate against **resident** data-API typed arrays → a `CellSet` bitmask over the canonical cell axis; compute reductions in-process (O(n), the column is already fetched for coloring). NA/uncovered cells → false. Powers the widget's live count preview + instant selection. *Tests:* T-3a — median-of-one-gene worked example yields the correct bitmask on a fixture; T-3b — boolean/set composition; T-3c — reductions (median/quantile/mad) numeric correctness vs a reference; T-3d — uncovered-cell handling.
- **PI-4** · Server (Rust) host evaluator — the domain-neutral core capability. Reads the working store (gene column / obs / clustering) via the data-API read surface, computes reductions, applies ops → a bitmask (runtime `roaring`/`bitvec` u32 per DATA_STORAGE_REDESIGN §3.9). Authoritative for `selection.setByPredicate` (AI/MCP), reproduce, and headless re-eval. Typed error when a referenced gene/col/clustering doesn't exist (relayed to the AI). *Tests:* T-4a integration — evaluate each fixture predicate → bitmask; T-4b — missing-field typed error; T-4c — pinned-input reproducibility (same artifact hash → identical bitmask across calls).
- **PI-5** · TS↔Rust evaluator parity (golden). A fixture dataset + a corpus of predicates asserting **byte-identical bitmasks** from PI-3 and PI-4. This is the load-bearing guarantee that "the human's preview == the AI's selection == the reproduced cells." *Tests:* T-5 — parity corpus (≥20 predicates spanning every operator/reduction) both evaluators agree; a divergence fails CI.
- **PI-6** · Geometry→predicate compilation. A lasso/box/column-brush resolves on the client to a bitmask *for immediate display* (existing live3 path) **and** compiles to a DSL predicate for the recipe: polygon→`pointInPolygon(embeddingRef, verts)`, box gate→`inBox`, brush→`between{col}`, cluster-pick→`{clustering, categories}`, freehand→`idList`. Exactly the provenance §B1 gesture table. *Tests:* T-6a — each gesture compiles to the specified predicate shape; T-6b — round-trip: compiled predicate re-evaluated (PI-3) reproduces the originally-displayed cells (within polygon-boundary tolerance); T-6c — freehand falls back to `idList`.
- **PI-7** · Selection-as-recipe capture (the interaction chokepoint). One "record selection" API that, on any selection commit, writes a provenance **run node** (`job_type="selection.*"`) storing `{predicate + pinned input-artifact content-hashes}` via live8's `ProvenanceCapture` seam — never the materialized mask. Resolves which artifacts a predicate references → their catalog content-hashes for pinning. Emits study-scoped `sync`. *Tests:* T-7a integration — a lasso commit persists a recipe node with the polygon predicate + embedding hash, size O(1) not O(N); T-7b — re-evaluating the stored recipe on the pinned input reproduces the cells; T-7c — set-algebra selection stores operand refs + op, not a merged mask.
- **PI-8** · `selection.setByPredicate` command + MCP tool + DSL-vocabulary resource. Register `selection.setByPredicate(predicate)` and `selection.current` as **commands** (so §0.4's registry→MCP generation emits the tool/resource — no bespoke MCP code). setByPredicate → PI-4 evaluator → set shared selection (PI-1) → record recipe (PI-7). Publish the **DSL operator vocabulary + available-fields** (gene/col existence from the data schema) as an MCP **resource** the AI reads before emitting a predicate. Safety hint: `read-run` (selection is non-mutating; the separate `annotate.assign` is the gated mutation, per §0.4.1). *Tests:* T-8a — setByPredicate over MCP sets the selection + records provenance; T-8b — the vocab/fields resource lists operators + reports a missing gene; T-8c — the two `mcp.rs` edits present (auto-attach + is-builtin) so the model actually sees the tool.
- **PI-9** · `cell-set-selector` shared widget core (§4.3 Tier 3). The host-provided predicate-builder control with a **live cell-count preview** driven by the TS evaluator (PI-3) — the reusable DE-group / gate builder every extension references (`{widget: cell-set-selector}`) instead of re-coding. (Full form-engine integration belongs to the forms workstream; this delivers the DSL-building + preview core it plugs in.) *Tests:* T-9a — build a compound predicate (cluster ∧ metadata threshold) → correct live count; T-9b — the emitted predicate matches the DSL schema and round-trips through PI-3.
- **PI-10** · Wire `selectionActions` + interactive tools to the ONE shared selection. Both a declarative `SelectionActionContribution` (acts on `api.selection.current()`) and a code interactive tool (annotation panel reading `api.selection.onChange`) consume the *same* `Stores.Coordination` selection — no per-module selection model. Availability-gate actions on `when:"has-selection"`. This is the §4.4 anti-fragmentation guarantee. *Tests:* T-10a integration — a selectionAction and an interactive-tool panel both observe the same lasso selection; T-10b — assigning an annotation from a predicate-sourced selection produces an annotation artifact whose provenance references the selection recipe (PI-7), not a frozen mask.

## Decisions
- **DEC-A · Two evaluators, bound by a golden parity test (PI-5).** *Recommend yes.* The doc demands both in-process client speed (§0.4.1 "already resident") *and* an authoritative server path for AI/MCP/reproduce. A single location can't serve both without a per-lasso round trip (client) or losing headless reproduce (server-only). Parity is the price; PI-5 pays it.
- **DEC-B · `CellSet` = the existing `IndexMask`/`Uint32Array` duality, promoted — not a new type.** Server mirror = `roaring`/`bitvec` u32 (DATA_STORAGE_REDESIGN §3.9).
- **DEC-C · Predicate schema is the single source; TS + Rust are generated** with an `emit_ts`-style golden test. Prevents TS/Rust drift that would break DEC-A parity.
- **DEC-D · Selection is `read-run` (non-mutating); the mutation is the separate `annotate.assign`.** Keeps the AI's selecting hand ungated while the write stays permission-gated (§0.5 study role + approval).
- **DEC-E · Recipe, never materialized mask, is the persisted form** (provenance DEC-GRAPH); freehand `idList` is the sole exception.
- **DEC-F · Brush becomes a first-class persistent Coordination field** (live3 has none) — needed so a QC/gate brush is linkable + recipe-able, not transient-local.
- **DEC-G · Evaluator is domain-neutral** — operates on generic per-cell columns from the data API (gene/obs/clustering), matching DATA_MODEL's "single-cell is not privileged."

## Risks
- **Substrate not built** — the real backend for PI-4/PI-7 (working store data API, provenance tables/seam) is greenfield/design-only. Mitigate: build PI-2/3/4/5 against the data-API *contract* with a fixture backend; land PI-7/8 when live8 provenance + Phase-0 data API exist. Sequence, don't block.
- **Polygon boundary determinism** across TS (d3 `polygonContains`) and Rust — a point exactly on an edge could diverge and break PI-5/T-6b. Decide a canonical inclusion rule in the DSL spec (PI-2) and test it explicitly.
- **Pinned-input-hash resolution** depends on the catalog exposing per-artifact content hashes; if the catalog lands without stable content-addressing, PI-7 reproducibility is unverifiable. Flag as a catalog requirement.
- **Coordination store is inside the viz package** (`@cytoanalyst/ui`), not yet in `@cyto/workbench-api`; PI-1 depends on the Phase-1/Phase-2 extraction+adoption landing first.
- **View-kind exposure** (`view.set`, brush-on-histogram) needs the `switch(cell.kind)`→`registerViewKind` refactor owned by the viz-adoption workstream — coordinate; the histogram brush (PI-1 `api.brush`) has no live3 backing today.
