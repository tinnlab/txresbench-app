# P8 — interaction-dsl (shared selection/brush/pick + cell-set predicate DSL + host evaluator + selection-as-recipe) — r3

Scope: DESKTOP + SINGLE-BOX SERVER ONLY. Independent blind round-3 plan.

## Decisions

### KEY DECISION — TWO evaluators (client TS **and** server Rust), bound by a golden parity test. NOT client-only.
**Position: build both, gate them with a byte-identical golden parity corpus.** Rejecting client-only.

Why not client-only:
- `selection.setByPredicate` is a **declared MCP tool** (§0.4.1/§0.4.2). MCP tools execute in the **Rust
  server** (loopback JSON-RPC, the app's native built-in-MCP model) and are invoked **headlessly by the LLM** —
  frequently when no human/browser is attached (§4.1.1: the AI's jobs default to `normal`/`batch` unless a human
  is actively waiting). There is **no client to delegate the evaluation to**. A client-only evaluator makes the
  headline AI capability (§0.4 "selection-as-recipe = the shared AI/human/provenance representation") impossible.
- **Headless reproduce** (§0.6): the selection recipe (predicate + pinned input hash) is re-evaluated to
  **regenerate the identical cells** during reproduce-script / methods-text export and the in-sandbox re-run
  **verification badge** — all headless, server-side, no browser. Requires a server evaluator.

Why not server-only:
- The **cell-set-selector widget's live cell-count** and the **lasso preview** need instant feedback over
  columns **already resident client-side for coloring** (§0.4.1 "likely already fetched"). A server round-trip
  per keystroke/drag is too slow. §0.4.1 explicitly says the median "evaluates **in-process (host/client)**" and
  names "**the host's** predicate evaluator" — the design contemplates BOTH.

Cost control: the DSL is **small and bounded** (a fixed operator vocabulary, no arbitrary code), so two
implementations of one bounded spec is a tractable, closed duplication — like a serializer with a golden test,
not an open-ended reimplementation. A shared JSON **golden parity corpus** (predicate × fixture columns →
expected bitmask words) is loaded by BOTH the TS and Rust test suites and asserted **byte-identical**; any drift
fails both. This is the same discipline as the ziee host's `emit_ts.rs` `types_ts_parity` golden test.

### Polygon-boundary determinism (mandatory because there are two evaluators)
A human lasso is geometric, so `inPolygon` is a DSL operator both evaluators must resolve identically:
- **Coordinate space:** the lasso→predicate compiler unprojects the screen polygon to **embedding-space f32
  vertices** (reuse live3 `unprojectInCell`) and stores THOSE in the recipe — never screen coords (screen
  depends on zoom/DPR → non-reproducible). Reproduce runs `inPolygon` over the **pinned embedding artifact**'s
  exact stored f32 coords.
- **One canonical algorithm:** port live3's existing `d3-polygon.polygonContains` ray-crossing **verbatim** into
  Rust — same vertex iteration order, same half-open crossing rule (`(yi>y) !== (yj>y)` + the x-side compare),
  same arithmetic order. TS keeps using d3-polygon; Rust mirrors it exactly.
- **Quantization backstop:** the recipe stores polygon vertices **quantized to the artifact's stored precision**;
  both sides quantize candidate coords + polygon identically before the crossing test → eliminates cross-language
  last-ULP divergence on on-edge / on-vertex / collinear points.
- **Prefilter must not change results:** the KD-tree bbox candidate narrowing (live3 `pointIndex.range`) is a
  perf optimization only; a parity invariant asserts `prefiltered == full-scan` on the corpus. Golden corpus
  includes on-edge, on-vertex, collinear, zero-area, and self-touching polygons.

### Other decisions
- **DEC-P8-A:** DSL wire form = **JSON AST** (not a string grammar). Directly = the MCP tool's JSON-schema input
  (§0.4.2 "an MCP tool IS name+description+JSON-schema input"), directly `serde`-deserializable in Rust, directly
  what the cell-set widget builds. No parser to write/keep-in-sync.
- **DEC-P8-B:** `CellSet` = live3 `IndexMask` (materialized, render hot path) **+ an optional source recipe**
  (predicate + pinned hashes). The mask drives rendering; the recipe is what persists to provenance. Never
  persist the materialized set (§0.6 "store as RECIPE … never a materialized cell set").
- **DEC-P8-C:** heavy computed features are **NOT** in the DSL (§0.4.1) — a 500-gene signature is a sandboxed
  analysis producing a `metadata-column` artifact; the predicate references that column (`{col: "ABC_sig"}`).
  The DSL stays a fast, safe filter over resident per-cell values. Reductions are limited to cheap O(n)
  (median/mean/quantile/mad over one column).
- **DEC-P8-D:** the shared primitives live in the **viz framework** (`@ziee/framework` viz-core, live3), promoted
  as the `api.selection`/`api.brush`/`api.pick` surface of `@cyto/workbench-api`; they are NOT re-invented in
  the analysis module. Coordination store is the single selection owner.
- **DEC-P8-E:** `select` is **read-safe** (only reads columns, only sets selection) → `safety: read-run`,
  auto-approved per §0.4 policy. The **assign/mutating** action is a separate, gated tool (out of P8 scope).

## Items

- **ITEM-1**: **Cell-set predicate DSL — canonical AST + JSON-schema (single source of truth).** Bounded, typed
  expression language over per-cell values. Operands: `{gene, layer?}`, `{col}`/`{obs}`, `{qc}`, literal;
  reductions `{reduce: "median"|"mean"|"quantile"|"mad", of, q?}`; comparisons `gt|gte|lt|lte|eq|neq`; boolean
  `and|or|not`; set ops `union|intersect|difference`; categorical membership `{in:[...]}`; geometric
  `{inPolygon:{coords:<embedding-ref>, polygon:[[x,y],…]}}`. Versioned (`dslVersion`). Depth + node-count caps.
  Emit a JSON-schema that (a) validates AI/client input, (b) IS the `setByPredicate` MCP tool input schema.
- **ITEM-2**: **Client TS evaluator** `evalPredicate(ast, dataCtx): IndexMask` in viz-core, over resident typed
  arrays from the data API, reusing live3 `IndexMask` + `selectInPolygon`. Cheap in-process reductions. Powers
  the live cell-count preview + lasso resolution. Returns typed errors (gene/col-not-found, type-mismatch), not
  opaque throws.
- **ITEM-3**: **Server Rust evaluator** — new host module `modules/predicate/` (`ast.rs` serde types mirroring
  ITEM-1, `eval.rs`, `reduce.rs`, `geometry.rs`). Reads kind-typed artifact columns (gene column / obs column /
  embedding coords) via the Phase-0 working-store data API → a packed-`u32` `BitMask` with the **same word
  layout** as `IndexMask`. Same reductions/comparisons/geometry/caps as TS.
- **ITEM-4**: **Golden parity harness.** Shared corpus dir of `{predicate, fixtureColumns, expectedMaskWords[]}`
  JSON cases; a Rust test (`tests/predicate/parity_test.rs`) and a TS test (`evalPredicate.parity.test.ts`) load
  the SAME files and assert byte-identical bitmask words. Covers reductions, boolean/set ops, categorical
  membership, empty/all, NA/NaN handling, and the ITEM-5 polygon boundary cases. Corpus generator + a `just`/npm
  target so both suites run it.
- **ITEM-5**: **`inPolygon` operator + polygon-boundary determinism.** (a) lasso→predicate compiler
  (screen→embedding-space f32, quantized, reusing `unprojectInCell`); (b) canonical ray-crossing ported verbatim
  from `d3-polygon.polygonContains` into Rust; (c) identical quantization both sides; (d) prefilter==full-scan
  invariant. Boundary/vertex/collinear/degenerate golden cases feed ITEM-4.
- **ITEM-6**: **Shared `api.selection` primitive.** Workbench-api surface `current(): CellSet`, `set(mask)`,
  `setByPredicate(ast)` (client: eval→set; server tool calls the same via ITEM-10), `onChange(cb)`. Backed by
  live3 Coordination store; extend its `pointSelection` to carry BOTH the materialized mask AND the source
  recipe (DEC-P8-B). `CellSet = IndexMask + optional recipe`.
- **ITEM-7**: **Shared `api.brush` primitive.** A brushed range on a numeric axis/column/histogram that resolves
  to a DSL predicate (`and(gte(col,min), lte(col,max))`) — generalizing live3's heatmap-only column brush
  (`matrixSelection.ts`) into a canvas/axis brush wired to Coordination + the DSL. A QC-threshold brush IS a
  predicate → same recipe/provenance path.
- **ITEM-8**: **Shared `api.pick` primitive.** Clicked/hovered single cell. Reuse live3 GPU-pick
  `HoverInfo{index}`; ADD a click-to-pick handler (live3 has hover only). Exposes current pick + `onPick`; used
  by trajectory-start/end style tools.
- **ITEM-9**: **Selection-as-recipe persistence.** Store predicate AST + pinned input hash(es) — content hashes
  of the referenced artifacts (gene layer / obs column / embedding) resolved from the catalog — as the
  provenance selection recipe; never the materialized list. Define the recipe payload shape + hash-pinning here;
  the run-node record is coordinated with the provenance workstream (currently design-only — see Dependencies).
- **ITEM-10**: **`selection.setByPredicate` host surface (→ MCP tool).** A REST/loopback handler that
  JSON-schema-validates the DSL (ITEM-1), runs the SERVER evaluator (ITEM-3) over the study's artifacts, sets the
  shared selection (sync-emit to the client), stores the recipe (ITEM-9). Study-role gated; `read-run`
  auto-approved. P8 owns the handler+evaluator; P9 GENERATES the MCP tool + the **DSL-vocabulary resource**
  (operator list + available genes/columns from the catalog) the AI reads.
- **ITEM-11**: **Headless reproduce path.** Re-evaluate a stored recipe server-side over the pinned artifacts
  (ITEM-3) to (a) verify the regenerated bitmask matches (reproducibility-badge input), (b) drive the
  methods-text templater ("selected cells where lognorm(ABC) > median"). Wire into the provenance reproduce/export
  seam (Phase 4).
- **ITEM-12**: **Typed error contract + caps.** Shared error vocabulary (gene/col not found, wrong type,
  unbounded/oversized expression, result-cardinality cap) returned identically by BOTH evaluators; AI relays it,
  human sees it inline. Expression depth/size + result caps enforced identically (part of the parity contract).

- **@cyto/workbench-api extraction (Phase 1)** — the `api.selection/brush/pick` façade lands there (ITEM-6/7/8).

## Sequencing

1. ITEM-1 (DSL AST + JSON-schema) — the contract everything derives from.
2. In parallel once ITEM-1 lands: ITEM-2 (client eval) + ITEM-3 (server eval) + ITEM-5 (inPolygon both sides) +
   ITEM-12 (errors/caps) — implemented against the same spec.
3. ITEM-4 (golden parity harness) — continuously, as ITEM-2/3/5 grow; it is the convergence gate for the two
   evaluators. Polygon cases (ITEM-5) added here.
4. ITEM-6/7/8 (selection/brush/pick primitives) — atop live3 + the client evaluator; ITEM-7 brush→predicate uses
   ITEM-1/2.
5. ITEM-9 (recipe persistence) + ITEM-10 (setByPredicate host surface) — need ITEM-3 + the catalog hash pinning.
6. ITEM-11 (headless reproduce) — last; needs ITEM-9 + the provenance export seam (Phase 4).

Blocked-until-foundation: ITEM-3/9/10/11 wait on the Phase-0 data API + catalog. ITEM-1/5 (spec + geometry) and
the client ITEM-2 can start against the FE data client / fixtures before the server foundation is complete.

## Risks

- **Two-evaluator drift** — mitigated by the golden parity harness (ITEM-4) as a hard gate; DSL kept deliberately
  small (DEC-P8-C) so the duplicated surface stays closed.
- **Cross-language f32 polygon divergence** on boundary/vertex/collinear points — mitigated by the verbatim
  d3-polygon port + quantization backstop (ITEM-5); explicit boundary golden cases.
- **Foundation not built** — the Phase-0 data API/catalog is the critical path and currently design-only; the
  server evaluator can't be integration-tested until it exists. Mitigation: build ITEM-1/2/3/5 against fixtures +
  the parity corpus first (unit-level, foundation-independent), integrate when Phase 0 lands.
- **Recipe/run-node ownership** overlaps the provenance workstream (design-only) — risk of two definitions.
  Mitigation: P8 owns the recipe PAYLOAD + hash-pinning; the run-node table is a single shared build with
  provenance; coordinate before migrating.
- **Coordination store selection form** is `Uint32Array` (materialized), not recipe-aware — ITEM-6 must extend it
  without breaking live3's render hot path (keep the mask; add the recipe alongside).
- **Screen-vs-embedding coord confusion** — a lasso stored in screen space is non-reproducible; the compiler MUST
  emit embedding-space coords (ITEM-5). Enforce via a reproduce round-trip test.
