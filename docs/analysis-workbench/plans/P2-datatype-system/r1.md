# P2 — Datatype System (round 1, blind)

Scope: the OPEN datatype registry (extension-contributed) + the subtyping lattice + the typed-artifact model
(`dataset ≡ analysis-output ≡ typed artifact`) + the generic storage-layout descriptors (chunked-dense /
chunked-sparse / columnar-table / chunked-1d) + the viewers-keyed-by-datatype dispatch + type-match gating.
Generalizes the closed single-cell `DataKind`/`ResultKind` enum into an open registry. **Desktop + 1-box,
local-FS.** Seed the lattice with `matrix` (abstract supertype) + `single-cell/anndata` (extends matrix) +
`clustering`, leave the seam OPEN (bulk/spatial/variant/structure are later registry entries).

This part owns the **type system**; P1 (data-foundation) owns the **physical** working store, the
`analysis_results`/`artifacts` catalog table, the blob store, byte-range serving, and the layout **slicer
implementation**. P2 supplies the *type descriptors* (datatype metadata, subtyping edges, storage-layout enum,
selector→index mapping) that P1's slicer and catalog consume. The seam between them is ITEM-1/ITEM-9 below.

## Items

- **P2-1 — `Datatype` descriptor + `DATATYPES` distributed-slice registry (backend).** A `Datatype` struct
  (`id`, `extends: Option<&'static str>`, `title`, `description`, `capabilities: &[&str]`, `storage:
  StorageLayoutSpec`, `viewers: &[&str]`) collected into a `linkme` `#[distributed_slice] static DATATYPES:
  [DatatypeEntry]` exactly mirroring `study/core/extension/registry.rs`'s `STUDY_EXTENSIONS` pattern (a `Copy`
  entry `static` per datatype, no central edit, no `submit!`). A `DatatypeRegistry` folds every entry at
  startup, published as a process-wide `OnceCell<Arc<DatatypeRegistry>>` (same shape as
  `set_global_registry`/`get_global_registry`). This is the open replacement for the closed
  `expression|embedding|clustering|…` enum.

- **P2-2 — The subtyping lattice + resolver.** Build a DAG from the `extends` edges at registry init;
  validate it (no cycles, every `extends` target resolves, single implicit root `data`). Provide the core
  query the whole platform gates on: `is_a(subtype_id, supertype_id) -> bool` (walk `extends` chain) +
  `ancestors(id) -> Vec<&str>` + `descendants(id) -> Vec<&str>`. Compatibility = `is_a`. This is the Galaxy
  datatype-lattice lesson: an analysis `accepts: matrix` matches `single-cell/anndata` because
  `single-cell/anndata is_a matrix`.

- **P2-3 — Seed datatypes (the 2-3 + supertypes) as `#[distributed_slice(DATATYPES)]` statics.** Register:
  `data` (implicit abstract root), `tabular` (extends `data`, abstract), `matrix` (extends `tabular`,
  abstract supertype), `single-cell/anndata` (extends `matrix`, concrete — `capabilities:
  ['sliceable','has-obs','has-var']`, `storage: chunked-sparse`), `clustering` (extends `data`, concrete —
  `capabilities: ['categorical','obs-aligned']`, `storage: columnar-table` / codes+categories). Each carries
  its `viewers` id list. This proves the lattice end-to-end and is the exact set the embedding/clustering
  modules (P11) need, with the seam open for bulk/spatial/variant/structure.

- **P2-4 — Typed-artifact model (`Artifact` = typed node: storage-ref + datatype + provenance).** Define the
  artifact as a node keyed by `(study_id, artifact_id)` carrying `datatype_id`, `storage_ref` (a prefix/blob
  handle — a multi-file artifact presents as ONE node, DATA_MODEL §"one artifact may be many files"),
  `shape`, `covered_cells`, `produced_by` (`upload` | `pipeline` | `<analysis_id>`), `provenance`. **A dataset
  = a source artifact** (`produced_by: upload/pipeline`); **an analysis output = a derived artifact**. P2 owns
  the *typed facet* + the `datatype_id` FK-to-registry column; P1 owns the physical row storage + blob. Ship
  the Rust `Artifact` type, its `datatype()` resolver (looks the id up in the registry → the `Datatype`
  descriptor), and `validate(&Artifact) -> Result` dispatching to the datatype's schema/shape check.

- **P2-5 — Storage-layout descriptors (domain-neutral, the Tier-2 seam).** A `StorageLayout` enum —
  `ChunkedDense`, `ChunkedSparse { orientation: Csc|Csr }`, `ColumnarTable`, `Chunked1d` — plus a
  `SelectorMapping` that maps a datatype's *semantic* selectors (gene→column, cell→row, locus→range,
  residue→index) to layout indices. A datatype DECLARES which layout its artifacts use + the selector map;
  the host slices the LAYOUT, never the domain. `single-cell/anndata` → `ChunkedSparse{Csc}` +
  `{gene→column, cell→row}`; `clustering` → `ColumnarTable`/codes+categories. This is the descriptor P1's
  generic slicer keys on; single-cell is one consumer of the sparse layout, not a privileged tier.

- **P2-6 — Type-match gating API (the `accepts`/`produces` resolver).** A `TypeSelector` (`{ type: String,
  subtypes_of: bool, multiple: bool, required: bool }`) + `matches(selector, artifact_datatype) -> bool`
  (= `is_a` when `subtypes_of`, else exact-id). Expose `available_for(artifact) -> Vec<analysis_id>` and
  `compatible_artifacts(selector, &[Artifact]) -> Vec<&Artifact>` — the SAME wiring that (a) gates analysis
  availability, (b) generates the artifact-ref picker (PLATFORM §4.3 Tier-2), (c) lets the AI planner chain
  compatible tools. **One declaration does two jobs** (gate + picker). This is the code P5/P6/P11 consume; P2
  ships the pure resolver + tests, the analysis-descriptor side is P5.

- **P2-7 — Viewers-keyed-by-datatype dispatch (registry + resolver).** A `ViewerRegistry` mapping
  `datatype_id → [viewer_id]`, resolved *up the lattice* (`viewersFor(id)` = viewers registered for `id` OR
  any ancestor, so a `matrix`-family viewer applies to `single-cell/anndata`). This generalizes the deck.gl
  view-kind registry (P7) into ONE viewer family (matrix-like) among many; a genome/structure/network viewer
  is a different family keyed on its own datatype. P2 owns the *dispatch contract* (which viewer families a
  datatype offers); P7 owns the deck.gl renderer impls. Backend surfaces the mapping via the datatype
  descriptor; FE mirror (P2-10) does the runtime dispatch.

- **P2-8 — Catalog schema: replace the closed `datasets` table's implicit kind with `datatype_id`.** A
  migration adding the typed-artifact columns to the working-store catalog (co-designed with P1's
  `analysis_results`/`artifacts` table): `datatype_id text NOT NULL` (a string FK to the code registry — NOT
  a DB enum, so a new datatype needs no migration), `storage_layout text`, `storage_ref text`, `covered_cells
  jsonb`, `produced_by text`, plus a CHECK-free design (validity enforced at write against the registry, not
  Postgres). Evolve the current `datasets` stub (`src/modules/dataset/migrations/…`) toward this or supersede
  it. **Datatype ids live in code, not an enum column** — this is what makes the registry open.

- **P2-9 — Registry ↔ P1 catalog/slicer integration seam.** Wire the datatype descriptor into P1's write path
  (`writeResult(datatype, artifact)` validates against the datatype schema + records `datatype_id` +
  `storage_layout` in the catalog) and P1's read/slice path (the generic slicer reads `storage_layout` +
  `SelectorMapping` from the registry to know how to slice). P2 exposes `registry.get(datatype_id) ->
  &Datatype`; P1 calls it. Defines the exact function signatures both parts agree on.

- **P2-10 — FE datatype mirror + viewer dispatch (`@txresbench/workbench-api` / `core/workbench`).** A TS `Datatype`
  interface (mirrors DATA_MODEL's sketch: `id`, `extends?`, `schema`, `storage`, `viewers`, `capabilities?`)
  + a client-side `DatatypeRegistry` with `isA(sub, sup)` + `viewersFor(id)` (lattice-walking) + the
  type-match `matches(selector, datatype)`. The registry is populated from a backend endpoint (P2-11) at
  boot. The canvas dispatches **viewers keyed by datatype** through this (`viewersFor(artifact.datatype)` →
  pick a viewer). Generated-or-hand-authored to stay in sync with the backend registry.

- **P2-11 — REST: expose the registry + type-match to the FE.** `GET /api/datatypes` (the full lattice:
  every datatype's id/extends/capabilities/storage/viewers — so the FE builds its mirror + the picker
  filters) and `GET /api/studies/{s}/artifacts?compatible_with=<selector>` (server-side `compatible_artifacts`
  for the Tier-2 picker). aide-documented (OpenAPI → `emit_ts` → `types.ts`), gated by the study read
  permission. The `/datatypes` list is study-independent (registry is process-global) but served behind auth.

- **P2-12 — Capabilities vocabulary + `validate` dispatch.** A small open string set (`sliceable`, `has-obs`,
  `has-var`, `categorical`, `genomic-coords`, `obs-aligned`) an artifact/datatype advertises, consumed by
  gating/viewer/DSL code (e.g. the cell-set DSL needs `has-obs`). Each datatype ships a `validate(&Artifact)`
  (shape/schema check) invoked on ingest (P2-4/P2-9); seed impls for the 3 concrete types.

- **P2-13 — Tests (unit + integration).** Unit: lattice `is_a`/ancestors/descendants + cycle/dangling-edge
  rejection; `matches` exact-vs-subtype; `viewersFor` lattice-walk; empty-registry no-op; seed datatypes
  resolve. Integration: `GET /api/datatypes` returns the seeded lattice; `compatible_with=matrix` selects a
  `single-cell/anndata` artifact but not a `clustering` one; write-path validation rejects a shape mismatch.
  FE: `DatatypeRegistry.isA`/`viewersFor` parity with backend.

## Decisions

- **Datatype ids are code-registered strings, NOT a Postgres enum.** The catalog stores `datatype_id text`;
  validity is enforced at write against the code registry. This is the single decision that keeps the registry
  OPEN (a new datatype = a `#[distributed_slice(DATATYPES)]` static, zero migration). Matches Galaxy's
  code-registered datatype classes.
- **`linkme` distributed slice (not a runtime `register()` call) for built-in datatypes** — identical to
  `STUDY_EXTENSIONS`/`MODULE_ENTRIES`, so a datatype self-registers at link time with no central edit.
  External (manifest-loaded) datatypes register at runtime via P5's loader into the same `DatatypeRegistry`.
- **Compatibility = subtype `is_a`, evaluated over `extends` edges** (Galaxy lesson). An analysis
  `accepts:{type: matrix, subtypes_of:true}` matches any `is_a matrix`. Exact-match when `subtypes_of:false`.
- **Abstract vs concrete datatypes.** `data`/`tabular`/`matrix` are ABSTRACT (no artifact is ever *directly*
  of type `matrix`; they exist only as supertypes for gating). `single-cell/anndata`/`clustering` are
  CONCRETE. Add an `abstract: bool` on `Datatype`; validation forbids an artifact whose `datatype_id` is
  abstract.
- **Storage layout is a domain-neutral descriptor keyed by the datatype, and the *fast path lives on the
  layout, never the domain*** (DATA_MODEL Tier-2). `single-cell/anndata` gets fast gene-column slicing because
  it declares `ChunkedSparse{Csc}` + `{gene→column}`, exactly like any future dense/1-D datatype — no
  single-cell privilege.
- **Local-FS storage for desktop+1-box.** `storage_ref` is a filesystem prefix under the study dir (Zarr
  directory / Parquet file / HDF5 file); the served-format decision (Zarr vs HDF5 vs kerchunk) is P1's, P2
  only records the *layout*. Object storage (MinIO/S3) is a later P1 swap behind the same `storage_ref`.
- **One artifact = one node even when many physical files** (Zarr chunk dir, `.bam`+`.bai`): `storage_ref` is
  a prefix/manifest; the datatype's reader assembles. N different-typed outputs of one run = N artifacts.
- **Viewer dispatch resolves UP the lattice** — a viewer registered for a supertype applies to all subtypes,
  so a matrix-family scatter renders `single-cell/anndata` without per-type wiring. P2 owns the mapping; the
  renderer is P7.
- **`Datatype.viewers` names viewer IDS, not components** — decoupling the type system (P2) from the render
  impls (P7); a viewer id resolves in P7's/P10-FE's viewer registry.
- **P2 vs P1 boundary is the type-descriptor line:** P2 = *what a thing IS* (datatype, subtyping, layout
  descriptor, selector map, capabilities, validate); P1 = *where the bytes are and how they're sliced/served*
  (blob store, catalog rows, byte-range endpoint, the slicer that READS P2's layout descriptor).

## Risks/unknowns

- **P1/P2 catalog-table ownership overlap (highest).** Both parts want to define the artifact/catalog row.
  Mitigation: ONE shared migration co-authored at P2-8; P2 owns the typed columns (`datatype_id`,
  `storage_layout`, `covered_cells`, `produced_by`), P1 owns the physical/index columns (`storage_ref`,
  `shape`, `run_id`, `job_file`, checksums). Must reconcile against P1 r1 before FINAL.
- **`datatype_id` as a code-string FK with no DB constraint** means a stale catalog row can reference a
  datatype no longer in the registry (e.g. an extension uninstalled). Need a boot-time reconcile / a "orphan
  datatype" degraded state (mirror the `memory_admin_settings.enabled` fail-soft pattern). Unknown: reject vs
  quarantine.
- **Abstract-vs-concrete + multiple-inheritance.** DATA_MODEL only shows single `extends`; if a real datatype
  ever needs two supertypes (e.g. `spatial/visium is_a matrix AND is_a image`) the single-parent chain
  breaks. Decision for r1: single `extends` (a chain, not a DAG-with-joins); flag multiple-inheritance as a
  future lattice generalization.
- **Selector→index mapping generality.** The 4 layouts + `{gene→column, cell→row, locus→range, residue→index}`
  cover the seeded + near-future types, but a novel datatype's selectors may not map to any layout (→ Tier-1
  client-decode or Tier-3 precompute, DATA_MODEL). P2 must not over-fit the mapping to single-cell; keep it an
  open `HashMap<semantic_selector, LayoutIndexRef>`.
- **FE/backend registry drift.** The TS `DatatypeRegistry` mirror (P2-10) must stay in sync with the Rust
  `DATATYPES`. Mitigation: FE populates from `GET /api/datatypes` at boot (single source = backend), not a
  hand-copied TS list; only the `Datatype` *interface* is duplicated.
- **`@txresbench/workbench-api` package doesn't exist yet** (P5). P2-10's `datatype.ts` may need a temporary home in
  `core/workbench` until P5 lands the package; note as a P5 dependency.
- **`clustering`'s place in the lattice.** It's an obs-aligned categorical, not a `matrix` — modeled as
  `extends data` with `capabilities:['categorical','obs-aligned']` + `ColumnarTable` layout (codes+
  categories). Confirm this against how P11's clustering module + P7's color-by consume it.
- **Existing `dataset` module churn.** Superseding the `datasets` stub table/model risks touching the
  `dataset/study_extension` (the study-cascade proof). Keep the study-extension seam; only reframe the data
  model underneath it.
