# P2 — Datatype System (r2)

Scope (per PLANNING_INDEX): the **open datatype registry** (Galaxy-model: dataset ≡ analysis-output ≡ typed
artifact) + **subtyping lattice** + **artifact model** + **storage layouts keyed on LAYOUT not domain**
(dense/sparse/columnar/1d — single-cell is NOT privileged) + **viewers-per-datatype dispatch**. Datatypes are
self-registering extensions. Desktop + single-box only; seams open, local arm only.

Grounded in: `DATA_MODEL.md` (authoritative), `PLATFORM_ARCHITECTURE.md §1/§4.2/§5.5`,
`docs/DATA_STORAGE_REDESIGN.md` (the single-cell layout being generalized), and the actual txr code
(`modules/dataset`, `modules/study`, `sdk/crates/txresbench-file`, live3 `viz-core/grid`).

## Items

- **ITEM-1**: `Datatype` descriptor + trait + self-registering registry. New `modules/datatype/`. A
  `Datatype` descriptor `{ id, extends: Option<String>, schema: JsonSchema, storage: StorageSpec,
  layout: LayoutKind, capabilities: Vec<String>, viewers: Vec<ViewerRef>, ingest: Option<IngestSpec>,
  converters: Vec<ConverterRef> }` + a `validate(ArtifactRef)->Result` code hook. Built-ins self-register via
  `#[distributed_slice(DATATYPES)]` — a direct mirror of `dataset/study_extension/extension.rs`'s
  `#[distributed_slice(STUDY_EXTENSIONS)]` and `MODULE_ENTRIES`. `DatatypeEntry { id, extends, constructor }`
  mirrors `StudyExtensionEntry`.
- **ITEM-2**: Subtyping lattice. Build the type lattice from `extends` edges at boot into an in-memory
  `DatatypeRegistry`: transitive `is_a(sub, super)`, `supertypes(id)` walk, cycle/orphan/duplicate-id
  validation (fail boot with a clear error). This is the compatibility engine — the whole "tools reused across
  data types" property is `is_a`.
- **ITEM-3**: Type-match resolver (the gating primitive). `matches(artifact_datatype, TypeSelector{ type,
  subtypesOf })` and `available_for(artifact) -> Vec<contribution_id>` over any registry keyed by
  `accepts: TypeSelector[]`. Generalizes the closed `requires: DataKind[]` / `produces` gating (PLATFORM_ARCH
  §1.2) to typed `accepts`/`produces` with subtyping. Consumed by P3/P5/P6 for analysis availability + form
  pickers.
- **ITEM-4**: Artifact model + `artifacts` table. One node = one typed artifact `{ id, study_id, datatype_id,
  storage_ref (prefix), layout, content_hash, shape/metadata JSONB, source: bool, produced_by_run_id:
  Option<Uuid>, covered_axes JSONB, created_at }`. Dataset = **source artifact** (`source=true`,
  `produced_by_run_id=NULL`); analysis output = **derived artifact**. Replaces the `dataset`/`analysis_results`
  split with one uniform catalog (DATA_MODEL "dataset ≡ analysis-output ≡ typed artifact").
- **ITEM-5**: Multi-file artifact (one artifact = N physical files, presents as ONE typed thing). `storage_ref`
  is a **prefix/manifest**; the datatype declares a `FileLayout { Single | Prefix | Manifest(files[]) }`; the
  reader assembles (Zarr dir, BAM+bai, mtx+barcodes+features). Content identity = **merkle/manifest hash over
  the file set** → one `content_hash` per artifact regardless of file count.
- **ITEM-6**: Multi-output run ingest (one run → N typed artifacts; fan-out). The `produces` manifest maps
  `outputs/*` paths → typed artifacts (`{ id, type, from }`, DATA_MODEL §"One job → many outputs"); P2 ingests
  each declared output as its own artifact row sharing `produced_by_run_id`. Undeclared files (logs/temp) are
  NOT promoted (captured as run metadata by P4). **produce-atomically / consume-individually**: downstream
  binds one specific typed output, never "the job".
- **ITEM-7**: Storage-layout abstraction keyed on LAYOUT, not domain. `LayoutKind { ChunkedDense, ChunkedSparse
  { orient: CSC|CSR }, ColumnarTable, Chunked1d }` + a `SelectorMap` mapping a datatype's **semantic** selectors
  (gene→column, cell→row, locus→range, residue→index) to layout indices. A datatype **declares which layout its
  artifacts use**; the host slices the *layout*. Single-cell expression = `ChunkedSparse(CSC)` — one consumer
  of the sparse layout, NOT a special tier (corrects DATA_STORAGE_REDESIGN's HDF5-CSC-as-THE-format).
- **ITEM-8**: Layout-keyed slicer seam (Tier-2 fast path). `trait LayoutSlicer { fn slice(layout, selector) ->
  TypedBinary }`, domain-neutral, one impl per `LayoutKind`. Host slices the layout, never "a single-cell
  matrix". Near-term: implement **sparse (gene-column) + dense (column)** slicers (the interactive hot path);
  columnar via DuckDB/Polars server-side or client DuckDB-WASM; 1d deferred behind the seam. P1 provides the
  physical range endpoint this reads from.
- **ITEM-9**: Tiered data-access routing. Per artifact, resolve to **Tier-1** (authed byte/Range + client
  decode — the DEFAULT, zero host format code; zarrita/igv.js/Mol\*/DuckDB-WASM), **Tier-2** (layout-slice,
  opt-in per datatype+layout for the 60fps hot path), or **Tier-3** (precompute-as-analysis for novel formats).
  A datatype declares which tier(s) its storage supports; the data API picks. Host provides exactly two
  domain-neutral capabilities: authed range serve (P1) + layout slice (ITEM-8).
- **ITEM-10**: Viewers-per-datatype dispatch contract. Datatype declares `viewers: Vec<ViewerRef{ family,
  params }>`; host `viewers_for(datatype_id)` resolves by walking the **subtype lattice** (a `matrix`-family
  viewer applies to `single-cell/anndata` by is-a). This is the contract P7 renders against: the deck.gl
  view-kinds are ONE viewer family (matrix-like); genome/structure/network are other families contributed by
  their datatype extensions. P2 owns the mapping; P7 owns the actual `registerViewKind` renderers + refactor.
- **ITEM-11**: Ingest + converter model. `IngestSpec` (uploaded file → this type, e.g. `.h5ad →
  single-cell/anndata` via a sandbox convert-to-Zarr, or kerchunk-virtualize) and `ConverterRef[]` (implicit
  Galaxy-style conversions between types). Near-term: wire the **one HDF5→Zarr ingest converter** the vertical
  slice needs; the general converter graph is a seam (declared, not traversed yet).
- **ITEM-12**: Seed built-in datatype set (proves lattice + layouts). `data` (root) ← `tabular` ← `matrix` ←
  `single-cell/anndata`; plus `embedding` (ChunkedDense), `clustering` (ChunkedSparse/small), `metadata-column`,
  `de`/`table` (ColumnarTable), `report/html` (opaque blob). ~8 entries covering dense/sparse/columnar layouts +
  a 3-deep subtype chain. `variant/vcf`, `structure/pdb`, `genome/bigwig`, `image/ome-tiff` are documented as
  **later registry entries**, seam open, NOT built now.
- **ITEM-13**: REST + sync surface. `GET /api/datatypes` (the lattice + viewer refs + layouts + capabilities,
  for the FE mirror), `GET /api/studies/{id}/artifacts?type=&subtypesOf=` (type-filtered artifact query for
  auto-populated pickers), artifact read via P1's data API. Owner/study-scoped sync entity `Artifact`. Study
  cascade: an `artifacts` cleanup in a `datatype` study-extension `on_study_deleted` (mirror
  `dataset/study_extension`).
- **ITEM-14**: Frontend datatype registry mirror. `modules/datatype/` store consuming `/api/datatypes`, exposing
  `isA(sub, super)`, `viewersFor(datatypeId)`, `artifactsOfType(studyId, selector)` — driving viewer dispatch
  (feeds P7) + the `artifact-ref` auto-populated Select pickers (PLATFORM_ARCH §4.3 Tier-2, the
  `api.artifacts.query({type})` surface). Runtime-derived from the server lattice (no hand-maintained TS union).
- **ITEM-15**: `dataset` placeholder → source-artifact migration. Back the existing `datasets` table/module by
  the `artifacts` model (dataset = source artifact `datatype: single-cell/anndata` (or `file/*` pre-ingest),
  `produced_by: upload`). Keep the module's FE surface/routes; unify storage under `artifacts`. Data migration
  from the current placeholder rows.

## Dependencies

- **P1 (data-foundation)** — owns local-FS blob store + authed byte-Range endpoint + data-API plumbing.
  **Cross-part seam to resolve:** P1's `analysis_results` catalog (spec'd only in DATA_STORAGE_REDESIGN §3.5 —
  `{id, (study_id, analysis_id), run_id, job_id, kind, job_file, element_path, axis, covered_cells, shape,
  params, status, created_at}`; **not yet built**) and P2's `artifacts` table are the SAME table — unify to ONE
  `artifacts` table, one owner. Rename `kind`→`datatype_id`, add `layout`/`content_hash`/`source`. P2 supplies
  the type columns; P1 supplies the physical read path. **Note:** today's `txresbench-file` store is UUID-pathed +
  per-user (a `checksum` column, but NO content-addressing/dedup) — P1 must add the CAS/content-hash keying the
  artifact model's `content_hash` assumes; artifacts reference blobs by `(file_id, blob_version_id)` like
  `file_rag` does. (Blocks ITEM-4/8/9.)
- **P3 (compute)** — the `produces` outputs-manifest + sandbox `/outputs`. Blocks ITEM-6 (P2 ingests the
  manifest into N typed artifacts; P3 produces the files + manifest).
- **P4 (provenance)** — the run-node table + producer/output edges. P2's `produced_by_run_id` FK targets P4's
  run node; P4 owns the fan-out edges + used/dead-output reachability. Blocks ITEM-6 fully.
- **P5 (contribution-api)** — datatypes are one contribution kind under `@txresbench/workbench-api` + the external

- **P7 (visualization)** — consumes ITEM-10's viewer-dispatch contract; implements the `switch→registry`

- **P10 (study-substrate)** — artifacts are study-scoped (`study_id` FK, `EffectivePermission`); on_study_deleted

- **P11 (three-modules)** — exercises the seed datatypes (single-cell/anndata, embedding, clustering) end-to-end.

## Decisions

- **Server-authoritative registry.** The datatype lattice lives in Rust (`#[distributed_slice(DATATYPES)]`,
  mirror `STUDY_EXTENSIONS`), exposed via `GET /api/datatypes`; the FE is a runtime-derived read-only mirror.
  Rationale: analyses' `accepts`/`produces` gating, artifact validation, and the catalog are all server-side —
  the lattice must be authoritative there. Descriptors are declarative data (id/extends/schema/layout/
  capabilities/viewer-refs); only `validate`/`ingest` are code.
- **One `artifacts` table, owned by P2's `modules/datatype`** (not two — merge P1's `analysis_results`). Dataset,
  analysis output, imported file are all rows; `source` bool + `produced_by_run_id` distinguish provenance. P1
  owns the physical store + range serving; P2 owns the typed catalog columns.
- **`datatype_id` is a validated string, not an FK** (the registry is in-code, no `datatypes` table). Boot-time
  validation rejects unknown ids from built-ins; runtime artifacts with an unknown datatype (removed extension)
  render as a generic "unknown datatype" card rather than crash.
- **LayoutKind is a small fixed core set** `{ChunkedDense, ChunkedSparse(CSC/CSR), ColumnarTable, Chunked1d}` —
  the Zarr/TileDB/Arrow model. A new **datatype** is a registry entry (no core change); a new **layout** is a
  rare core change. Single-cell CSC is one layout, equal to dense/columnar/1d — **no domain privilege**.
- **Tier-1 (authed range + client decode) is the DEFAULT** (zero host format code); Tier-2 layout-slice is
  opt-in per datatype+layout for the interactive hot path only; Tier-3 = precompute-as-analysis for novel
  formats. Zarr-as-served-format makes the host a dumb range server; the client (zarrita) slices.
- **Subtype match for `accepts`; supertype walk for viewer fallback.** `subtypesOf:true` selector = "this type
  or any subtype". `viewers_for` climbs the lattice so a supertype viewer covers subtypes.
- **Near-term seed = ~8 datatypes** proving the lattice + dense/sparse/columnar + one HDF5→Zarr ingest
  converter. Variant/structure/genome/imaging are later registry entries — seam open, populate incrementally
  (DATA_MODEL "design the seam open now; populate it incrementally").
- **Multi-file → one content hash** (merkle/manifest over the file set); multi-output → N artifacts one run
  (fan-out). produce-atomically / consume-individually.

## Risks

- **P1/P2 catalog-table double-ownership** (`analysis_results` vs `artifacts`) — must converge to one table +
  one owner or the schema forks. HIGH; resolve in sequencing step 1 with P1's planner.
- **ITEM-6 blocked on unbuilt P3 manifest + P4 run node** — the multi-output path can't be validated until
  those land; keep the single-output path working meanwhile and sequence ITEM-6 late.
- **Over-building Tier-2 slicers.** Four layout slicers is real work; Tier-1 client-decode removes most of it.
  Ship only sparse+dense server-slicing (the 60fps hot path); route everything else through Tier-1/columnar
  client decode.
- **ViewerRef schema churn with P7.** If P2's dispatch contract doesn't match P7's `registerViewKind` shape,
  both re-work. Co-design the `ViewerRef` `{family, params}` shape with P7 before ITEM-10 lands.
- **FE mirror drift.** Hand-maintaining a TS datatype union will diverge from the server lattice; derive it at
  runtime from `/api/datatypes` (ITEM-14) — no static mirror.
- **sqlx compile-time vs open datatype ids.** The `artifacts` table is a kernel (compile-time-checked) table,
  fine; but the *open* `datatype_id` means no DB-level referential integrity for it — enforced at boot + graceful
  degradation, not by FK.
- **Scope creep to "general bioinformatics workbench".** The model is broad; hold the near-term line at the
  single-cell seed set with the seam open, per DATA_MODEL's honest-scope note.

## Effort

- ITEM-1/2/3 (registry + lattice + type-match): **M** — mechanical mirror of `STUDY_EXTENSIONS` + a small graph.
- ITEM-4/5/15 (artifact model + multi-file + dataset migration): **M–L** — schema + the P1 unification seam.
- ITEM-7/8/9 (layouts + slicer + tiers): **L** — the technically deepest; bounded by shipping only sparse+dense
  server slicing near-term.
- ITEM-6 (multi-output ingest): **M**, but gated on P3/P4.
- ITEM-10/11 (viewer dispatch + ingest converter): **M** — contract + one HDF5→Zarr converter.
- ITEM-12/13/14 (seed set + REST + FE mirror): **M**.

Total: **Large** (~the biggest of the foundation parts alongside P1), but front-loaded value: ITEMs 1–4 unblock
P3/P5/P6/P7 gating immediately; the layout/tier depth (7–9) can land incrementally behind Tier-1.
