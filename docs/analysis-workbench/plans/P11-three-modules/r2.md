# P11 — Three modules (the vertical slice): data-io · embedding · clustering

**What this is.** The end-to-end proof that a single-cell workflow (upload → QC/normalize → embed → cluster →
explore) is buildable as **three no-Rust extensions** composed purely by the artifact graph, each run captured
in provenance. It builds **nothing in the kernel** — it *consumes* P1 (working store + catalog + data API + authed
range serving), P2 (open datatype registry + subtyping + storage layouts), P3 (JobRunner→bwrap + scientific
rootfs + `inputs.json`/outputs-manifest contract), P4 (provenance auto-capture), P5 (`@cyto/workbench-api` +
manifest loader + declarative `settings` provisioner + build-time discovery glob), P6 (docks + host-rendered
form-from-schema + result-from-kind + `fieldProvider`/`selectionAction` slots), P7 (view-kind registry), P8
(shared selection + recipe). If a module needs Rust, that's a bug in P1–P8, not a P11 item.

Each extension is a self-contained dir under `extensions/` (created by P5): `extension.yaml` + `compute/*.py`
(sandboxed) + `schema/*.json` (params + settings JSON-schema) + `ui/*.tsx` (built against `@cyto/workbench-api`).
Compute is **always** a sandboxed Python script (scanpy/anndata/leiden/umap ecosystem); "save" is not code — the
script writes typed artifacts + a `manifest.json` to `/outputs`; the host ingests + catalogs + stamps provenance.

Ground truth for the parameter vocabulary is the legacy forms (`cytoanalyst-ref/sc-website`:
`NewEmbeddingForm.tsx`, `NewClusteringForm.tsx`, `CellFilteringFormItems.tsx`, `UploadForm.tsx`) and job-templates
(`data-process.ts`/`sample-save.ts`/`embedding-create.ts`/`clustering-create.ts`). The interface-round mocks
(`ui/src/modules/analysis/analyses/{qc-filter,normalize-lognorm,pca,umap,leiden,...}/plugin.tsx`) are the
descriptor shape (id/category/requires/produces/params/defaults/methodsText) to promote from FE-mock →
declarative manifest + real sandbox compute.

## Items

### Module 1 — data-io (upload + sandboxed QC/normalize + save)
- **ITEM-1**: `extensions/data-io/extension.yaml` — manifest declaring: `analyses: [data.process, save.sample]`;
  `views: [{samples, area:left, component:ui/UploadPanel}, {qc-review, area:bottom, when:"has:qc-report",
  component:ui/QcReviewPanel}]`; `settings: [{id:qc-defaults, schema:schema/qc.settings.json}]`;
  `activation: [onView:samples, onAnalysis:data.process]`; `apiVersion:"^1.0"`. Each analysis carries LLM-facing
  metadata (`description`/`when`/`examples`/`safety: read-run`) so P9 auto-emits the MCP tool.
- **ITEM-2**: `schema/process.params.json` — the QC+normalize params JSON-schema grounded in the legacy vocabulary:
  QC filter — `min_genes`, `max_genes`, `max_pct_mito` (+ `mito_regex` default `^MT-|^mt-`), `min_cells`, optional
  ribo/cell-cycle regress toggles (`regress_mito`/`regress_ribo`/`regress_cellcycle` + gene lists); normalize —
  `method` enum (`logNormalize`|`SCT`), `scaling_factor` default 10000, `find_var_feature_method` enum (`vst`),
  `n_var_features` default 3000; `sample_id_filters` (artifact-ref multi). Renders via P6 host form-from-schema.
- **ITEM-3**: `compute/process.py` — sandboxed scanpy script: reads `/inputs/matrix.*` (uploaded-matrix handle) +
  `/inputs/params.json`; runs QC metrics → filter cells/genes → normalize (log1p / target-sum) → HVG → optional
  regress-out; writes `/outputs/expression.zarr` (`single-cell/expression`, chunked-sparse CSC layout for P1/P2
  fast gene-column slicing), per-cell obs `metadata-column` artifacts (n_genes, pct_mito, total_counts), a
  `qc-report` artifact (pre/post distributions + threshold cutlines as JSON+small parquet), and `manifest.json`
  mapping output paths → typed artifacts (one run node fans out to N artifacts, per DATA_MODEL "one job → many
  outputs").
- **ITEM-4**: `compute/save.py` + `save.sample` analysis — takes the reviewed/accepted `expression` (+ obs) and
  materializes the persisted **sample** artifact(s) (per-sample split when multi-sample: `sample_id_in`,
  delimiter/position from legacy UploadForm) → `produces: [sample]`. Host ingests → catalog `sample` rows. (The
  "save" is host-ingest of typed outputs, not module storage code.)
- **ITEM-5**: `schema/qc.settings.json` + declarative `settings:qc-defaults` — deployment-wide default QC
  thresholds (min_genes/max_pct_mito/…); P5 declarative `settings` provisioner renders the admin card + gated
  GET/PUT + sync entity, **zero server code**. `data.process` params default from this row when unset.
- **ITEM-6**: `ui/UploadPanel.tsx` (left dock) — thin panel over `@cyto/workbench-api`: drives the host **file
  store** (`ziee-file`) upload (supported types AnnData `.h5ad`, 10x `.h5`/`.zip`/`.tar.gz`, mtx trio), shows the
  uploaded-file → `uploaded-matrix` artifact, and offers "Process" (opens the host-rendered `data.process` form).
  Client-side preview (assays, N cells, metadata columns) mirrors legacy `read-anndata`/`read-10X` — parse in JS
  for preview only; real ingest is the sandbox.
- **ITEM-7**: `ui/QcReviewPanel.tsx` (bottom dock, `when:"has:qc-report"`) — renders the `qc-report` artifact:
  pre/post-filter QC violin/histograms (n_genes, pct_mito, counts) with threshold cutlines, cells-kept/removed
  KPIs, per-sample table; **Accept** (→ `save.sample`) / **Re-run with new thresholds** (re-opens `data.process`).
  This is the "QC-review" JTBD affordance — a human must see what filtering did before committing.
- **ITEM-8**: `qc-report` datatype + its viewer registration — declare the `report/qc` datatype (P2 registry;
  small parquet/JSON storage layout, `viewers:[qc-review]`) so the QC panel is dispatched by datatype, not
  hardcoded. (`single-cell/expression` + `matrix` supertype + `metadata-column` come from P2 core; data-io only
  adds `report/qc`.)

### Module 2 — embedding (sandboxed umap/pca → embedding; fieldProvider; scatter view-kind)
- **ITEM-9**: `extensions/embedding/extension.yaml` — `analyses: [embedding.umap, embedding.pca]`
  (`accepts:[{type:single-cell/expression, subtypesOf:true}] → produces:[embedding]`); `fieldProviders:
  [embeddings]`; declares (or references built-in) the `scatter` view-kind for `coordinates`/`embedding`. LLM
  metadata + `safety: read-run`. `recipeOrder` after data-io in the standard recipe.
- **ITEM-10**: `schema/umap.params.json` + `schema/pca.params.json` — grounded in `NewEmbeddingForm`: PCA —
  `n_pcs`/`nPCADim` default 30, `dim_reduction_method` (`tsvd`), HVG upstream; UMAP — `n_neighbors` default 30,
  `min_dist` default 0.3, `metric` enum default `cosine`, `spread` default 1 (+ tSNE `perplexity` 30 optional as
  a second method). `sample_id_filters`/`metadata_filters` as artifact-ref/cell-subset inputs. Optional Harmony
  `integrated_by:sample` toggle deferred to a later integration module (seam noted, not built).
- **ITEM-11**: `compute/pca.py` + `compute/umap.py` — sandboxed scanpy: read `/inputs/expression.zarr` → scale →
  PCA (`sc.pp.pca`) → `sc.pp.neighbors` → `sc.tl.umap`; write `/outputs/embedding.zarr` (obsm `X_umap` N×2, dense
  `chunked-dense` layout) + `manifest.json` (`type:embedding`). PCA can produce a separate `reduced`/`pca`
  embedding artifact consumable by clustering.
- **ITEM-12**: `ui/EmbeddingFields.tsx` — registers a **`fieldProvider:embeddings`** into the P6 left-rail slot:
  lists the study's `embedding` artifacts (catalog query via `api.data.catalog()`), a click sets the active
  embedding as the scatter's coordinate source. No catalog SQL — declared `accepts` binds the artifact graph.
- **ITEM-13**: **Adopt live3's scatter as the built-in `scatter` view-kind.** Register
  `visualization-wt/.../viz-core/DeckScatterCanvas.tsx` (+ `ColormapScatterLayer`, `SelectableScatter`,
  `ChunkedScatter`) into the P7 **view-kind registry** with a declared data contract: `coordinates` N×2 from an
  `embedding` artifact (P1 typed-binary/zarrita range read), color-by from a `fieldProvider` (cluster/metadata/
  gene), selection wired to P8. Must pass P7's conformance battery (`viewKindBattery.test.ts`). This is the one
  view-kind the slice ships as built-in; it is the center-canvas hero (WORKBENCH_IA).

### Module 3 — clustering (sandboxed leiden → clustering; fieldProvider; selectionAction:subcluster)
- **ITEM-14**: `extensions/clustering/extension.yaml` — `analyses: [clustering.leiden, clustering.louvain]`
  (`accepts:[{type:embedding}] → produces:[clustering]`; gated until an `embedding` exists);
  `fieldProviders:[clusterings]`; `selectionActions:[{id:subcluster, when:"has-selection", command:
  clustering.subcluster}]`. LLM metadata (`description:"Group cells into clusters on the neighborhood graph of an
  embedding"`, `when`, `examples`, `safety: read-run`).
- **ITEM-15**: `schema/leiden.params.json` — grounded in `NewClusteringForm`: `method` enum
  (`leiden`|`louvain`|`kmeans`) default `louvain`, `resolution` 0.01–3 default 0.6 (hidden unless graph method),
  `n_neighbors` default 20, `distance_metric` (`euclidean`|`cosine`), `n_iterations` default 10, `seed`,
  templated `name:"Cluster {embedding}"`, `embedding_ids` artifact-ref (multiple). kmeans branch → per-embedding
  `n_clusters` (the legacy `nCluster_{embeddingId}` dynamic field → schema `repeat-per` embedding).
- **ITEM-16**: `compute/leiden.py` — sandboxed scanpy: read `/inputs/embedding.zarr` → (re)build kNN graph →
  `sc.tl.leiden`/`louvain` at resolution → write `/outputs/clustering.zarr` (obs categorical: `codes` Uint16 +
  `categories`) + `manifest.json` (`type:clustering`). Deterministic on `seed` for reproducibility.
- **ITEM-17**: `ui/ClusterFields.tsx` — registers `fieldProvider:clusterings` → color-by in the left rail;
  clicking a clustering colors the scatter by cluster (categorical colormap via the view-kind's Coordination
  store, P7).
- **ITEM-18**: **`selectionAction:subcluster`** — on the current shared selection (P8 cell-set, stored as a
  **recipe** — predicate + input hash, not a materialized list), run `clustering.leiden` scoped to the selected
  cells → a new `clustering` artifact covering only that sub-population (NA outside). Reads `api.selection`,
  submits a compute job scoped by the recipe, writes back a clustering. Proves the selection→re-analysis loop +
  provenance recipe end-to-end.

### Cross-cutting (compose the three; prove the platform properties)
- **ITEM-19**: **Artifact-graph composition + availability gating** — verify (no new code) that the kernel builds
  the DAG from each manifest's `accepts`/`produces`: data-io ungated; embedding gated on `single-cell/expression`;
  clustering gated on `embedding`; subcluster on `has-selection`. The catalog `requires`/`produces` edges ARE the
  provenance edges (P4). No module imports another.
- **ITEM-20**: **Standard-recipe spine** — `inStandardRecipe`/`recipeOrder` across the three (upload/process=1,
  embed=2, cluster=3) so the host assembles the guided "Run standard analysis" path from the registry (mirrors
  interface-round `analysisRegistry.standardRecipe()`), correct as modules are added/removed.
- **ITEM-21**: **Scientific rootfs deps** — ensure the P3 scientific rootfs image includes
  `scanpy`/`anndata`/`zarr`/`leidenalg`/`umap-learn`/`scikit-misc`(HVG)/`harmonypy` at the pinned versions the
  three `compute/*.py` import; add a smoke test that each script imports cleanly in the rootfs. (Adds package
  requirements to P3's rootfs manifest — the only "backend" touch, and it's a data/dep declaration, not Rust.)
- **ITEM-22**: **Provenance + methodsText** — each analysis declares `methodsText(p)` (promote from the mock
  plugins) so the run node carries a templated methods paragraph; verify each sandbox run auto-produces a run
  node + content-addressed code blob + input/output edges via P4 (zero P11 code — it's inherent in the compute
  contract).
- **ITEM-23**: **MCP surface (auto, verify)** — confirm each analysis + the `subcluster` selection-action becomes
  a P9 MCP tool from the manifest metadata (no MCP code in P11); the AI can chain `embedding.umap` →
  `clustering.leiden` over the typed graph. Add the untrusted-content note only if the module surfaces external
  data (it doesn't).
- **ITEM-24**: **Zarr-on-ingest decision wiring** — data-io `process.py` writes served artifacts as **Zarr**
  directly (AnnData-Zarr, so P1/zarrita range-read + P2 chunked-sparse work without an HDF5 slicer). If an upload
  is `.h5ad`, the sandbox converts to Zarr at process time (anndata writes Zarr natively). No HDF5-specific host
  Rust in the serve path (per DATA_MODEL storage table).

### Tests
- **ITEM-25**: **Unit** (FE + schema) — manifest JSON-schema validity + `apiVersion` range; params schema
  round-trip (host form renders every field type); availability gating (`missing`/`runnable`) per module;
  `fieldProvider` list derivation; `methodsText` templating; the scatter view-kind passes the conformance battery.
- **ITEM-26**: **Integration** (real sandbox, tiny fixture) — a ~200-cell `.h5ad` fixture through:
  `data.process` → assert `expression`+`qc-report`+obs artifacts land in the catalog with a provenance node;
  `embedding.umap` → assert an `embedding` (N×2) artifact; `clustering.leiden` → assert a `clustering` (codes+
  categories) artifact; `subcluster` on a predicate selection → a selection-scoped clustering. Runs via
  P3 JobRunner→bwrap; scoped to the study (P10). Save full logs (`tee`).
- **ITEM-27**: **E2E** (Playwright, on the real workbench shell) — upload the fixture → Process (QC form) →
  review QC panel → Accept → embed → color-by embedding on the scatter → cluster → color-by cluster → lasso a
  region → Subcluster → new clustering appears. The single spec that proves the whole vertical slice on the real
  canvas.

  `CellFilteringFormItems.tsx` (sample/metadata/cluster filters), `UploadForm.tsx` (file types, multi-sample
  split), and `server/job-templates/{data-process,sample-save,embedding-create,clustering-create}.ts` (compute
  step shape — Rscript→Python port; scanpy replaces the legacy Seurat/R).
- **Descriptor shape** from the interface-round mocks (`ui/src/modules/analysis/analyses/*/plugin.tsx` +
  `registry.ts` availability/standardRecipe selectors) — promote FE-mock `buildResult` → real sandbox compute +
  declarative manifest.
- **Scatter** = live3 `feat/visualization` deck.gl scatter (DeckScatterCanvas + ColormapScatterLayer +
  SelectableScatter + ChunkedScatter + conformance battery) — adopted as the built-in view-kind, not rebuilt.
- **Host kernel**: P1 data API/catalog/range-serving, P2 datatype registry, P3 `sandbox::run_analysis` +
  `ExtraMount` + JobRunner + rootfs, P4 provenance, P5 workbench-api + manifest loader + `settings` provisioner,

  file store `ziee-file`.

## Dependencies
- **Hard blockers (must exist first):** P1 (working store + catalog + data API + Zarr range-serving) · P2
  (datatype registry + `single-cell/expression`/`matrix`/`metadata-column` core types + chunked-sparse/dense
  layouts) · **P3 (JobRunner→bwrap + scientific rootfs + inputs.json/outputs-manifest — THE key dependency; no
  analysis runs without it)** · P5 (`@cyto/workbench-api` + manifest loader + build-time discovery glob +
  declarative `settings` provisioner) · P6 (docks + host form-from-schema + result-from-kind + `fieldProvider`/
  `selectionAction`/`view` slots).
- **Feature-completing:** P7 (view-kind registry — scatter) · P8 (selection + recipe — subcluster) · P4
  (provenance auto-capture — methodsText/run nodes) · P9 (MCP auto-generation — verify) · P10 (study substrate —
  scoping/sync).
- **Internal ordering:** ITEM-3/4 (data-io compute) → ITEM-11 (embedding compute) → ITEM-16 (clustering compute)
  by artifact type. UI + schema per module can proceed once P5/P6 slots exist. ITEM-13 (scatter) needs P7.
  ITEM-18 (subcluster) needs P8. ITEM-19/20 need all three manifests. Tests (25–27) last.

## Sequencing
1. **Gate**: confirm P1/P2/P3/P5/P6 landed (data API read/write, a datatype registered, a sandbox analysis runs
   end-to-end, a manifest discovered, a form renders). If not, P11 is blocked — do not stub the kernel.
2. **data-io** (ITEM-1–8, 24): manifest + `process.py`/`save.py` + params/settings schema + UploadPanel +
   QcReviewPanel + qc-report datatype. Deliver: upload → QC/normalize → `expression` in catalog + QC review.
3. **embedding** (ITEM-9–13): manifest + pca/umap compute + params + EmbeddingFields + adopt scatter view-kind
   (P7). Deliver: expression → embedding → colored scatter on the canvas.
4. **clustering** (ITEM-14–18): manifest + leiden compute + params + ClusterFields + subcluster selection-action
   (P8). Deliver: embedding → clustering → color-by + lasso→subcluster.
5. **Cross-cutting** (ITEM-19–24): composition/gating, standard recipe, rootfs deps, provenance, MCP, Zarr-ingest.
6. **Tests** (ITEM-25–27): unit → integration (real sandbox fixture) → e2e vertical slice.

## Decisions
- **Compute engine = scanpy/anndata (Python), not Seurat/R.** The legacy ran Rscript; the platform's rootfs and
  ecosystem (leidenalg, umap-learn, zarr) are Python-first, and DATA_MODEL's Zarr serve-path aligns with
  anndata's native Zarr writer. Port the legacy params, not the R.
- **Served format = Zarr (write directly in compute), tables = Parquet, qc-report = small parquet+JSON.** No
  HDF5 in the serve path; `.h5ad` uploads are converted to Zarr inside `process.py`. (DATA_MODEL storage table.)
- **`save.sample` is host-ingest, not module storage code.** The compute writes typed artifacts + `manifest.json`;
  the host catalogs them. Module 1 adds only the declarative `qc-defaults` settings row (Layer A) — zero SQL.
- **One built-in view-kind ships in P11: `scatter`** (adopted from live3). Other view-kinds (violin/heatmap/
  dot-plot) are P7's library — the slice needs only scatter to prove color-by. Non-scatter QC plots render inside
  the QC-review panel from the `qc-report` artifact (host-rendered), not as canvas view-kinds.
- **Selection stored as a recipe (predicate + pinned input hash), never a materialized cell list** (P8/P4) — so
  subcluster is reproducible and scale-safe.
- **Datatypes: `report/qc` is contributed by data-io; `single-cell/expression`+`matrix`+`metadata-column`+
  `embedding`+`clustering` are P2 core** (shared across modules). data-io/embedding/clustering declare `produces`
  against them; only `report/qc` is module-owned.
- **Dynamic/dependent fields** (kmeans `nCluster_{embeddingId}`; method-hidden resolution/neighbors) expressed via
  the P6 schema's `when`/`repeat-per`; if a case exceeds the schema, fall back to a Tier-4 code form — but the
  three modules should be fully declarative (they were ~90% typed fields in the legacy inventory).

## Risks
- **Foundation not ready.** P11 is the *last* phase and totally blocked on P1–P8. If the compute path (P3) or
  data API (P1) is a stub, the "no-Rust extension" claim can't be demonstrated. Mitigate: the ITEM-1 gate; build
  P11 only after a single sandbox analysis proven end-to-end.
- **Rootfs dep drift.** scanpy/leidenalg/umap version skew → import failures inside bwrap (`--clearenv`, no
  network). Mitigate ITEM-21 import-smoke test; pin versions in the rootfs manifest.
- **Zarr write inside the sandbox** must produce a P1/P2-ingestable layout (chunked-sparse CSC for expression,
  chunked-dense for embedding, categorical for clustering) exactly as the datatype declares — a mismatch breaks
  range-read/color-by. Mitigate: integration test asserts the served gene-column + coordinate reads.
- **Subcluster selection scoping** — the recipe must map the P8 predicate to the cells the sandbox job filters on
  (covered_cells provenance); off-by-axis errors silently mis-cluster. Mitigate: ITEM-18 asserts NA-outside +
  covered_cells.
- **QC-review UX correctness (JTBD).** Filtering that silently drops half the cells is a defect even if the code
  "works" — the review panel must make pre/post + cutlines legible before Accept. Mitigate: ITEM-7 + the e2e
  spec assert the review affordance, not just the artifact.
- **View-kind adoption coupling** — live3's scatter is `switch(cell.kind)`-closed until P7's registry refactor;
  P11's scatter registration depends on that refactor landing (P7), not on P11.
- **MCP metadata completeness** — a missing `description`/`safety` yields an unusable or wrongly-gated AI tool.
  Mitigate: ITEM-23 lints every analysis manifest for LLM metadata.

## Effort
~4–6 engineer-weeks **assuming P1–P8 are landed** (this is a consumer, not a builder). Rough split: data-io
(compute + upload/QC panels + qc-report datatype) ≈ 2 wk (heaviest — file ingest + QC review UX); embedding
(compute + fieldProvider + scatter adoption) ≈ 1–1.5 wk (scatter is adopted, not built); clustering (compute +
fieldProvider + subcluster) ≈ 1 wk; cross-cutting + rootfs deps + tests ≈ 1–1.5 wk. Dominated by the three
`compute/*.py` correctness + the integration/e2e proof; the UI is thin over `@cyto/workbench-api`. **Zero Rust.**
