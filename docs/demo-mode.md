# Demo mode

TxResBench can run as a **web-service demo**: the same app, served over
HTTP, restricted to the example data with recorded results in place of real
runs, and a single shared workspace for every visitor. The desktop app is
the default; demo mode is a deployment choice (config, env or CLI switch)
and never falls back on — or hides — anything the desktop build does.

This page is the deployment reference: the configuration, the bundle, the
limits, what is blocked, and how to run and verify the demo.

## What the demo is

- **The example data only.** The app's own example tables (100 patients,
  2959 measurement rows, 269 predict rows — three markers) are the only data
  any visitor can load; every file-upload surface answers `403 DEMO_MODE`
  for anything else.
- **Recorded results.** A run replays the results of real runs that were
  recorded once, in desktop mode, on the example data: the states, the
  per-method predictions, the log lines and the measured seconds all come
  from the recording. No analysis code, no sandbox, no environment download
  and no network is used at run time in demo mode.
- **One shared pool.** Every visitor reads the same runs, results and saved
  models, and the pages say so. The only per-visitor state is an anonymous
  cookie session, used for rate limiting and for stopping a run the same
  browser started. Delete, rename, import and export are blocked; the
  retention below deletes old entries automatically.
- **Nothing to download, nothing to track.** The demo runs on your own
  server; no analytics and no tracking anywhere. It speaks HTTP only, never
  out to the internet.

## Configuration

The demo block is a top-level `demo:` key of the server config file:

```yaml
demo:
  enabled: true
  download_url: "https://github.com/tinnlab/txresbench-app/releases"
  history_limit: 50
  model_limit: 50
  max_bytes: 8388608
  replay_speed: 10.0
  notice: "demo_banner"
  bundle_path: "/var/lib/txresbench-demo/demo-bundle"
```

| key | default | meaning |
|---|---|---|
| `enabled` | `false` | demo mode on (config-file leg) |
| `download_url` | `""` | the desktop download page the notice bar and header link open; empty renders no link |
| `history_limit` | `50` | shared-pool retention limit for runs (the "last 50 runs" the pages quote) |
| `model_limit` | `50` | shared-pool retention limit for model rows (whole sets are evicted) |
| `max_bytes` | `8 MiB` | request-body cap; visitors can only post the small example tables, so this bounds a hostile payload at the wire level |
| `replay_speed` | `10.0` | divisor of the recorded seconds during a replay (each method at least 1.5 s) |
| `notice` | `"demo_banner"` | notice text key; the server maps it to the canonical sentence, an unknown key falls back to the default |
| `bundle_path` | `<app-data-dir>/demo-bundle` | the recorded bundle directory |

The switch is **CLI `--demo` > env `TXR_DEMO=1` > file `demo.enabled` > off**.
The env and CLI legs are ON-only (`TXR_DEMO=0` leaves the file's decision
standing); the tunable values always come from the file.

Relevant env vars:

| var | meaning |
|---|---|
| `TXR_DEMO` | ON-only demo switch (`1`; any non-empty non-`0` value) |
| `TXR_DEMO_BUNDLE` | the bundle directory; wins over `demo.bundle_path` |
| `TXR_APP_DATA_DIR` | the app data dir (the SQLite store, run dirs, the bundle's default home) |
| `TXR_DATABASE_URL` | SQLite target; wins over `database.url`/`database.path`/the data-dir default |
| `TXR_SECRET_STORAGE_KEY` | at-rest secret encryption key (deployment secret like `jwt.secret`) |

`GET /api/app/mode` (no auth) answers
`{mode: "demo", download_url, limits: {history, models}, notice}`; the UI
reads it at boot. The desktop build answers `{mode: "desktop", …}` with an
empty notice.

## The demo bundle

Demo runs replay a **recorded bundle**: a version-1 JSON manifest plus one
chance-shaped prediction table (`patient_id,probability,note`) per recorded
method, per recorded configuration, for the train run and for the reuse run
on the example predict table. The manifest also carries the example tables'
content hashes, the measured seconds, the log lines and each saved model's
metadata.

The bundle is generated by a **real desktop-mode run** on the example data:

```bash
# against a running desktop-mode server (default http://127.0.0.1:3100)
python3 scripts/demo/record-demo-bundle.py --out /var/lib/txresbench-demo/demo-bundle
```

To replace the bundle, record a fresh one to the same path and restart the
service. The loader validates the bundle **at boot**: a missing manifest, a
wrong format or version, a stale content hash (the example files changed), a
malformed table or an undefined configuration refuses to start demo mode
with a message naming the path and the recorder. A bundle recorded against
different example data is refused on purpose — the demo may never replay
predictions recorded for other tables.

## Limits

- Runs: the newest `history_limit` non-pinned runs are kept (50 by default);
  the seeded example run and the example model set are **pinned** and never
  evicted or counted.
- Models: non-pinned model rows beyond `model_limit` are evicted as whole
  sets, oldest first, with their files (rows and files in one transaction).
- Enforcement runs after every run/model-set insert, every 10 minutes and at
  boot; a run that is still replaying is never evicted.
- Rate limits: the framework limiter is always configured in demo mode
  (`server.rate_limit` when set, else 50 requests/s with a burst of 500),
  and every browser session gets its own governor keyed on the anonymous
  cookie (falling back to the peer IP).
- Request body: `demo.max_bytes` (8 MiB); enforced as a body-stream
  middleware, so it caps even the file-validation routes that disable their
  own extractor-level limit.
- Anonymous sessions: the cookie lives 30 days; stale sessions are reaped.

## What is blocked

One route-policy table (`src-app/server/src/modules/demo/allowlist.rs`)
classifies every operation of the OpenAPI surface as **allowed**, **adapted**
or **blocked**; the whole-app gate answers `403
{"error_code": "DEMO_MODE", "message": "This is not available in the demo"}`
for anything blocked, and a route added without a row fails the suite (the
gate also fails closed). The classification: the app's own read routes plus
the auth session trio (`GET /auth/me`, `POST /auth/refresh`,
`POST /auth/logout`) are allowed; the data and run surfaces are adapted
(example-only uploads, recorded runs, replay controls for the starting
session, generated model names, shared-pool counters); everything else —
delete/rename/import/export/clear, pretrained download-install-refresh, and
every framework route (accounts, auth providers, admin features, files, mcp,
notifications, sandbox, sync) — is blocked. The completeness test pins the
table against the shipped OpenAPI spec, so the blocklist cannot quietly
drift.

## Running the demo

```bash
# record the bundle once (desktop mode), then serve:
scripts/demo/run-demo.sh \
    --data-dir /var/lib/txresbench-demo \
    --bundle /var/lib/txresbench-demo/demo-bundle \
    --download-url https://github.com/tinnlab/txresbench-app/releases
```

`run-demo.sh` writes the server config (bind address/port, the demo block,
a generated `jwt.secret` persisted next to it) into the data dir, checks the
bundle's manifest, and execs the `txresbench` binary with `--demo`. On the
sigtrans development host every process is capped through `ops/cap.sh`
(`CAP_SH`, `CAP_CPUS` never above 4); a deployment host may set `CAP_SH=`.
`--port 0` binds an ephemeral port and prints the address at boot.

Samples to copy and edit (not configured here): the systemd unit
`scripts/demo/systemd/txresbench-demo.service` (foreground service, restart
on failure, its own data dir) and the reverse-proxy snippet
`scripts/demo/nginx/txresbench-demo.conf`:

- TLS terminates at the proxy; the demo server binds `127.0.0.1`.
- The proxy must send `Host`, `X-Forwarded-For`, `X-Forwarded-Proto` and
  `X-Forwarded-Host` — the generated config sets
  `server.trust_forwarded_headers: true`, and those headers are what make
  the rate-limit keys and the TLS-detection correct behind the proxy.
- `proxy_buffering off` (the events stream) and a generous
  `proxy_read_timeout` are the two directives that matter for the UI.

## Verification

`scripts/demo/e2e-demo.py` is the deployment proof. It boots its own demo
server (or attaches to a running one with `--app-url`) and drives the three
paths — train, reuse, pretrained — over the API, then checks: the blocked
route sweep (every OpenAPI operation outside the allowlist answers
`403 DEMO_MODE`, and an upload attempt fails), the two-session shared pool,
stop/skip refused to a foreign session, the 50-run/50-model retention with
the pinned entries kept, replay results equal to the bundle, and that no
sandbox process was ever started. The reference build and test flows are
the same as for any server change; no special build is needed for demo mode
(the switch is in the production binary).
